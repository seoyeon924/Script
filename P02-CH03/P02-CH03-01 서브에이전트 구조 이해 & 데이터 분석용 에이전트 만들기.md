## s3 — 서브에이전트란?

**[화면: 슬라이드]**

서브에이전트는 Claude 모델이 작업을 나눠서 실행하는 독립 인스턴스입니다.

화면의 흐름을 보시면요.
사용자가 요청하면 **Claude 모델(현재 세션)**이 작업을 분석해요.
그리고 서브에이전트 1, 2, 3을 만들어요.

여기서 중요한 게 셋이 동시에 시작한다는 거예요. 순서 없이 한꺼번에 처리합니다. 이게 **병렬 실행**이에요.
각 서브에이전트는 자기 일만 받아요. 다른 에이전트가 뭘 하는지 모릅니다. 이게 **독립 컨텍스트**예요.
각자 결과를 파일로 저장하고, 마지막에 메인 Claude가 취합해요. 이게 **파일로 취합**입니다.

한 명이 다 하는 게 아니라 역할을 나눠서, 동시에, 파일로 이어지는 구조예요.
이게 서브에이전트의 기본 작동 방식입니다.

## s27 — 서브에이전트, 언제 쓰면 좋을까

**[화면: 슬라이드]**

서브에이전트 구조가 특히 잘 맞는 상황이 세 가지예요.

**작업이 쪼개질 때**입니다.
수집·분석·시각화처럼 역할이 명확하게 나뉘는 작업이에요.
각자 맡은 것만 처리하면 되니까 서브에이전트 구조가 딱 맞습니다.

**반복 실행이 잦을 때**예요.
같은 파이프라인을 매주 돌려야 한다면, 한 번 구성해두면 계속 쓸 수 있어요.

**팀과 공유할 때**입니다.
.md 파일이라서 git으로 팀 전체가 같은 에이전트를 쓸 수 있어요.

반대로, 주의해야 할 상황도 있습니다.

**비용이 올라가요.**
에이전트 수만큼 컨텍스트 창이 따로 생기거든요.

**초기 설정이 필요합니다.**
파일 구성이랑 역할 정의에 시간이 들어요.

**간단한 작업엔 과해요.**
한 번짜리 질문은 Claude에게 바로 물어보는 게 빠릅니다.

그럼 이 구조가 왜 효과적인 걸까요?
서브에이전트의 특성을 하나씩 보면 이해가 됩니다.

## s4 — 서브에이전트 3가지 특성

**[화면: 슬라이드]**

앞에서 세 가지 특성을 언급했는데, 이제 각각이 실제로 어떤 의미인지 보겠습니다.

**01 독립 실행**입니다.

각 에이전트는 자기 일만 받아서 처리해요.
전체 대화는 모릅니다.
그래서 혼선이 없어요.
집중도는 높지만, 맥락은 따로 전달해야 합니다.

**02 순차 또는 병렬 실행**입니다.

서브에이전트가 항상 동시에 실행되는 건 아니에요.
의존성이 있으면 순차로, 없으면 병렬로 — 상황에 맞게 선택할 수 있습니다.
병렬로 돌릴 때는 처리 시간이 줄고, 그만큼 비용이 늘어나요.

**03 파일로만 소통**이에요.

에이전트끼리 직접 연결이 없어요.
결과를 파일로 저장하고, 메인이 마지막에 수집합니다.
결과 추적은 쉽지만, 파일 저장을 명시적으로 지시해야 해요.

이 세 가지 특성 덕분에 효율적이지만, 그렇다고 무조건 좋은 건 아니에요.
장단점을 같이 봐야 합니다.

## s18 — 데이터 시각화에서 서브에이전트의 장단점

**[화면: 슬라이드]**

데이터 분석 파이프라인에서 실제로 어떤 점이 좋고, 어떤 점을 주의해야 하는지 봅니다.

장점 세 가지예요.

**01 실패 단계만 재실행 가능**합니다.
EDA가 이미 완료됐다면, ingestion이랑 EDA는 건너뛰고 지표 설계 단계인 @analyst만 다시 실행하면 돼요.
파일이 체크포인트 역할을 하기 때문입니다.

**02 역할별 독립 컨텍스트가 있어 혼선 방지**예요.
@eda는 탐색만, @analyst는 지표만 — 각자 맡은 역할에만 집중하니까 결과 품질이 올라갑니다.

**03 병렬 처리도 선택적으로 가능**해요.
CSV 파일 여러 개를 동시에 분석하는 것처럼, 독립적인 작업은 한꺼번에 돌릴 수 있습니다.

단점입니다.

**01 초기 설정이 필요해요.**
에이전트 .md 파일이 있어야 합니다.
처음엔 시간이 들지만, 한 번 만들어두면 계속 쓸 수 있어요.

**02 단순 작업엔 오버스펙이에요.**
짧은 작업은 한번에 요청하는 게 빠릅니다.

**03 에이전트 간 직접 소통이 안 돼요.**
파일을 경유해야 해서 유연성이 제한됩니다.

그렇다면 구체적으로 어떻게 만드는 걸까요?
먼저 어디에 등록하는지부터 봅니다.

## s6 — 에이전트 파일 작성법

**[화면: 슬라이드]**

파일 구조는 세 부분으로 나뉩니다.

**❶ 이름 + 설명**이에요.
`name`이 호출 이름이 됩니다. `@eda`처럼 부르는 이름이에요.
`description`은 역할 요약입니다.

**❷ 모델 + 도구**예요. 둘 다 선택이에요.
`model`이랑 `tools`는 생략해도 됩니다.

**❸ 역할 지시서**예요.
이 에이전트가 어떤 일을 어떻게 처리할지 자연어로 써요.

오른쪽 예시를 보시면요.
name이 eda, description이 탐색적 분석 전담입니다.
model은 haiku, tools는 Bash, Read, Write로 설정했어요.
그 아래에 자연어로 역할 지시서를 써줬습니다.

구조는 이게 전부예요.
그럼 실제로 만드는 방법을 봅니다.

## s24 — 두 가지 만드는 방법

**[화면: 슬라이드]**

에이전트를 만드는 방법이 두 가지입니다.

**방법 1 — 에디터(안티그래비티·VS Code)**예요.

Claude에게 "데이터 분석 에이전트 생성해줘"라고 말하면 돼요.
.claude/agents/ 폴더에 파일이 자동으로 생깁니다.
생성 후에 **세션을 재시작**해야 @에이전트명으로 호출할 수 있어요.

**방법 2 — 터미널**입니다.

터미널에서 `/agents`를 입력하면 인터랙티브 UI가 열려요.
이름이랑 역할을 입력하고 저장하면 됩니다.
이 방법은 **세션 재시작 없이 바로 사용**할 수 있어요.
.md 파일로 자동 저장되니까 git으로 관리도 됩니다.

name과 description — 이 두 필드만 필수예요.
나머지는 나중에 추가해도 됩니다.
