## s17 — Agent Manager 빌드

> **🎬 촬영** — 슬라이드만

지금까지 클립 01에서 OpenClaw와 에이전트 구조를 살펴봤고, 클립 02에서는 파이프라인과 크론 자동화를 직접 실행해봤습니다.

클립 01에서는 OpenClaw를 설치하고 텔레그램 봇을 연결했어요. 클립 02에서는 Echo가 Aria, Sam, Min, Evan을 순서대로 지휘하는 파이프라인을 직접 돌려봤습니다.

크론 잡으로 매주 월요일 자동 실행까지 연결했고, 결과 파일이 `runs/latest/outputs/` 안에 일곱 개 쌓이는 것도 확인했죠.

이제 세 번째 클립입니다. 지금까지는 터미널로만 에이전트를 관리했어요. 명령어 치고, 출력 보고, 다시 명령어 치고. 에이전트가 한 명일 때는 그게 편한데요. 다섯 명이 동시에 움직일 때는 얘기가 달라집니다.

구체적으로 어떤 상황인지 예를 들어볼게요. 월요일 아침에 크론 잡이 제대로 돌았는지 보려면 `openclaw cron list`를 칩니다. 결과물이 나왔는지 보려면 `runs/latest/outputs/` 폴더를 열어봐야 해요. Min이 데이터 정제 중에 오류를 냈는지는 세션 기록을 따로 확인해야 하고요. 토큰을 얼마나 썼는지는 `openclaw status`로 봅니다. 확인 지점이 최소 네 군데예요.

Echo가 뭐 하고 있는지, Min이 오류 났는지, 크론 잡이 제대로 돌고 있는지를 터미널에서 하나씩 확인하려면 명령어를 네다섯 번 따로 실행해야 해요. 상태가 흩어져 있으니까요.

여기서 질문이 하나 나올 수 있어요. "터미널에 익숙해지면 되는 거 아닌가요?" 익숙함의 문제가 아닙니다. 상태가 네 군데에 흩어져 있으면 아무리 익숙해도 네 번 확인해야 해요. 확인 지점 자체를 한 곳으로 모아야 해결되는 문제입니다.

이 클립에서는 그 문제를 해결하는 도구를 직접 만들어요. 이름이 **Agent Manager**입니다. 에이전트 상태, 실행 결과물, 크론 잡을 전부 한 화면에서 볼 수 있는 네이티브 데스크탑 앱이에요.

한 화면에서 본다는 게 어떤 의미인지 미리 말씀드릴게요. 방금 말한 확인 작업들이 각각 Dashboard, Gallery, CronJobs 탭 하나씩에 대응됩니다. 명령어 네 번이 클릭 세 번으로 바뀌는 거예요.

앱 예시는 Echo, Min, Evan 세 명 기준으로 만들어요. PROMPT.md의 에이전트 배열에 두 명을 추가하면 다섯 명 전부로 확장할 수 있어요. 그 방법도 뒤에서 알려드릴게요.

만드는 방법이 좀 특이해요. 코드를 직접 짜지 않아요. `manager/` 폴더 안에 **PROMPT.md** 파일이 있습니다. 이 파일 하나에 앱 전체 설계가 다 담겨있어요. Claude Code에 이 파일 내용을 붙여넣으면 React와 Tauri로 된 앱이 자동으로 생성됩니다.

설계서를 글로 쓰고, 코드는 AI가 만드는 방식이에요. 그래서 이 클립의 앞부분은 앱 만들기가 아니라 **설계서 읽기**에 씁니다. PROMPT.md가 어떻게 쓰여 있는지를 뜯어보면, 여러분이 나중에 다른 앱을 만들 때 프롬프트를 어떻게 써야 하는지가 같이 잡혀요.

앱 개발 경험이 없어도 됩니다. Tauri가 뭔지 몰라도 됩니다. 프롬프트를 붙여넣고 기다리면 돼요. React 문법을 몰라도 이 클립을 따라오는 데 지장이 없습니다. 우리가 손으로 다루는 파일은 PROMPT.md 하나뿐이니까요.

그게 이 클립이 보여주고 싶은 것입니다. Claude Code는 "코드 작성 도구"가 아니에요. **설계서를 받아서 앱을 만들어주는 자동화 파트너**입니다. 어떻게 되는지 지금 바로 보겠습니다.

**[화면: 터미널 → 앱]**

먼저 터미널을 열어주세요. `manager/` 폴더로 이동합니다.

```bash
cd ~/Projects/openclaw-pipeline-kit/manager
```

이 폴더 안에는 지금 앱 설계서인 `PROMPT.md`, 간단한 안내 `README.md`, 그리고 Tauri 설정이 담긴 `src-tauri/` 폴더만 있어요. 앱 소스 코드는 아직 없습니다. 여기서 Claude Code를 실행할 거예요.

왜 하필 이 폴더 안에서 실행하는지 짚고 갈게요. Claude Code는 실행된 폴더를 작업 공간으로 삼습니다. 프롬프트에도 "이 폴더에 만들어줘"라고 써있어요. 상위 폴더에서 실행하면 파일이 엉뚱한 위치에 생길 수 있습니다. 프롬프트의 지시와 실행 위치를 맞추는 것, 작지만 중요한 습관이에요.

```bash
claude
```

Claude Code가 실행됩니다. 프롬프트 입력창이 뜨면 이제 PROMPT.md 파일을 열어야 해요. 여기서 잠깐, 이 파일에 뭐가 담겨있는지 같이 읽어볼게요.

**[화면: PROMPT.md 파일 열기]**

파일을 열면 맨 위에 이렇게 써있습니다.

```
# OpenClaw Agent Manager — 빌드 프롬프트
아래 내용을 Claude Code에 그대로 붙여넣으세요.
manager/ 폴더 안에서 실행하면 Agent Manager 앱이 자동으로 만들어집니다.
```

그리고 그 아래에 실제 프롬프트가 있어요. 처음 시작 부분입니다.

```
이 폴더(manager/)에 React + TypeScript + Vite + Tauri 2 앱을 만들어줘.
완성되면 npm install && npm run tauri dev 로 바로 실행되게 해줘.
```

기술 스택이 적혀있어요. **Vite 5, React 18, TypeScript, Tauri 2**. Tauri는 Rust로 만든 경량 데스크탑 프레임워크예요. Electron이랑 비슷하지만 훨씬 가볍습니다.

이 두 줄이 프롬프트 엔지니어링 관점에서 왜 중요한지 볼게요. 첫째, 기술 스택을 못 박았어요. 만약 "에이전트 관리 앱 만들어줘"라고만 쓰면 Claude Code가 스택을 스스로 고릅니다. 어떤 날은 Next.js로, 어떤 날은 Electron으로 만들어요. 결과를 예측할 수 없게 됩니다. 둘째, 완료 조건이 있어요. "npm install && npm run tauri dev로 바로 실행되게 해줘." 이 문장을 빼고 시키면 코드는 다 만들었는데 설정 파일이 빠져서 실행이 안 되는 경우가 생깁니다. 완료 조건을 명시하면 Claude Code가 실행 가능 여부까지 스스로 점검해요.

여기서 한 가지만 기억하시면 돼요. 외부 CSS 라이브러리가 없어요. 스타일을 전부 인라인 `style` 객체로 처리합니다. 이것도 의도된 선택이에요. CSS 라이브러리를 쓰면 설치되는 버전에 따라 결과가 달라질 수 있는데, 인라인 스타일은 프롬프트에 적은 값이 코드에 그대로 들어갑니다. 의존성이 줄어들수록 생성 결과의 편차도 줄어들어요.

그 다음에 **디자인 토큰** 섹션이 있습니다.

```
배경: #F9FAFB
텍스트 기본: #191F28
서브 텍스트: #6B7684
비활성: #B0B8C1
테두리: #E5E8EB
파란 accent: #3182F6
활성 배경: #EBF3FE
카드 배경: #FFFFFF
카드 그림자: 0 1px 6px rgba(0,0,0,0.07)
카드 radius: 12px
버튼 radius: 8px
폰트: system-ui, -apple-system, "Apple SD Gothic Neo", sans-serif
```

색상 값이 구체적으로 다 들어있어요. 배경색, 텍스트 색, 테두리 색, 강조색까지. 이게 왜 중요하냐면, Claude Code는 "예쁘게 만들어줘"라는 지시를 받으면 자기 판단으로 색을 고릅니다. 그 결과가 매번 달라져요. 일관된 UI를 원하면 이렇게 토큰을 직접 명시해줘야 합니다.

실제로 대조해보면 차이가 분명해요. 토큰 없이 "깔끔한 대시보드 스타일로"라고만 시키면, 버튼마다 radius가 다르고 회색이 세 가지쯤 섞인 화면이 나옵니다. 틀린 건 아닌데 통일이 안 돼요. 토큰을 명시하면 모든 컴포넌트가 같은 값을 참조하니까, 뷰가 여섯 개여도 한 사람이 만든 것처럼 보입니다.

여기서 잠깐 멈추고 생각해보세요. 여러분 회사에 브랜드 색상 가이드가 있다면, 그 값을 이 자리에 그대로 넣으면 됩니다. 배경색과 파란 accent 두 개만 바꿔도 앱 분위기가 완전히 달라져요.

**에이전트 목록** 섹션도 있습니다.

```
{ id: "main",  name: "Echo", color: "#818cf8", workspace: "~/.openclaw/workspace",      sessionsDir: "~/.openclaw/agents/main/sessions" }
{ id: "min",   name: "Min",  color: "#34d399", workspace: "~/.openclaw/workspace-min",  sessionsDir: "~/.openclaw/agents/min/sessions" }
{ id: "evan",  name: "Evan", color: "#fb923c", workspace: "~/.openclaw/workspace-evan", sessionsDir: "~/.openclaw/agents/evan/sessions" }
```

Echo, Min, Evan 세 명의 에이전트 정보예요. 각자 색상, 워크스페이스 경로, 세션 디렉토리가 지정돼있어요. 이 정보가 `constants.ts` 파일에 딱 한 곳만 들어갑니다. 앱 어디서든 이 파일 하나를 참조해요.

이렇게 한 곳에 모으라고 지시하는 이유가 있어요. 이 지시를 빼고 시키면 Claude Code가 에이전트 이름을 각 컴포넌트에 하드코딩하는 경우가 있습니다. 그러면 나중에 에이전트를 추가할 때 파일 여섯 개를 고쳐야 해요. `constants.ts` 한 곳만 참조하게 만들면 배열에 한 줄 추가하는 것으로 끝납니다. 프롬프트에서 데이터가 놓일 위치까지 지정해주는 것, 이게 유지보수를 내다본 설계예요.

경로도 눈여겨보세요. workspace와 sessionsDir이 에이전트마다 달라요. 에이전트마다 작업 폴더가 분리돼 있기 때문입니다. 이 경로가 틀리면 앱은 만들어져도 데이터가 안 보여요. 여러분이 커스텀할 때 제일 먼저 확인할 부분입니다.

그 다음은 **레이아웃 구조**가 나와요.

```
display:flex; height:100vh
- 왼쪽: Sidebar (width:220px, background:#FFFFFF, borderRight:1px solid #E5E8EB)
- 오른쪽: main (flex:1, overflow:auto, paddingTop:32px)
```

사이드바 너비, 배경색, 테두리까지 픽셀 단위로 다 들어있습니다. "왼쪽에 메뉴 만들어줘"가 아니라 "width 220px, 배경 흰색, 오른쪽 테두리 1px"이에요. 레이아웃을 이렇게 수치로 적으면 생성할 때마다 같은 화면이 나옵니다. 수치를 빼고 시키면 사이드바가 어떤 날은 넓게, 어떤 날은 아이콘만 남은 형태로 나와요.

그리고 각 뷰가 어떻게 전환되는지도 써있어요.

```
dashboard → <Dashboard onSelectAgent={fn} />
agent     → <AgentDetail agent={selectedAgent} />
gallery   → <Gallery />
cron      → <CronJobs />
git-sync  → <GitSync />
settings  → <Settings />
```

컴포넌트 이름까지 지정한 것에 주목하세요. Dashboard, AgentDetail, Gallery처럼 이름을 정해주면 생성되는 파일 이름도 그대로 나옵니다. 나중에 "Gallery 수정해줘"라고 요청할 때 Claude Code가 어떤 파일을 고쳐야 하는지 바로 알아요. 이름을 안 정해주면 매번 다른 이름으로 만들어져서 후속 요청이 어려워집니다.

이 프롬프트에 무려 여섯 개 뷰의 설계가 다 들어있어요. 사이드바 구조, 각 탭, 버튼 클릭 시 동작, 데이터를 어떤 CLI 명령어로 가져오는지까지. 이 파일 하나로 Claude Code가 앱 전체를 만드는 거예요.

정리하면 이 프롬프트의 패턴은 네 가지예요. 기술 스택과 완료 조건, 디자인 토큰, 데이터 정의, 레이아웃 수치. 여러분이 다른 앱을 만들 때도 이 네 칸을 채우면 됩니다. 잠깐 멈추고 생각해보세요. 여러분이 매일 반복하는 확인 업무가 있다면, 그걸 이 네 칸에 어떻게 나눠 담을 수 있을까요?

이 파일 내용을 전체 선택해서 복사합니다. Claude Code 입력창에 붙여넣어요.

**[화면: Claude Code에 프롬프트 붙여넣기]**

붙여넣고 엔터를 누르는 순간부터 Claude Code가 작동을 시작합니다. 어떤 순서로 만들어지는지 같이 보겠습니다.

Claude Code가 제일 먼저 하는 일은 **파일 구조를 파악하는 것**입니다. PROMPT.md 끝부분에 파일 구조가 명시돼 있거든요.

```
manager/
  package.json
  vite.config.ts
  tsconfig.json
  index.html
  src/
    main.tsx
    App.tsx
    index.css
    constants.ts
    types/
      index.ts
    hooks/
      useTauri.ts
    views/
      Dashboard.tsx
      AgentDetail.tsx
      Gallery.tsx
      CronJobs.tsx
      GitSync.tsx
      Settings.tsx
    components/
      Sidebar.tsx
      ...
  src-tauri/
    tauri.conf.json
    Cargo.toml
    src/
      main.rs
      lib.rs
```

Claude Code가 이 구조대로 폴더와 파일을 하나씩 만들어요. 화면에서 보면 파일 이름이 하나씩 뜨면서 생성됩니다.

파일 구조를 프롬프트 끝에 넣은 것도 이유가 있어요. 구조를 빼고 시키면 Claude Code가 파일을 어디에 둘지 스스로 정하는데, 그러면 컴포넌트 여러 개가 한 파일에 뭉치거나 폴더 구조가 매번 달라집니다. 구조를 주면 그 틀 안에서만 작업해요. 설계 도면을 주고 시공을 맡기는 것과 같은 원리입니다.

먼저 `package.json`이 생겨요. Vite, React, TypeScript, Tauri API, lucide-react 의존성이 들어가 있어요. lucide-react는 아이콘 라이브러리입니다. 뒤에서 볼 상태 아이콘, 파일 아이콘이 전부 여기서 나와요.

다음에 `constants.ts`가 생깁니다. 에이전트 세 명의 정보가 배열로 들어가는 파일이에요. 아까 프롬프트에서 본 그 배열이 여기로 그대로 옮겨집니다. 나중에 에이전트를 추가할 때 열어볼 파일이 바로 이거예요.

`types/index.ts`가 생겨요. `Agent`, `View`, `AgentStatus` 같은 TypeScript 타입 정의가 들어갑니다. 데이터 모양을 미리 정해두는 파일이라고 이해하시면 됩니다.

`hooks/useTauri.ts`가 생겨요. 이게 중요한 파일이에요. 세 가지 함수가 있어요. `runCommand`는 터미널 명령어를 실행하고 결과를 돌려줍니다. `readFile`은 파일을 읽어요. `writeFile`은 파일에 씁니다. 이 세 함수 덕분에 앱이 `openclaw status` 같은 CLI 명령어를 바로 실행할 수 있어요.

여기서 궁금하실 수 있어요. "Tauri 말고 그냥 웹 페이지로 만들면 안 되나요?" 안 됩니다. 웹 브라우저는 보안상 로컬 파일을 마음대로 읽거나 터미널 명령어를 실행할 수 없어요. `openclaw status`를 실행하려면 운영체제에 직접 접근할 수 있어야 합니다. 그래서 네이티브 앱이 필요하고, Tauri가 그 통로를 열어주는 거예요. 방금 본 `useTauri.ts`의 세 함수가 바로 그 통로입니다.

파일이 만들어지는 동안 기다리는 시간이 좀 있어요. 그동안 방금 붙여넣은 프롬프트에서 주목할 부분 하나 더 볼게요. 프롬프트에는 각 뷰가 데이터를 어떤 명령어로 가져오는지가 적혀있습니다. Dashboard는 `openclaw status`, CronJobs는 `openclaw cron list`. 이게 이 앱의 정체를 말해줘요. 새로운 시스템을 만드는 게 아니라, 우리가 터미널에서 치던 명령어를 대신 쳐주고 결과를 화면에 그려주는 앱인 거예요. 그래서 앱이 보여주는 정보와 터미널에서 보는 정보가 항상 같습니다.

그 다음에 뷰 파일들이 하나씩 만들어집니다. `Dashboard.tsx`, `Gallery.tsx`, `CronJobs.tsx` 순서로요. 화면에 파일 이름이 뜰 때마다 프롬프트의 해당 섹션이 코드로 바뀌고 있다고 보시면 됩니다.

마지막으로 `src-tauri/` 폴더 안에 Rust 관련 파일들이 생깁니다. `tauri.conf.json`에는 앱 이름, 윈도우 크기, 권한 설정이 들어가요. 권한 설정이 중요한 부분입니다. Tauri는 기본적으로 앱이 시스템에 접근하는 걸 막아둬요. 명령어 실행과 파일 읽기·쓰기를 허용하는 설정이 여기에 들어가야 useTauri의 세 함수가 실제로 작동합니다.

이 전체 과정이 대략 2~3분 안에 끝납니다. 빈 폴더가 완전한 앱 소스코드로 채워지는 거예요.

또 하나 자주 나오는 질문이 있어요. "생성되는 코드가 매번 완전히 똑같나요?" 완전히 똑같지는 않습니다. 변수 이름이나 세부 구현은 조금씩 달라질 수 있어요. 하지만 파일 구조, 컴포넌트 이름, 색상 값, 데이터 흐름은 프롬프트에 못 박혀 있어서 그대로 나옵니다. 프롬프트가 구체적일수록 편차가 줄어드는 거예요.

Claude Code가 완료 메시지를 내보내면 이제 실행할 차례예요.

```bash
npm install && npm run tauri dev
```

`npm install`이 의존성을 설치해요. 처음이라면 1~2분 걸립니다. 그 다음에 `npm run tauri dev`를 실행하면 Rust 컴파일이 시작됩니다. 처음 빌드는 2~3분 더 걸려요. Rust는 첫 빌드만 오래 걸리고, 이후 변경사항은 훨씬 빠르게 반영됩니다.

컴파일이 도는 동안 화면을 잠깐 볼게요. 터미널에 Rust 패키지들이 하나씩 컴파일되는 로그가 올라갑니다. 이게 Tauri의 특징이에요. 앱의 껍데기는 Rust로 컴파일되고, 그 안에서 React 화면이 돌아갑니다. 무거워 보일 수 있는데 반대예요. Electron은 브라우저 전체를 앱에 담아서 설치 파일이 수백 메가가 되는데, Tauri는 운영체제에 이미 있는 웹뷰를 재사용해서 완성 앱이 수 메가 수준입니다.

기다리는 동안 하나 더 짚을게요. 만약 빌드 중에 오류가 나면 어떻게 할까요? 오류 메시지를 복사해서 Claude Code에 그대로 붙여넣으면 됩니다. 자기가 만든 코드니까 오류 위치를 찾아서 고쳐줘요. 이것도 이 방식의 장점입니다. 만든 주체와 고치는 주체가 같아요.

**[화면: Agent Manager 앱 실행]**

앱 창이 열립니다. 왼쪽에 사이드바가 있고, 오른쪽에 Dashboard가 기본으로 떠있어요.

사이드바를 먼저 보겠습니다. 맨 위에 OpenClaw 로고가 있고, 그 아래 에이전트 세 명이 리스트로 나와요. Echo는 인디고, Min은 에메랄드, Evan은 오렌지 색상 원형 아바타를 쓰고 있어요. 프롬프트의 디자인 토큰과 에이전트 배열에 적어둔 색이 그대로 반영된 겁니다. 이 목록은 `constants.ts`에서 읽어와요. 정적인 정보라 새로고침이 필요 없습니다.

에이전트 목록 아래에 구분선이 있고, 네비게이션 메뉴가 있습니다. Dashboard, Gallery, CronJobs, Git Sync, Settings 다섯 개예요. 아까 프롬프트에서 본 뷰 전환 표의 항목들과 하나씩 대응됩니다.

사이드바 맨 아래에는 모니터링 위젯이 있어요. 에이전트 세 명의 토큰 사용량이 프로그레스 바로 표시됩니다. `openclaw status` 결과를 실시간으로 파싱해서 보여주는 거예요. 앞에서 본 `runCommand` 함수가 여기서 일합니다. 명령어를 실행하고, 출력에서 토큰 숫자를 뽑아서 프로그레스 바 길이로 바꿔주는 거예요.

오른쪽 Dashboard를 보겠습니다. 에이전트 카드가 세 개 있어요. 각 카드에 에이전트 이름, 워크스페이스 경로, Agent ID가 표시돼 있어요. 이 값들도 전부 `constants.ts`에서 옵니다. "View Files" 버튼과 "Send Message" 버튼도 있습니다.

카드 아래에 **OpenClaw Status** 섹션이 있어요. `openclaw status` 명령어 결과가 그대로 표시됩니다. 옆에 새로고침 버튼이 있어서 클릭하면 최신 상태로 업데이트돼요. 새로고침을 누르면 `runCommand`로 명령어를 다시 실행하는 겁니다. 화면에 보이는 건 결국 터미널 출력 그대로예요. 터미널과 앱이 다른 정보를 보여줄 일이 없습니다.

에이전트 카드에서 "View Files"를 클릭해볼게요. 오른쪽 영역이 에이전트 상세 뷰로 바뀝니다. 탭이 네 개 있어요. Files, Heartbeat, History, Send Message. 하나씩 클릭하면서 각 탭의 데이터가 어디서 오는지 같이 볼게요.

**Files 탭**에서는 에이전트 워크스페이스 안 파일 목록이 보여요. `constants.ts`에 적힌 workspace 경로를 읽어서 목록을 만듭니다. 파일을 클릭하면 `readFile` 함수가 내용을 읽어서 아래 패널에 바로 미리보기로 표시해요. 터미널에서 `cat`을 치던 작업이 클릭 한 번이 된 거예요.

**Heartbeat 탭**에서는 에이전트의 HEARTBEAT.md 파일 내용을 볼 수 있어요. 편집도 가능하고 저장 버튼도 있어요. `readFile`로 열고, 저장 버튼을 누르면 `writeFile`로 씁니다. 이 앱에서 보기만 하는 게 아니라 쓰기까지 하는 대표적인 지점이에요. 에이전트에게 새 지시를 내려야 할 때 터미널 없이 여기서 바로 수정할 수 있습니다.

**History 탭**에서는 세션 기록이 날짜순으로 나와요. `constants.ts`의 sessionsDir 경로에서 읽어옵니다. 클릭하면 그 세션에서 에이전트가 무슨 대화를 했는지 볼 수 있어요. 클립 02에서 파이프라인을 돌렸다면 그 기록이 여기 남아있습니다. 에이전트가 오류를 냈을 때 원인을 추적하는 용도로 제일 자주 열게 될 탭이에요.

**Send Message 탭**에서는 에이전트에게 직접 메시지를 보낼 수 있어요. `openclaw sessions send` 명령어를 앱 안에서 실행하는 거예요. 입력창에 쓰고 보내면 `runCommand`가 명령어를 대신 쳐줍니다. 텔레그램으로 보내던 메시지를 앱에서 보내는 셈이에요.

여기서 잠깐 멈추고 생각해보세요. 여러분이 클립 02에서 만든 파이프라인 기준으로, 어느 에이전트의 어느 탭을 제일 자주 열게 될까요? 데이터 정제가 자주 막힌다면 Min의 History 탭일 거고, 지시를 자주 바꾼다면 Echo의 Heartbeat 탭일 거예요. 자주 쓸 화면을 미리 정해두면 나중에 앱을 커스텀할 때 우선순위가 잡힙니다.

이제 Gallery 탭으로 넘어가겠습니다.

어디서 가져오는 건지 설명할게요. `~/Projects/openclaw-pipeline-kit/runs/` 폴더를 스캔해요. 각 run 폴더 안의 `outputs/` 디렉토리에 있는 파일들을 전부 읽어들입니다. 클립 02에서 파이프라인이 결과물을 저장하던 바로 그 위치예요. 앱이 별도 데이터베이스를 두는 게 아니라 파일 시스템을 그대로 읽는 구조입니다. 그래서 터미널에서 파일을 지우거나 추가해도 앱과 어긋날 일이 없어요.

파일 확장자마다 아이콘이 달라요. `.md` 파일은 파란 문서 아이콘, `.html` 파일은 초록 지구본 아이콘, `.csv` 파일은 주황 테이블 아이콘입니다. 이 색 구분 덕분에 어떤 종류의 파일인지 한눈에 보여요. 아이콘은 아까 package.json에서 본 lucide-react에서 온 거예요.

카드 안에는 파일명이 굵게 써있고, 아래에 수정 날짜가 표시됩니다. 오른쪽 하단에는 담당 에이전트 태그가 있어요. 파일명 번호를 보고 판단합니다. 01, 02로 시작하는 파일은 Aria, 03, 04는 Sam, 05는 Min, 06, 07은 Evan이에요. 클립 02에서 본 파이프라인 순서랑 일치하죠.

이 판단 규칙도 PROMPT.md에서 온 거예요. 파일명 번호와 에이전트를 짝지어주는 규칙이 프롬프트에 적혀있고, Claude Code가 그걸 코드로 옮긴 겁니다. 여러분 파이프라인의 산출물 이름 규칙이 다르다면 프롬프트의 이 부분만 바꾸면 돼요.

**[화면: 파일 내용 모달 열기]**

모달이 열리면서 파일 내용이 표시됩니다. 마크다운은 그대로 텍스트로, HTML은 미리보기로 볼 수 있어요.

이 기능이 왜 편리하냐면, 터미널에서 결과물을 보려면 `cat` 명령어를 치거나 파일을 직접 열어야 해요. Gallery에서는 클릭 한 번으로 내용을 확인할 수 있어요. 파이프라인이 여러 번 돌아서 결과물이 쌓여있을 때 특히 유용합니다.

여기서 질문 하나 짚고 갈게요. "파이프라인을 여러 번 돌리면 카드가 계속 쌓이나요?" 네. `runs/` 아래 run 폴더가 늘어나는 만큼 카드도 늘어납니다. 카드에 수정 날짜가 표시되니까 최신 결과물을 구분할 수 있어요. 지난주 대시보드와 이번 주 대시보드를 나란히 놓고 비교하는 용도로도 쓸 수 있습니다.

오른쪽 상단에 새로고침 버튼도 있어요. 클릭하면 `runs/` 폴더를 다시 스캔해서 최신 파일을 반영합니다. 파이프라인이 도는 중간에 눌러보면 결과물 카드가 하나씩 늘어나는 것도 볼 수 있어요. 에이전트들이 지금 어디까지 진행했는지 이 화면만으로 파악이 됩니다.

Gallery 뷰에서 수강생 여러분이 직접 해볼 수 있는 것이 있어요. 파이프라인을 한 번 더 돌리고 Gallery를 새로고침하면, 새로 생긴 결과물이 카드로 나타납니다. 누가 어떤 파일을 만들었는지 에이전트 태그로 바로 구분할 수 있어요.

잠깐 멈추고 생각해보세요. 여러분 업무 산출물이라면 카드에 어떤 정보가 더 필요할까요? 보고서라면 대상 기간이, 대시보드라면 데이터 기준일이 필요할 수 있어요. 그런 요구사항이 생기면 PROMPT.md에 한 줄 추가하고 다시 생성하면 됩니다.

이제 CronJobs 탭으로 이동하겠습니다.

## s20 — CronJobs 뷰

CronJobs 탭 클릭 → `openclaw cron list` 파싱 결과 표시.
ok(초록) / error(빨강) / paused(회색) 상태 보여주기.

---

**[화면: 앱]**

사이드바에서 CronJobs를 클릭합니다.

**[화면: CronJobs 탭 화면]**

크론 잡 카드들이 나타납니다. 클립 02에서 등록했던 잡들이 보여요.

어떻게 가져오는지 설명할게요. 앱이 마운트되는 시점에 `openclaw cron list` 명령어를 자동으로 실행합니다. 그 결과를 파싱해서 카드로 표시하는 거예요. 마운트 시점이라는 건 이 탭 화면이 처음 열리는 순간이라는 뜻입니다. 탭을 클릭하는 순간 `runCommand`가 명령어를 치고, 출력이 돌아오면 카드로 바뀌는 거예요.

파싱 방법이 조금 특이해요. `openclaw cron list`의 출력 형식은 헤더 줄이 먼저 나오고, 그 아래에 데이터 줄이 나와요. 앱은 헤더 줄에서 각 컬럼의 위치를 먼저 파악합니다. Name, Schedule, Next, Last, Status, Agent ID 컬럼이 몇 번째 글자에서 시작하는지를요. 그런 다음 데이터 줄을 그 위치대로 잘라서 값을 추출합니다.

왜 이렇게 파싱하는지 궁금하실 수 있어요. 그냥 공백으로 자르면 안 되나? 안 됩니다. 크론 잡 이름에 공백이 들어가면 컬럼이 밀려서 값이 엉켜요. 헤더 위치 기준으로 자르면 이름에 공백이 있어도 정확하게 분리됩니다. 이런 파싱 방식까지 PROMPT.md에 적어둔 덕분에 Claude Code가 안정적인 코드를 만든 거예요.

카드 구조를 보겠습니다. 왼쪽에 상태 아이콘이 있어요. ok는 초록 체크 아이콘, error는 빨간 경고 아이콘, paused는 회색 일시정지 아이콘입니다.

가운데에 크론 잡 이름이 굵게 표시되고, 그 아래에 스케줄이 모노스페이스 폰트로 보여요. 클립 02에서 등록할 때 쓴 크론 표현식 그대로입니다.

오른쪽에 다음 실행 시간과 마지막 실행 시간이 표시됩니다. 아래에는 담당 에이전트 컬러 배지가 붙어있어요. 어느 에이전트가 이 잡을 맡고 있는지 색으로 바로 구분됩니다.

상태 색상만으로도 전체 상황을 빠르게 파악할 수 있어요. 카드가 전부 초록이면 정상이에요. 빨간 카드가 보이면 그 잡에 문제가 생긴 겁니다. 회색은 잠시 멈춰둔 상태예요.

"빨간 카드가 보이면 어떻게 하나요?" 잡 이름과 담당 에이전트 배지를 확인하고, 그 에이전트의 History 탭에서 마지막 세션을 열어보면 됩니다. 어디까지 진행되다 멈췄는지 대화 기록에 남아있어요. 아까 본 탭들이 이렇게 연결돼서 쓰입니다.

새로고침 버튼을 클릭하면 `openclaw cron list`를 다시 실행해서 최신 상태로 갱신됩니다. "앱을 켜둔 채로 두면 자동으로 갱신되나요?"라고 물으실 수 있는데, 마운트 시점에 한 번 실행하고 그 뒤로는 새로고침 버튼을 누를 때 갱신돼요. 월요일 아침에 크론이 돌았는지 확인하려면 앱을 열고 이 탭에서 새로고침 한 번, 그게 전부입니다.

이렇게 Agent Manager 하나로 에이전트 상태, 결과물, 크론 잡을 전부 한 화면에서 관리할 수 있어요.

잠깐 지금까지 만든 게 무엇인지 정리해볼게요. 빈 폴더에 PROMPT.md 파일 하나가 있었어요. Claude Code에 그 내용을 붙여넣었더니 React + Tauri 앱이 자동으로 만들어졌습니다. 앱 개발을 한 줄도 직접 짜지 않았는데 대시보드, 갤러리, 크론 뷰가 다 있는 앱이 나왔어요.

이게 가능한 이유가 있습니다. PROMPT.md에 설계가 매우 구체적으로 들어있었거든요. 색상 값, 컴포넌트 이름, 어떤 CLI 명령어로 데이터를 가져오는지, 파일 구조까지. Claude Code는 이 설계서를 코드로 변환하는 역할을 했을 뿐이에요.

이 방식에는 중요한 장점이 있습니다. 나중에 앱을 수정하고 싶을 때 PROMPT.md를 바꾸면 됩니다. "에이전트를 두 명 더 추가해줘"라고 하거나, "Gallery에서 HTML 파일은 실제 렌더링으로 미리보기 해줘"라고 Claude Code에 요청하면 수정해줘요. 코드 구조를 몰라도 자연어로 요청하면 됩니다.

자기 프로젝트에 맞게 바꾸는 방법도 간단해요. PROMPT.md에서 에이전트 목록 부분만 수정하면 됩니다. `AGENTS` 배열에 자기 에이전트 이름과 색상, 워크스페이스 경로를 넣어주면 돼요. 다섯 명이 아니라 세 명이어도 되고, 에이전트 이름을 다르게 써도 됩니다. 파일 하나만 수정하고 Claude Code에 다시 붙여넣으면 새 에이전트에 맞는 앱이 생성됩니다.

여기서 잠깐 멈추고 생각해보세요. 여러분이 지금 운영 중인 에이전트, 혹은 앞으로 만들 에이전트를 떠올려보세요. 이름은 뭐고, 워크스페이스 경로는 어디인가요? 그 두 가지만 정해지면 `AGENTS` 배열 한 줄이 완성됩니다. 강의가 끝나고 PROMPT.md를 열어서 그 한 줄을 직접 바꿔보는 것, 그게 이 클립의 실습 과제예요.

마무리로 넘어가겠습니다.

이것으로 OpenClaw 업무 자동화 챕터가 끝났습니다. 세 클립에서 뭘 했는지 하나씩 되짚어볼게요.

클립 01에서는 OpenClaw를 이해하고 텔레그램 봇을 연결했어요. OpenClaw를 설치하고, 에이전트마다 워크스페이스와 세션이 분리되는 구조를 살펴봤습니다. 터미널이 아니라 메신저로 에이전트에게 일을 시킬 수 있는 기반을 만든 클립이었어요.

클립 02에서는 파이프라인을 실제로 실행하고, 크론 잡으로 주간 자동화를 연결했어요. Echo가 Aria, Sam, Min, Evan을 순서대로 지휘해서, CSV 파일 하나를 넣으면 대시보드와 임원 보고서까지 자동으로 나오는 흐름을 만들었습니다. 결과물 일곱 개가 `runs/latest/outputs/`에 쌓이는 것을 확인했고, 매주 월요일 자동 실행까지 걸어뒀어요.

이번 클립 03에서는 Agent Manager를 Claude Code로 직접 만들었어요. 에이전트 상태, 결과물, 크론 잡을 한 화면에서 모니터링할 수 있는 네이티브 앱입니다. 코드를 한 줄도 직접 짜지 않고 PROMPT.md라는 설계서 하나로 만들었다는 점, 그리고 그 설계서에 뭘 적어야 결과가 안정적으로 나오는지를 본 게 이 클립의 중요한 부분이에요.

마무리로 이번 챕터를 끝내고 여러분이 바로 해볼 수 있는 것 세 가지를 드릴게요.

첫 번째는 **자기 데이터로 파이프라인 한 번 돌려보기**입니다. `runs/latest/input/`에 업무 CSV 파일을 넣고 Echo에게 파이프라인 실행을 요청해보세요. 어떤 대시보드가 나오는지 확인해보는 거예요. 강의 예제가 아니라 자기 팀의 실제 데이터로 돌려보면, 어디를 손봐야 할지가 훨씬 구체적으로 보입니다.

두 번째는 **크론 잡 하나 등록하기**예요. 매주 월요일 아침에 자동으로 파이프라인이 돌아가게 설정해두면, 월요일마다 최신 대시보드가 자동으로 생성됩니다. 등록 방법은 클립 02에서 한 그대로예요. 등록해두고 Agent Manager의 CronJobs 탭에서 초록 체크가 뜨는지 확인해보세요.

세 번째는 **Agent Manager를 자기 에이전트에 맞게 수정하기**입니다. PROMPT.md에서 `AGENTS` 배열을 바꾸고 Claude Code에 다시 붙여넣으면, 자기 팀 에이전트 구성에 맞는 Manager가 만들어져요. 바꿀 것은 에이전트 이름, 색상, 워크스페이스 경로 세 가지뿐입니다.

챕터 전체를 통해 말하고 싶었던 것은 하나예요. 에이전트 자동화는 코딩 실력의 문제가 아닙니다. 어떻게 역할을 나누고, 어떻게 설계서를 쓰는지의 문제예요. PROMPT.md 파일처럼 설계를 명확하게 적으면 Claude Code가 나머지를 해줍니다. 이 챕터에서 다룬 파이프라인, 크론, Agent Manager 전부 설계서에서 출발했어요. 다음에 자동화하고 싶은 업무가 생기면 코드가 아니라 설계서부터 쓰세요.
