## s7 — CLIP 02 섹션 브레이크 (3분)

> **🎬 촬영** — 슬라이드만 (간지)

**[화면: s7 섹션 브레이크 슬라이드]**

두 번째 클립을 시작할게요. 이번 클립 주제는 파이프라인 자동화예요. 5-agent 파이프라인으로 대시보드를 자동 생성하고, 크론으로 주간 리포트까지 자동으로 운영하는 데까지 갑니다.

잠깐, 클립 시작 전에 전체 그림부터 짚고 가겠습니다.

지난 클립에서 OpenClaw 설치랑 기본 연동까지 마쳤습니다. Echo 봇이 텔레그램으로 제 메시지를 받는 것도 확인했고, Claude Code가 작업 에이전트로 붙어있다는 것도 봤어요.

지난 클립까지의 상태를 정확히 말하면 이래요. 제가 메시지를 보내면 에이전트가 반응한다. 여기까지예요. 그러니까 아직은 제가 매번 시켜야 움직입니다. 사람이 트리거인 상태예요.

이번 클립에서는 그 위에 뭘 올리냐면 — **자동화**예요.

제가 직접 텔레그램에 메시지를 보내지 않아도, 정해진 시간에 알아서 에이전트가 깨어나서 파이프라인을 실행하고, 결과물까지 만들어주는 흐름을 만들 거예요. 사람이 트리거였던 걸 시간이 트리거가 되도록 바꾸는 거예요. 이게 되면 여러분이 잊고 있어도 보고서가 나옵니다.

구체적으로 세 가지를 봅니다.

첫 번째, 에이전트 5명이 어떤 구조로 협업하는지. Aria, Sam, Min, Evan, 그리고 메인인 Echo가 어떤 순서로 일을 나누는지를 설명해요. 각 에이전트가 어떤 파일을 만들고, 그 파일이 다음 에이전트한테 어떻게 넘어가는지까지 봅니다. 이 구조를 이해해야 뒤에서 결과물을 봤을 때 "이건 누가 왜 만들었는지"가 보여요.

두 번째, 크론 설정이에요. "매주 월요일 오전 9시에 자동으로 파이프라인 실행"을 명령 한 줄로 설정하는 방법이에요. 크론 표현식 읽는 법부터 시작해서, 여러분 업무에 맞는 스케줄을 직접 설계하는 것까지 다룹니다.

세 번째, 실전 실행이에요. CSV 파일 하나 넣고 텔레그램으로 메시지 한 줄 보내면 대시보드 HTML이랑 임원 보고서까지 자동으로 만들어지는 걸 라이브로 보여드립니다. 그리고 결과물 파일 7개를 하나씩 뜯어볼 거예요. 파일마다 어떤 구조로 쓰여 있는지, 어디를 봐야 하는지를 같이 읽습니다.

순서에도 이유가 있어요. 구조를 먼저 알아야 스케줄을 설계할 수 있고, 스케줄을 알아야 실전 실행이 이해됩니다. 그래서 구조 → 크론 → 실행 순서예요.

클립이 좀 길어요. 30분짜리 데모 섹션이 하나 있는데, output 파일을 직접 열어서 같이 보는 시간이에요. 중간에 파이프라인이 도는 대기 시간도 있으니까, 천천히 따라오시면 됩니다.

자, 시작해요.

## 실행 방식 두 가지 — 단톡방 세팅부터 (10분)

> **🎬 촬영** `[화면: 텔레그램 앱 + 터미널]`
> 미리 만들어둔 단톡방 그대로 사용. 새로 안 만들어도 됨. 화면으로는 이미 봇 5개 들어있는 단톡방을 보여주면서 "이렇게 만들어두면 된다"고 설명.

**[화면: 텔레그램 앱 — 봇 5개가 들어있는 단톡방]**

본격적으로 파이프라인을 돌리기 전에, 에이전트한테 일을 시키는 방법이 두 가지가 있다는 걸 먼저 짚고 갈게요. 상황에 따라 골라 쓰면 돼요.

첫 번째는 **Echo 한 명한테 DM으로 시키는 방법**이에요. 두 번째는 **단톡방에 다섯 명을 모아놓고 협업시키는 방법**이고요. 둘 다 결과물은 똑같이 나와요. 차이는 "과정이 눈에 보이느냐"예요.

하나씩 볼게요.

### 방법 1 — Echo 한 명한테 DM으로 (간단·저비용)

**[화면: 텔레그램 Echo 봇 DM 화면]**

제일 간단한 방법이에요. 텔레그램에서 Echo 봇하고 일대일 대화창을 열어요. 거기에 "이 CSV로 파이프라인 돌려줘"라고 보내면 끝이에요.

이러면 Echo가 혼자서 7단계를 순서대로 다 처리해요. 데이터 프로파일링부터 대시보드까지 Echo 한 명이 쭉 만들어요. 여러분 눈에는 Echo가 "1단계 완료", "2단계 완료" 하고 진행 상황만 보고하는 게 보여요.

이 방법의 장점은 두 가지예요. 하나는 단톡방을 안 만들어도 된다는 거예요. 봇 하나만 있으면 돼요. 다른 하나는 비용이 적게 든다는 거예요. 에이전트 한 명이 처리하니까 모델 호출이 상대적으로 적어요.

실무에서는 이 방법을 훨씬 많이 써요. 혼자 쓰는 자동화라면 굳이 다섯 명을 부를 필요가 없거든요. 매일 아침 리포트 받는 용도라면 Echo 한 명으로 충분해요.

여기서 질문 하나 하실 수 있어요. "그러면 다섯 명은 왜 만든 거예요?" 좋은 질문이에요. 다섯 명 협업은 다음 방법에서 설명할게요. 각자 장단점이 있어요.

---

### 방법 2 — 단톡방에서 다섯 명 협업 (과정이 다 보임)

**[화면: 텔레그램 단톡방 — Echo·Aria·Sam·Min·Evan]**

두 번째는 단톡방에 다섯 명을 다 모아놓고 돌리는 방법이에요. 이 강의에서 주로 보여드릴 방식이에요.

먼저 단톡방을 어떻게 만드는지부터 볼게요. 텔레그램에서 새 그룹을 만들고, 봇 다섯 개를 전부 초대해요. Echo, Aria, Sam, Min, Evan 다섯 개 봇이요. 그룹 이름은 아무거나 괜찮아요. 저는 "AI Pipeline"이라고 지었어요.

**[화면: 단톡방 만들기 → 봇 5개 초대]**

봇을 초대하는 방법은 사람 초대하는 거랑 똑같아요. 그룹 만들 때 멤버 추가 화면에서 봇 유저네임을 검색해서 하나씩 넣으면 돼요.

단톡방을 만들었으면 그룹 ID를 알아내야 해요. 이게 왜 필요하냐면, Echo한테 "어느 단톡방에서 협업할지"를 알려줘야 하거든요.

**[화면: web.telegram.org 주소창]**

그룹 ID 찾는 방법이에요. 브라우저에서 web.telegram.org에 접속해서 그 단톡방을 클릭해요. 그러면 주소창 끝에 숫자가 보여요. 그 숫자 앞에 마이너스를 붙인 게 그룹 ID예요. 주소에 이미 마이너스가 붙어 있으면 그대로 쓰면 돼요.

이 그룹 ID는 메모장에 적어두세요. 파이프라인 시작할 때 Echo한테 알려줘야 해요.

자, 이제 이 단톡방에서 돌리면 뭐가 다른지 볼게요. Echo한테 DM이 아니라 이렇게 보내요.

```
그룹 ID는 -XXXXXXXXXX야.
단톡방에서 Aria 불러서 파이프라인 시작해줘.
CSV는 ~/Projects/openclaw-pipeline-kit/runs/latest/input/ 에 있어.
```

`-XXXXXXXXXX` 자리에 방금 메모한 그룹 ID를 넣으면 돼요.

이러면 Echo가 단톡방에 들어가서 "Aria, 데이터 프로파일링 해줘"라고 멘션을 날려요. Aria가 작업하고 결과를 단톡방에 올려요. 그다음 Sam, Min, Evan 순서로 넘어가요. 여러분은 단톡방에서 다섯 명이 실제로 대화하듯이 일을 주고받는 걸 눈으로 봐요.

이 방법의 장점은 **과정이 다 보인다**는 거예요. 누가 어느 단계에서 뭘 만들고 있는지, 어디서 막혔는지가 채팅으로 다 남아요. 교육용으로, 그리고 처음 파이프라인을 이해할 때 이 방식이 좋아요.

단점은 비용이에요. 다섯 명이 각자 모델을 호출하니까 Echo 혼자 할 때보다 토큰을 더 써요. 그래서 실무에서 매일 돌리는 자동화라면 방법 1을, 과정을 보여주거나 각 단계를 세밀하게 제어하고 싶으면 방법 2를 쓰는 게 좋아요.

여기서 한 가지 짚을게요. 단톡방에서 봇들이 서로 대화하는 것처럼 보이지만, 실제로 봇끼리 텔레그램 메시지를 주고받는 건 아니에요. 텔레그램 봇은 다른 봇의 메시지를 못 읽거든요. 진짜 작업 전달은 OpenClaw 내부에서 세션 호출로 이뤄지고, 각 에이전트는 자기 봇 계정으로 결과를 단톡방에 "보고"만 하는 거예요. 단톡방은 사람이 지켜보는 무대라고 생각하시면 돼요.

정리하면 이래요. 혼자 빠르게 돌릴 땐 방법 1, 과정을 보여주고 싶을 땐 방법 2. 이 클립에서는 구조를 이해하는 게 목적이니까 방법 2, 단톡방 협업을 중심으로 보겠습니다.

## s8 — 에이전트 5종 구조 (12분)

> **🎬 촬영** — 슬라이드만

**[화면: s8 슬라이드]**

이번 실습에서 쓸 에이전트는 다섯 명이에요.

다섯 명이라고 하면 좀 많아 보일 수 있는데, 실제로 여러분이 관리해야 할 건 하나예요. 나머지는 알아서 돌아갑니다. 왜 다섯 명인지부터 이야기할게요.

---

분석 파이프라인을 한 에이전트가 혼자 처리하면 어떻게 될까요?

작업이 길어질수록 컨텍스트가 쌓입니다. 처음엔 빠르게 가다가, 데이터 프로파일링 결과가 쌓이고, EDA 결과가 또 쌓이고, 거기에 KPI 계산까지 더해지면 에이전트의 작업 창이 무거워져요. 그러다 결국 앞에서 분석한 내용을 참조를 못 하거나, 응답이 느려지거나, 최악의 경우 중간에 끊겨요.

사람으로 비유하면 이래요. 한 명한테 데이터 검수부터 보고서 디자인까지 일곱 가지 일을 연달아 시키는 거예요. 앞의 여섯 가지 작업 기억을 전부 머리에 담은 채로 일곱 번째 일을 해야 합니다. 뒤로 갈수록 실수가 늘어요.

그래서 **역할을 쪼갭니다**. 각 에이전트가 딱 자기 담당 스텝만 보고 결과를 파일로 넘겨요. 다음 에이전트는 그 파일을 받아서 이어서 작업하고요. 컨텍스트가 분리되니까 각 에이전트가 훨씬 깔끔하게 일합니다.

여기서 이런 질문 하실 수 있어요. 파일로 넘기지 말고, 에이전트끼리 대화로 넘기면 안 되나요? 됩니다. 그런데 파일로 넘기는 게 두 가지 면에서 유리해요. 하나, 기록이 남아요. 어느 단계에서 뭐가 나왔는지 파일로 확인할 수 있습니다. 둘, 재시작이 돼요. 중간에 STEP 4에서 실패하면, STEP 1부터 3까지의 결과 파일은 그대로 남아있으니까 4부터 다시 하면 됩니다. 대화로 넘기면 처음부터 다시 해야 해요.

또 하나 물어보실 수 있어요. 에이전트가 다섯이면 비용이나 시간이 다섯 배 아닌가요? 아니에요. 전체 작업량은 같아요. 한 명이 일곱 스텝을 하나, 다섯이 나눠서 하나, 처리하는 일의 총량은 동일합니다. 오히려 각자 짧고 가벼운 컨텍스트로 일하니까 실패가 줄어요. 재작업이 줄어드는 만큼 실질 비용은 내려갑니다.

이게 멀티 에이전트 파이프라인의 이유예요.

역할을 나누는 기준도 짚고 갈게요. 아무렇게나 다섯으로 나눈 게 아니에요. **산출물 단위**로 나눴습니다. 데이터를 파악하는 일, 비즈니스 언어로 번역하는 일, 숫자를 계산하는 일, 결과물을 포장하는 일. 성격이 다른 일마다 담당을 붙인 거예요. 회사에서 데이터 엔지니어, 기획자, 분석가, 디자이너가 나뉘어 있는 것과 같은 기준입니다.

---

자, 다섯 명을 소개할게요.

**Echo**가 메인이에요. 총괄 지휘관이라고 보시면 됩니다. 여러분이 텔레그램으로 메시지를 보내면 Echo가 받아요. 크론 잡이 설정된 시간에 보내는 메시지도 Echo한테 갑니다.

Echo가 하는 일이 뭐냐면, 메시지를 받아서 파이프라인을 오케스트레이션해요. "Aria, 이 CSV 데이터 프로파일링해줘." "Sam, Aria 결과 받아서 KPI 뽑아줘." 이런 식으로 각 서브 에이전트한테 순서대로 지시를 내립니다. 그리고 전부 완료되면 결과물 파일 목록을 텔레그램으로 여러분한테 돌려보내요.

중요한 게 하나 있어요. Echo는 분석을 직접 하지 않습니다. 데이터를 열어보지도 않아요. Echo의 AGENTS.md에는 분석 방법이 아니라 **진행 규칙**이 적혀 있어요. 파이프라인이 STEP 1부터 7까지 어떤 순서로 진행되는지, 각 스텝을 누구한테 위임하는지, 앞 스텝의 결과 파일이 만들어진 걸 확인하고 다음 스텝으로 넘어가라는 규칙, 그리고 전부 끝나면 파일 목록을 텔레그램으로 보고하라는 완료 규칙. 이게 전부입니다.

왜 이렇게 설계했을까요? Echo가 분석까지 하면 아까 말한 컨텍스트 문제가 그대로 돌아와요. 지휘하는 에이전트는 지휘만 해야 전체 진행 상황을 놓치지 않습니다. 사람 조직에서도 프로젝트 매니저가 실무를 다 떠안으면 일정 관리가 무너지는 것과 같아요.

여러분은 Echo한테 시작 신호만 주면 됩니다. 나머지는 Echo가 다 알아서 해요.

---

**Aria**는 STEP 1-2 담당이에요.

STEP 1이 **데이터 프로파일링**이에요. CSV 파일을 받으면 컬럼 구조를 파악하고, 결측치가 얼마나 있는지, 각 컬럼의 데이터 타입이 뭔지, 특이한 값은 없는지 체크해요. 결과를 `01_dataset_profile.md` 파일로 저장합니다.

STEP 2가 **EDA 보고서**예요. 프로파일링 결과를 바탕으로 변수 간 분포를 보고, 주요 패턴이랑 이상치를 정리해서 `02_eda_report.md`를 만들어요.

Aria의 AGENTS.md에는 뭐가 적혀 있냐면, 점검 목록이에요. 컬럼별 데이터 타입을 확인할 것, 결측치 개수와 비율을 표로 정리할 것, 고유값을 나열할 것, 이상해 보이는 값은 근거와 함께 기록할 것, 결과는 `01_dataset_profile.md`와 `02_eda_report.md`라는 이름으로 저장할 것. 이런 식으로 해야 할 일과 출력 형식이 지시돼 있습니다.

STEP 1과 2를 왜 한 에이전트가 맡을까요? 둘 다 원본 데이터를 직접 들여다보는 작업이기 때문이에요. 프로파일링하면서 파악한 데이터 감각이 EDA에 그대로 이어집니다. 이걸 다른 에이전트한테 쪼개면 데이터를 두 번 읽어야 해요. 같은 데이터를 보는 작업은 한 명한테 묶는 게 효율적입니다.

Aria는 데이터를 처음 만나는 에이전트예요. 다른 에이전트들이 Aria의 결과물을 기반으로 작업하기 때문에, 프로파일링이 꼼꼼할수록 이후 단계의 품질이 올라갑니다. 반대로 Aria가 결측치나 이상치를 놓치면, Min의 계산이 틀어지고 Evan의 대시보드에 잘못된 숫자가 올라가요. 첫 단추라서 점검 목록이 제일 촘촘합니다.

---

**Sam**은 STEP 3-4 담당이에요.

STEP 3이 **문제 정의**입니다. Aria가 EDA 보고서를 만들고 나면, Sam은 그 결과를 읽어서 "이 데이터가 어떤 비즈니스 문제에 쓸 수 있겠다"를 정리해요. `03_problem_definition.md`에 저장됩니다.

STEP 4가 **KPI 요약**이에요. 문제 정의를 바탕으로 어떤 지표를 봐야 할지, 어떻게 계산해야 할지를 정리해서 `04_kpi_summary.md`를 만들어요.

Sam이 중요한 이유가 있어요. Aria가 데이터의 현황을 보고했다면, Sam은 그걸 비즈니스 언어로 번역하는 역할이에요. 뒤에 Min이랑 Evan이 Sam의 KPI 정의를 기반으로 분석이랑 대시보드를 만들거든요. Sam이 KPI를 잘 정의할수록 최종 결과물 품질이 달라집니다.

Sam의 AGENTS.md에는 이런 지시가 들어 있어요. Aria의 EDA 보고서를 먼저 읽을 것, 원본 데이터를 다시 분석하지 말 것, 문제 정의에는 비즈니스 컨텍스트·분석 목표·범위·가설을 포함할 것, KPI는 지표명·계산식·단위·목적을 표로 정리할 것. 특히 "원본을 다시 분석하지 말 것"이 중요해요. Sam이 Aria의 일을 반복하면 역할 분리가 무의미해지거든요. 앞 사람의 결과물을 신뢰하고 자기 일만 하라는 규칙입니다.

문제 정의와 KPI를 왜 한 에이전트가 맡을까요? KPI는 문제 정의에서 나오기 때문이에요. "예산 배분이 문제다"라고 정의한 사람이 "그러면 ROAS를 봐야 한다"는 결론까지 내는 게 자연스러워요. 이 둘을 쪼개면 문제 따로 지표 따로, 서로 안 맞는 문서가 나올 수 있습니다.

실무에 대입해보면 Sam은 데이터 기획자 포지션이에요. 마케터분들이 "데이터는 있는데 뭘 봐야 할지 모르겠다"고 할 때 필요한 게 이 번역 단계입니다. 그 일을 Sam이 자동으로 해주는 거예요.

---

**Min**은 STEP 5 담당이에요.

KPI 기반 **심층 분석이랑 인사이트 도출**입니다. Sam이 정리한 KPI를 실제 데이터에 적용해서 계산하고, 트렌드를 분석하고, 눈에 띄는 패턴이나 이상 신호를 찾아요. 결과는 `05_analysis_report.md`로 저장됩니다.

Min의 AGENTS.md에는 이런 규칙이 있어요. Sam이 정의한 KPI만 계산할 것, 계산식은 `04_kpi_summary.md`에 적힌 그대로 쓸 것, Sam이 세운 가설을 데이터로 검증하고 결과를 명시할 것, 해석에는 반드시 근거 수치를 붙일 것. "정의된 KPI만 계산할 것"이라는 제약이 있는 이유가 있어요. Min이 마음대로 지표를 추가하면 매주 보고서의 지표 구성이 달라져요. 지난주랑 이번 주를 비교할 수 없게 됩니다. 일관성을 지키려고 걸어둔 제약이에요.

STEP 5가 왜 단독 스텝일까요? 계산량이 제일 많은 단계라서 그래요. 채널별, 월별로 지표를 전부 집계하고 해석까지 붙이는 작업이라 컨텍스트를 통째로 줘야 합니다. 여기에 다른 일까지 얹으면 앞에서 말한 무거워지는 문제가 다시 생겨요.

Min이 만드는 분석 보고서가 임원 보고서랑 대시보드의 원재료가 됩니다. 수치 계산이랑 해석은 Min이 다 해요. Evan은 Min의 숫자를 옮겨 담기만 하고, 새로 계산하지 않습니다. 숫자의 출처를 한 곳으로 고정하는 거예요. 대시보드랑 보고서의 숫자가 서로 다른 사고를 막는 장치입니다.

---

**Evan**이 마지막 STEP 6-7이에요.

STEP 6이 **대시보드 제작**입니다. Min의 분석 결과를 받아서 HTML 대시보드를 만들어요. 차트 라이브러리 쓰고, 반응형 레이아웃 짜고, 브라우저에서 바로 열리는 `06_dashboard.html`을 생성합니다.

STEP 7이 **임원 보고서**예요. 전체 파이프라인 결과를 경영진이 읽기 좋게 정리한 `07_executive_report.md`를 만들어요. 수치만 나열하는 게 아니라, 배경 → 주요 발견 → 권고안 형식으로 정리됩니다.

Evan의 AGENTS.md는 다른 에이전트랑 성격이 달라요. 분석 지시가 아니라 **형식 지시**가 들어 있습니다. 대시보드에는 어떤 디자인 가이드를 따를 것, KPI 카드를 상단에 배치할 것, 차트에는 어떤 라이브러리를 쓸 것. 임원 보고서는 배경·주요 발견·기회와 위험·권고·다음 리뷰라는 다섯 부분 형식을 지킬 것. 내용은 Min의 보고서에서 가져오고, Evan은 표현 방식만 책임집니다.

대시보드랑 임원 보고서를 왜 한 에이전트가 맡을까요? 둘 다 같은 재료로 만드는 포장이기 때문이에요. 입력이 똑같이 `05_analysis_report.md`예요. 재료는 하나인데 보는 사람이 달라서 형태가 두 개인 거죠. 화면으로 볼 사람에겐 대시보드, 문서로 읽을 사람에겐 보고서.

Evan은 결과물의 마지막 포장을 담당하는 에이전트예요. 분석이 아무리 좋아도 전달이 나쁘면 안 읽힙니다. 그래서 포장에 전담을 붙였어요.

---

이 흐름을 정리하면 이렇습니다.

```
CSV 입력
  └→ Aria (STEP 1-2: 프로파일링 + EDA)
        └→ Sam (STEP 3-4: 문제 정의 + KPI)
              └→ Min (STEP 5: 심층 분석)
                    └→ Evan (STEP 6-7: 대시보드 + 임원 보고서)
                          └→ Echo가 텔레그램으로 결과 전송
```

순차적이에요. 앞 단계 결과물이 다음 단계의 입력이 됩니다. 파일로 넘어가기 때문에 중간에 하나가 실패해도 재시작할 수 있어요.

이 그림을 읽는 방법을 짚어드릴게요. 화살표 하나가 파일 하나예요. Aria에서 Sam으로 가는 화살표는 `02_eda_report.md`가 넘어간다는 뜻이고, Sam에서 Min으로 가는 화살표는 `03`이랑 `04` 파일이 넘어간다는 뜻입니다. 에이전트끼리 직접 대화하는 게 아니라, 파일을 놓고 가면 다음 사람이 주워서 일하는 방식이에요.

왜 병렬이 아니라 순차일까요? 병렬로 돌리면 빠를 것 같잖아요. 그런데 이 파이프라인은 병렬이 불가능해요. Sam은 Aria의 EDA 없이는 문제를 정의할 수 없고, Min은 Sam의 KPI 없이는 계산할 게 없어요. 각 단계가 앞 단계의 출력을 입력으로 쓰기 때문에, 순서가 곧 구조입니다. 순서를 억지로 바꾸면 빈 파일을 놓고 일하는 에이전트가 생겨요.

---

**AGENTS.md** 파일 이야기를 잠깐 할게요.

각 에이전트가 어떤 역할을 맡고, 어떤 파일을 만들어야 하는지는 AGENTS.md에 정의돼 있습니다.

Echo가 파이프라인을 시작할 때 이 파일을 먼저 읽어요. "Aria는 STEP 1-2 담당이고, 결과는 `01_dataset_profile.md`에 저장해야 한다." 이런 내용이 명시돼 있어요. Echo가 이걸 읽고 각 에이전트한테 지시를 내립니다.

이 AGENTS.md를 여러분이 직접 수정할 수 있어요. 예를 들어 KPI를 특정 지표로 고정하고 싶다면, Sam의 AGENTS.md에 "반드시 매출·전환율·ROAS를 포함할 것"이라고 추가하면 됩니다. 대시보드 색상이나 레이아웃을 바꾸고 싶다면 Evan의 AGENTS.md에 추가하면 되고요.

여기서 자주 하는 실수가 하나 있어요. AGENTS.md를 수정하면서 결과 파일 이름 규칙까지 바꾸는 거예요. 예를 들어 Aria의 지시문에서 `01_dataset_profile.md`를 다른 이름으로 바꿔버리면, Sam은 여전히 원래 이름의 파일을 찾도록 지시받은 상태라서 파일을 못 찾아요. 파이프라인이 중간에서 끊깁니다. 역할이나 기준을 추가하는 건 자유롭게 하시되, 파일 이름과 순서 규칙은 건드리지 마세요. 이건 에이전트들 사이의 약속이에요.

코드를 건드리지 않고 자연어로 에이전트 행동을 커스텀하는 방식이에요. 이 부분은 s37에서 다시 볼게요.

---

수동 작업이랑 비교해볼게요.

이 분석 파이프라인을 사람이 직접 하면 얼마나 걸릴까요? 데이터를 받아서 pandas로 EDA 돌리고, 결과 해석하고, 문제 정의 문서 쓰고, KPI 계산식 정리하고, 차트 그리고, 대시보드 HTML 짜고, 임원 보고서 쓰는 거예요. 빠른 사람도 반나절이에요. 데이터가 크거나 복잡하면 하루 이상 잡아야 합니다.

시간만 문제가 아니에요. 매주 반복하면 품질이 흔들려요. 이번 주엔 이상치 체크를 했는데 다음 주엔 바빠서 건너뛰고, 보고서 형식도 매번 조금씩 달라지고요. 사람이 반복 작업을 하면 생기는 자연스러운 편차입니다. 파이프라인은 AGENTS.md에 적힌 점검 목록을 매번 똑같이 수행해요. 결과물 형식도 매번 같습니다. 반복 업무에서는 이 일관성이 속도만큼 중요해요.

구체적인 상황으로 그려볼게요. 마케팅팀에서 매주 월요일에 주간 광고 리포트를 만드는 담당자가 있다고 해봅시다. 월요일 오전이 통째로 이 작업에 들어가요. 파이프라인을 쓰면 그 오전이 비어요. 담당자가 하는 일은 결과물을 검토하고, 이상한 부분이 있는지 확인하고, 권고안에 자기 판단을 얹는 것으로 바뀝니다. 만드는 사람에서 검토하는 사람으로 역할이 올라가는 거예요.

이 파이프라인을 돌리면 20-40분이면 끝납니다. 여러분이 하는 일은 CSV 하나 넣고 텔레그램으로 메시지 한 줄 보내는 게 전부예요.

## s21 — 크론 메시지가 대시보드를 만드는 방법 (5분)

> **🎬 촬영** — 슬라이드만

**[화면: s21 슬라이드]**

자, 에이전트 구조를 봤으니까 이제 **언제, 어떻게 실행되는지** 흐름을 봅시다.

크론이라는 단어가 익숙하지 않으신 분도 있을 거예요. 그냥 **정해진 시간에 자동으로 뭔가를 실행하는 스케줄러**라고 생각하시면 됩니다. 알람 시계에 메모를 붙여둔 거라고 보시면 돼요. 정해진 시간에 알람이 울리고, 붙어있던 메모가 에이전트한테 전달됩니다. 알람이 시간 담당, 메모가 내용 담당이에요.

이 크론은 Linux·Mac에 기본으로 내장돼 있는 기능이에요. 수십 년 동안 서버 관리자들이 백업이나 정기 작업을 돌릴 때 써온 검증된 도구입니다. OpenClaw는 이 크론을 에이전트 메시지랑 연결해줘요. 새로운 스케줄러를 발명한 게 아니라, 이미 있는 스케줄러에 메시지 전달 기능을 붙인 거예요.

흐름을 그려볼게요.

```
크론 트리거 (정해진 시간)
    ↓
Echo 에이전트에게 message 전송
    ↓
Echo가 메시지를 받아서 파이프라인 실행
    ↓
결과 완료 후 텔레그램으로 알림 전송
```

이 그림을 위에서부터 읽어볼게요. 첫 줄, 크론 트리거. 정해진 시간이 되면 크론이 깨어납니다. 둘째 줄, 등록해둔 메시지가 Echo한테 전달돼요. 셋째 줄, Echo는 그 메시지를 읽고 s8에서 본 파이프라인을 시작합니다. Aria부터 Evan까지 순서대로요. 넷째 줄, 전부 끝나면 텔레그램으로 결과 알림이 옵니다. 크론이 하는 일은 첫 두 줄뿐이에요. 나머지는 에이전트 구조가 알아서 처리합니다.

중요한 포인트가 있어요. 크론이 에이전트에게 보내는 건 **사람이 직접 보내는 채팅 메시지랑 완전히 같은 형식**입니다.

여러분이 텔레그램에서 Echo한테 "파이프라인 실행해줘."라고 보내는 거랑, 크론이 오전 9시에 자동으로 같은 메시지를 보내는 거랑 에이전트 입장에선 차이가 없어요. 둘 다 똑같이 처리됩니다.

이게 왜 중요하냐면, **별도의 API나 자동화 코드가 필요 없다**는 뜻이에요. 크론에 메시지 내용만 써두면 그걸 에이전트가 받아서 실행합니다.

다른 설계도 가능했을 거예요. 자동화 전용 API를 만들고, 스크립트를 짜서 호출하는 방식이요. 실제로 많은 자동화 도구가 그렇게 돼 있습니다. 그런데 그 방식은 배울 게 늘어나요. API 문법 따로, 채팅 문법 따로. 메시지 방식은 배울 게 하나예요. 채팅으로 시켜본 일은 전부 크론으로 자동화할 수 있습니다. 손으로 한 번 해보고, 잘 되면 그 메시지를 그대로 크론에 등록하는 흐름이에요.

여기서 이런 질문 하실 수 있어요. 크론이 보낸 메시지에도 에이전트가 답장을 하나요? 네, 합니다. 사람이 보낸 메시지에 답하듯이 똑같이 답해요. 파이프라인이 끝나면 텔레그램으로 오는 완료 알림이 바로 그 답장입니다.

---

매주 월요일 오전 9시에 대시보드가 만들어지는 흐름을 상상해보세요.

월요일 9시, 여러분은 아직 출근 준비 중이에요. OpenClaw 크론이 자동으로 Echo한테 메시지를 보냅니다. Echo가 파이프라인을 시작하고, 다섯 에이전트가 순서대로 작업해요. 40분쯤 후에 텔레그램으로 "파이프라인 완료. 생성된 파일: 01_dataset_profile.md, 02_eda_report.md ... 07_executive_report.md"라는 알림이 와요.

여러분은 출근해서 커피 한 잔 마시면서 06_dashboard.html을 열면 됩니다. 오전 보고 준비 완료예요.

이게 크론이랑 파이프라인을 연결했을 때 만들어지는 루틴이에요.

수동이었을 때랑 비교해보세요. 크론이 없으면 월요일 아침마다 여러분이 기억해내야 해요. "아, 리포트 돌려야지." 그리고 텔레그램을 열고 메시지를 보내야 하죠. 메시지 한 줄이니까 별거 아닌 것 같지만, 휴가 가면 끊기고, 바쁘면 잊어버려요. 크론은 잊지 않습니다. 반복 업무에서 사람의 기억을 빼내는 것, 이게 이 연결의 목적이에요.

---

## s13 — 크론 스케줄 종류 (5분)

> **🎬 촬영** — 슬라이드만

**[화면: s13 슬라이드]**

크론 스케줄 지정 방식이 두 가지예요. 상황에 따라 골라 쓰시면 됩니다.

---

첫 번째는 `--every`예요. **단순 주기**를 지정할 때 쓰는 방식입니다.

```bash
--every 1d    # 매일
--every 2h    # 2시간마다
--every 30m   # 30분마다
--every 1w    # 매주
```

숫자 + 단위로 써요. `d`는 day, `h`는 hour, `m`은 minute, `w`는 week입니다.

네 줄을 하나씩 읽어볼게요. `--every 1d`는 1일마다, 그러니까 매일 한 번이에요. `--every 2h`는 2시간마다. 하루에 12번 실행됩니다. `--every 30m`은 30분마다. 모니터링처럼 자주 확인해야 하는 작업용이에요. `--every 1w`는 일주일마다 한 번입니다.

매일 한 번 전날 데이터 요약을 받고 싶다면 `--every 1d`를 쓰면 됩니다. 실시간성이 중요한 데이터라면 `--every 2h`로 2시간마다 돌릴 수도 있어요.

언제 실행되냐고요? `--every` 옵션은 등록한 시점부터 주기가 시작돼요. 오전 10시에 `--every 1d`로 등록하면 매일 오전 10시에 실행됩니다.

여기가 `--every`의 약점이에요. 등록한 시각이 곧 실행 시각이 됩니다. "매일 오전 8시 정각에 실행"을 원하는데 오후 3시에 등록하면, 매일 오후 3시에 돌아요. 이걸 모르고 등록하면 원하는 시간에 리포트가 안 와서 당황하게 됩니다. 정확한 시각이 필요하면 다음에 볼 `--cron`을 쓰세요.

---

두 번째는 `--cron`이에요. **정확한 시간을 지정**하고 싶을 때 쓰는 방식입니다.

cron 표현식이라는 걸 씁니다. 처음 보면 좀 낯설 수 있는데, 패턴만 알면 읽기 어렵지 않아요.

```
형식: 분 시 일 월 요일
예시: 0 9 * * 1
      │ │ │ │ └── 요일 (1=월요일)
      │ │ │ └──── 월 (*=매월)
      │ │ └────── 일 (*=매일)
      │ └──────── 시 (9=오전 9시)
      └────────── 분 (0=0분)
```

`0 9 * * 1`은 "매주 월요일 오전 9시 0분"이에요.

읽는 요령을 알려드릴게요. 다섯 칸이 왼쪽부터 분, 시, 일, 월, 요일 순서예요. 별표 `*`는 "전부"라는 뜻입니다. 일 자리에 `*`면 매일, 월 자리에 `*`면 매월이에요.

`0 9 * * 1`을 칸별로 읽으면 이렇게 돼요. 첫 칸 `0`, 0분. 둘째 칸 `9`, 9시. 셋째 칸 `*`, 날짜 제한 없음. 넷째 칸 `*`, 월 제한 없음. 다섯째 칸 `1`, 월요일. 합치면 "월요일이면 날짜 상관없이 9시 0분에 실행"이 됩니다.

처음엔 뒤에서부터 읽는 게 편해요. 요일부터 보면 "월요일에", 그다음 시·분을 보면 "9시 0분에". 한국어 어순이랑 맞아서 자연스럽게 읽힙니다.

여기서 자주 하는 실수가 하나 있어요. 분이랑 시의 순서를 바꿔 쓰는 거예요. "9시니까 9를 먼저"라고 생각해서 `9 0 * * 1`이라고 쓰면, 이건 매주 월요일 **0시 9분**이 됩니다. 새벽에 파이프라인이 돌아요. 분이 먼저, 시가 그다음. 이 순서만 기억하시면 됩니다. 등록 후에 스케줄이 의도대로 들어갔는지 확인하는 방법은 다음 슬라이드에서 볼게요.

자주 쓰는 패턴 몇 가지 알려드릴게요.

```bash
"0 9 * * 1"     # 매주 월요일 오전 9시
"0 8 * * 1-5"   # 평일 매일 오전 8시
"0 9 1 * *"     # 매월 1일 오전 9시
"30 17 * * 5"   # 매주 금요일 오후 5시 30분
```

네 가지를 하나씩 해독해볼게요.

`0 9 * * 1` — 분 0, 시 9, 요일 1. 매주 월요일 오전 9시. 주간 보고용 기본 패턴이에요.

`0 8 * * 1-5` — 요일 자리가 `1-5`예요. 하이픈은 범위입니다. 1부터 5까지, 월요일부터 금요일까지라는 뜻이에요. 평일 매일 오전 8시. 일일 리포트에 씁니다. 주말엔 안 돌아요.

`0 9 1 * *` — 이번엔 일 자리에 `1`이 있고 요일 자리가 `*`예요. 매월 1일 오전 9시. 월간 결산용입니다. 셋째 칸의 1은 날짜, 다섯째 칸의 1은 요일. 같은 숫자라도 자리가 다르면 뜻이 달라져요.

`30 17 * * 5` — 분이 30, 시가 17, 요일이 5. 매주 금요일 오후 5시 30분. 17시는 24시간 표기예요. 주간 마감 정리에 씁니다.

월요일 오전 주간 보고라면 `0 9 * * 1`, 퇴근 전 일일 요약이라면 `30 17 * * 1-5` 이런 식으로요.

---

스케줄을 정할 때의 사고 과정도 이야기할게요. 표현식 문법보다 이게 더 중요해요.

거꾸로 계산하는 겁니다. 결과물이 필요한 시점에서 출발해요. 월요일 10시에 주간 회의가 있다고 해봅시다. 회의 전에 대시보드를 검토하려면 9시 반쯤엔 결과가 있어야 해요. 파이프라인이 20~40분 걸리니까, 늦어도 9시에는 시작해야 합니다. 그래서 `0 9 * * 1`이 아니라, 상황에 따라 더 이른 시각이 답일 수도 있어요. "몇 시에 돌릴까"가 아니라 "몇 시에 필요한가"에서 역산하는 거예요.

데이터가 준비되는 시점도 봐야 해요. 전일 데이터를 분석하는 크론을 자정 직후에 돌리면, 데이터가 아직 집계 전일 수 있어요. 데이터가 쌓이는 시점 이후, 결과가 필요한 시점 이전. 이 사이에 스케줄을 놓는 게 설계의 전부입니다.

---

`--every`랑 `--cron` 중 어떤 걸 쓸지는 간단해요.

"며칠마다, 몇 시간마다"처럼 **간격**이 중요하면 `--every`를 쓰세요. "월요일 오전 9시에"처럼 **특정 시간**이 중요하면 `--cron`을 쓰세요.

여기서 이런 질문 하실 수 있어요. `--every 1w`로 등록해도 매주 한 번이니까 주간 보고에 쓸 수 있지 않나요? 쓸 수는 있어요. 그런데 등록한 요일·시각에 묶입니다. 수요일 오후에 등록하면 매주 수요일 오후에 돌아요. 월요일 오전으로 바꾸려면 그 시각에 맞춰 다시 등록해야 하죠. `--cron "0 9 * * 1"`은 언제 등록하든 월요일 9시예요. 같은 주기라도 시각이 의미 있으면 `--cron`이 맞습니다.

비즈니스 루틴이라면 대부분 `--cron`이에요. 보고서는 특정 요일, 특정 시간에 만들어야 하거든요. `--every`는 시각이 아무래도 상관없는 반복 작업, 예를 들어 몇 시간마다 지표를 갱신하는 용도에 어울립니다.

---

## s23 — 크론 message — 바로 쓸 수 있는 프롬프트 (5분)

> **🎬 촬영** `[데모 — 터미널]`

복붙용:
```bash
# 매주 월요일 오전 9시
openclaw cron add \
  --cron "0 9 * * 1" \
  --message "그룹 ID는 -XXXXXXXXXX야. 단톡방에서 Aria 불러서 파이프라인 시작해줘. CSV는 ~/Projects/openclaw-pipeline-kit/runs/latest/input/ 에 있어. 완료 후 생성된 파일 목록을 알려줘." \
  --agent main

# 매일 오전 8시
openclaw cron add \
  --every 1d \
  --message "~/Projects/openclaw-pipeline-kit/runs/latest/input/ 최신 파일 분석해서 지표 3개와 전일 대비 변화 요약해줘." \
  --agent main
```

등록 확인:
```bash
openclaw cron list
```

---

**[화면: 터미널]**

프롬프트 작성법을 보기 전에, 왜 이게 중요한지 먼저 이야기할게요.

크론이 에이전트한테 보내는 메시지는 **여러분이 직접 써두는 텍스트**예요. 이 메시지를 에이전트가 받아서 그대로 실행하기 때문에, 메시지가 모호하면 에이전트가 엉뚱하게 동작할 수 있어요. 사람한테 지시할 때랑 똑같아요. 지시가 명확할수록 결과도 명확합니다.

크론 메시지가 일반 채팅보다 더 까다로운 이유가 하나 있어요. 채팅은 에이전트가 잘못 알아들으면 여러분이 바로 정정할 수 있어요. "아니, 그 파일 말고 이 파일." 이렇게요. 크론은 새벽이든 아침이든 여러분이 없을 때 실행됩니다. 정정할 기회가 없어요. 그래서 한 번에 정확하게 전달되도록 메시지를 써둬야 합니다. 지금 볼 세 가지 팁이 전부 그 목적이에요.

---

프롬프트 작성 팁 세 가지예요.

**첫 번째, 파일 경로를 절대경로로 명시하세요.**

```bash
# 좋지 않은 예
--message "input 폴더에 있는 CSV로 파이프라인 실행해줘."

# 좋은 예
--message "~/Projects/openclaw-pipeline-kit/runs/latest/input/ 에 있는 CSV 파일로 파이프라인 실행 을 실행하세요."
```

왜냐하면 크론은 특정 작업 디렉토리를 전제하지 않아요. 상대경로를 쓰면 어느 위치에서 실행되느냐에 따라 파일을 못 찾을 수 있습니다. 절대경로는 어디서 실행돼도 항상 같은 파일을 가리켜요.

나쁜 예를 다시 보세요. "input 폴더"라고만 하면 에이전트가 어느 input 폴더인지 추측해야 해요. 추측이 맞을 수도 있지만, 다른 프로젝트에도 input 폴더가 있으면 엉뚱한 데이터를 분석할 수 있습니다. 여기서 자주 하는 실수가 경로를 손으로 타이핑하다가 폴더명 한 글자를 틀리는 거예요. 그러면 에이전트가 파일을 못 찾아서 파이프라인이 시작도 못 합니다. 경로는 타이핑하지 말고, 터미널에서 복사해서 붙여넣으세요.

---

**두 번째, 완료 조건을 명시하세요.**

```bash
# 완료 조건이 없는 예
--message "데이터 분석해줘."

# 완료 조건이 있는 예
--message "~/Projects/.../input/ CSV로 파이프라인 실행하세요. 완료 후 생성된 파일 목록을 알려주세요."
```

"완료 후 파일 목록 출력"처럼 끝내는 조건이 있어야 에이전트가 작업이 끝난 걸 인식하고 멈춥니다. 완료 조건이 없으면 에이전트가 계속 다음 작업을 찾거나, 응답 대기 상태에서 멈출 수 있어요.

완료 조건은 여러분한테도 필요해요. "완료 후 생성된 파일 목록을 알려주세요"라고 써두면, 파이프라인이 끝났을 때 텔레그램으로 파일 목록이 옵니다. 그 목록을 보고 7개가 다 만들어졌는지 폰에서 바로 확인할 수 있어요. 완료 조건이 곧 보고 형식인 거예요. 사람한테 일 시킬 때 "끝나면 뭐뭐 됐는지 알려줘"라고 붙이는 것과 같습니다.

---

**세 번째, 슬래시 명령어를 직접 넣으세요.**

```bash
--message "... 파이프라인 실행 을 실행하세요."
```

"파이프라인 실행해줘"처럼 Echo가 알아듣는 자연어 시작 문구를 넣어주세요. 슬래시 명령어가 아니라 자연어예요. Echo의 AGENTS.md에 파이프라인 실행 순서가 정의돼 있어서, 시작 지시만 명확하면 나머지는 알아서 진행해요.

이게 왜 좋냐면, 메시지에서 해석의 여지를 줄여주기 때문이에요. "데이터 분석 좀 해줘"라고 하면 Echo가 어떤 분석을 원하는지 판단해야 해요. `파이프라인 실행`이라고 하면 판단할 게 없어요. AGENTS.md에 정의된 그 절차를 그대로 실행하면 됩니다. 자연어의 유연함이 필요 없는 자리에서는 정해진 문구가 안전해요.

---

자, 실제 명령어를 터미널에 붙여넣겠습니다.

**[화면: 터미널]**

```bash
# 매주 월요일 오전 9시 — 주간 대시보드
openclaw cron add \
  --cron "0 9 * * 1" \
  --message "그룹 ID는 -XXXXXXXXXX야. 단톡방에서 Aria 불러서 파이프라인 시작해줘. CSV는 ~/Projects/openclaw-pipeline-kit/runs/latest/input/ 에 있어. 완료 후 생성된 파일 목록을 알려줘." \
  --agent main
```

붙여넣기 전에 이 명령을 부분별로 읽어볼게요.

첫 줄 `openclaw cron add`. 크론 잡을 새로 등록하겠다는 뜻이에요.

둘째 줄 `--cron "0 9 * * 1"`. 방금 배운 표현식이죠. 매주 월요일 오전 9시입니다.

셋째 줄 `--message`가 제일 길어요. 이 안에 문장이 네 개 들어 있는데, 각각 역할이 있습니다. "그룹 ID는 -XXXXXXXXXX야." — Echo한테 어느 단톡방에서 작업할지 알려주는 문장이에요. 이게 없으면 Echo가 어느 방에 서브 에이전트들을 불러야 할지 몰라요. "단톡방에서 Aria 불러서 파이프라인 시작해줘." — 시작 지시예요. 첫 주자인 Aria를 지목합니다. "CSV는 ~/Projects/openclaw-pipeline-kit/runs/latest/input/ 에 있어." — 입력 위치예요. 첫 번째 팁에서 말한 절대경로가 여기 들어갑니다. "완료 후 생성된 파일 목록을 알려줘." — 두 번째 팁의 완료 조건이에요.

넷째 줄 `--agent main`. 이 메시지를 받을 에이전트 지정이에요. main이 Echo입니다. 총괄한테 보내야 파이프라인 전체가 돌아요. 실수로 다른 에이전트를 지정하면 그 에이전트 혼자 자기 스텝만 하고 끝납니다.

따라해보세요. 복붙하셔도 됩니다. `-XXXXXXXXXX` 자리만 여러분 그룹 ID로 바꾸시고요. 잠깐 기다릴게요. 그 사이에 하나 말씀드리면, 월요일 9시로 등록해도 지금 당장 뭔가 실행되지는 않아요. 예약만 걸린 상태예요. 실제 실행은 다음 월요일 9시입니다. 그래서 등록 직후엔 화면에 아무 변화가 없는 게 정상이에요.

등록이 되면 터미널에 성공 메시지가 뜹니다. 확인해볼게요.

```bash
openclaw cron list
```

등록된 크론 목록이 나와요. 출력을 한 줄씩 보면, ID는 이 크론 잡을 가리키는 식별자예요. 나중에 이 잡을 관리할 때 씁니다. 스케줄 칸에 `0 9 * * 1`이 보이면 표현식이 의도대로 들어간 거예요. s13에서 말한 분·시 순서 실수도 여기서 잡을 수 있습니다. 메시지 칸에는 등록한 문장이 그대로 보이고, 에이전트 칸에 main이 보여요. 방금 등록한 항목이 있으면 정상이에요.

크론을 등록만 하고 list로 확인 안 하는 것도 자주 하는 실수예요. 오타가 있어도 등록 자체는 되는 경우가 있거든요. 등록하면 바로 list. 이걸 습관으로 붙이세요.

---

매일 오전 8시짜리 일일 요약 크론도 하나 더 등록해볼게요.

```bash
# 매일 오전 8시 — 일일 지표 요약
openclaw cron add \
  --every 1d \
  --message "~/Projects/openclaw-pipeline-kit/runs/latest/input/ 최신 파일 분석해서 지표 3개와 전일 대비 변화 요약해줘." \
  --agent main
```

이건 `--cron` 대신 `--every 1d`를 썼어요. 매일 실행하는데 특정 시간은 상관없는 경우예요. 메시지도 앞의 것보다 가볍죠. 파이프라인 전체를 돌리는 게 아니라 지표 3개랑 전일 대비 변화만 요약해달라고 했어요. 매일 받는 건 가볍게, 매주 받는 건 무겁게. 주기랑 작업 무게를 맞추는 거예요. 매일 7개 파일짜리 풀 파이프라인을 돌리면 읽지도 않는 보고서가 쌓입니다.

---

활용 시나리오를 몇 가지 드릴게요. 여러분 상황에 맞게 응용하시면 됩니다. 각 시나리오마다 스케줄이랑 메시지를 왜 그렇게 잡았는지도 같이 볼게요.

**마케팅팀** 시나리오예요. 매주 월요일 오전 9시에 지난 주 광고 성과 CSV를 분석해서 채널별 ROAS, 전환율, 예산 소진율 대시보드를 만들어요. 팀장이 출근하기 전에 이미 대시보드가 준비돼 있는 거예요. 월요일 9시인 이유는 광고 성과가 주 단위로 집계되고, 주간 회의가 보통 월요일에 있기 때문이에요. 메시지에 ROAS·전환율·예산 소진율을 콕 집어 넣은 건, 팀에서 매주 보는 지표를 고정하기 위해서입니다. 지표를 명시 안 하면 에이전트가 매주 다른 지표를 고를 수 있어요.

```bash
openclaw cron add \
  --cron "0 9 * * 1" \
  --message "~/data/marketing/weekly/ 최신 CSV로 파이프라인 실행해줘. 채널별 ROAS·전환율·예산 소진율 포함한 대시보드 만들어줘. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

**IR팀** 시나리오예요. 매월 1일 오전 8시에 전월 재무 지표를 분석해요. 매출, 영업이익, 비용 구조 변화를 임원 보고서 형식으로 만들어줍니다. 표현식이 `0 8 1 * *`인 걸 보세요. 셋째 칸에 1이 들어가고 요일 칸이 `*`예요. 요일이 아니라 날짜 기준이라는 뜻입니다. 재무 데이터는 월 단위로 마감되니까 매월 1일이 맞아요. s13에서 본 "같은 1이라도 자리가 다르면 뜻이 다르다"가 여기서 실제로 쓰입니다.

```bash
openclaw cron add \
  --cron "0 8 1 * *" \
  --message "~/data/finance/monthly/ 최신 CSV로 파이프라인 실행해줘. 매출·영업이익·비용 구조 분석 포함한 임원 보고서 만들어줘. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

**HR팀** 시나리오예요. 매월 첫째 월요일에 인력 현황 데이터를 분석합니다. 부서별 인원 변동, 이탈률, 채용 현황을 정리해줘요. 요일 자리의 `1#1`은 "첫째 주 월요일"을 뜻하는 확장 표기예요. 매월 1일이 주말일 수 있는데, 월초 첫 근무 주에 받고 싶을 때 이런 표기를 씁니다. 인사 데이터처럼 월 단위로 움직이지만 확인은 근무일에 해야 하는 경우예요.

```bash
openclaw cron add \
  --cron "0 9 * * 1#1" \
  --message "~/data/hr/monthly/ 최신 CSV로 파이프라인 실행해줘. 부서별 인원·이탈률·채용 현황 분석해줘. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

**영업팀** 시나리오예요. 평일 매일 오전 8시에 전일 영업 실적을 분석해요. 지역별, 담당자별 목표 달성률이랑 파이프라인 현황을 매일 아침 받아봅니다. `0 8 * * 1-5`의 `1-5`가 앞에서 배운 범위 표기예요. 주말엔 영업 활동이 없으니까 돌릴 이유가 없죠. 토요일 아침에 의미 없는 리포트가 오는 걸 막는 표기입니다. 영업처럼 일 단위로 움직이는 조직은 주기가 짧고, 재무처럼 월 단위로 움직이는 조직은 주기가 길어요. 업무의 리듬이 곧 크론의 주기예요.

```bash
openclaw cron add \
  --cron "0 8 * * 1-5" \
  --message "~/data/sales/daily/ 최신 CSV로 파이프라인 실행해줘. 지역별·담당자별 목표 달성률 분석. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

**1인 사업자** 시나리오예요. 주간 정산 데이터나 구글 애널리틱스 export CSV를 넣어두면, 매주 월요일에 트래픽·전환·수익 요약이 텔레그램으로 와요. 별도 분석 툴 없이도 주간 현황을 파악할 수 있습니다. 1인 사업자한테 이 구성이 특히 잘 맞는 이유가 있어요. 분석 담당 직원이 없잖아요. 대시보드 툴을 구독하고 배우는 것도 부담이고요. 주말에 정산 CSV를 폴더에 넣어두는 것까지만 하면, 월요일 아침에 요약이 도착해요. 분석팀을 고용한 것과 비슷한 루틴이 크론 한 줄로 생기는 겁니다.

```bash
openclaw cron add \
  --cron "0 9 * * 1" \
  --message "~/data/business/weekly/ 최신 CSV로 파이프라인 실행해줘. 트래픽·전환·수익 주간 요약 만들어줘. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

공통점이 보이시나요? 절대경로, 파이프라인 실행 요청, 완료 조건. 이 세 가지가 항상 들어가 있어요. 이 패턴을 그대로 쓰시면서 파일 경로랑 분석 요구사항만 바꾸시면 됩니다.

다섯 시나리오를 나란히 놓고 보면 바뀐 건 세 군데뿐이에요. 스케줄 표현식, 데이터 폴더 경로, 그리고 분석 요구사항 문장. 나머지 뼈대는 전부 동일합니다. 그러니까 여러분이 새 크론을 만들 때 할 일은 이 세 칸을 채우는 거예요. 우리 팀 데이터는 언제 나오는가, 어디에 두는가, 뭘 보고 싶은가. 이 세 질문에 답하면 크론 한 줄이 완성됩니다.


## s42 — 직업군별 자연어 자동화 시나리오 (7분)

> **🎬 촬영** — 슬라이드만

**[화면: s42 슬라이드]**

방금 크론 표현식을 배웠어요. `0 9 * * 1` 이런 거요. 그런데 솔직히 말씀드리면, 이 표현식을 외울 필요가 없어요.

OpenClaw한테는 그냥 한국어로 말하면 됩니다. "매주 월요일 아침 9시에 이거 해줘"라고 텔레그램에 보내면, OpenClaw가 그 말을 알아듣고 예약을 알아서 잡아줘요. 표현식은 OpenClaw가 내부에서 변환하는 거고, 여러분은 사람한테 부탁하듯이 말하면 됩니다.

그래서 이번엔 코드나 표현식 없이, 순수하게 한국어 문장 하나로 어떤 자동화가 가능한지 직업군별로 다섯 가지 보여드릴게요.

---

**마케터부터 볼게요.**

"매주 월요일 아침 9시에 지난주 광고 CSV 분석해서 채널별 ROAS랑 전환율 대시보드 만들어줘." 이 한 문장이면 됩니다. 월요일 출근 전에 주간 광고 대시보드가 텔레그램에 와 있어요. 우리가 이번 클립에서 만든 게 딱 이거예요.

**재무나 IR 담당자예요.**

"매달 1일 아침에 전월 재무 데이터로 매출·영업이익·비용 변화 임원 보고서 만들어줘." 재무는 월 단위로 마감되니까 매달 1일이 맞아요. "매달 1일"이라고 말로 하면 돼요. 날짜 표현식을 몰라도요.

**HR, 인사 담당자예요.**

"매달 첫째 주 월요일에 인력 현황 분석해서 부서별 인원 변동·이탈률·채용 현황 정리해줘." 여기서 "첫째 주 월요일"이 표현식으로는 꽤 까다로운 건데, 말로는 그냥 "첫째 주 월요일"이면 끝이에요.

**영업팀이에요.**

"평일 아침 8시마다 전일 영업 실적 분석해서 지역·담당자별 목표 달성률 보내줘." "평일"이라고만 하면 주말은 알아서 빠져요. 토요일 아침에 의미 없는 리포트가 오는 걸 막으려고 표현식을 외울 필요가 없어요.

**마지막으로 1인 사업자예요.**

"매주 월요일에 정산 CSV로 트래픽·전환·수익 요약해서 텔레그램으로 보내줘." 분석 담당 직원도, 대시보드 툴 구독도 없이, 주말에 CSV만 폴더에 넣어두면 월요일 아침에 요약이 와요. 분석팀을 고용한 것과 비슷한 루틴이 문장 하나로 생기는 겁니다.

다섯 개를 관통하는 구조가 보이시죠. **언제, 어떤 데이터로, 뭘 만들지.** 이 세 가지만 문장에 담으면 돼요. 표현식도, 코드도 필요 없습니다.

그리고 한 가지 더요. 이렇게 자주 쓰는 자동화는 이름을 붙여서 저장해둘 수 있어요. "이 작업을 '주간 광고 리포트'라는 이름으로 기억해줘"라고 하면, 다음부터는 긴 문장 대신 그 이름만 부르면 됩니다. 반복하는 업무일수록 이렇게 이름을 붙여두면 편해요.

정리하면, 크론 표현식은 원리를 이해하는 데는 좋지만, 실제로 쓸 때는 그냥 한국어로 말하면 됩니다. 이게 OpenClaw의 편한 점이에요.

로그가 흘러나오기 시작합니다. 각 줄이 무슨 의미인지 설명할게요. 로그 읽는 법을 한번 익혀두면, 나중에 파이프라인이 이상하게 동작할 때 어디를 봐야 할지 스스로 찾을 수 있어요.

[Echo] Parsing intent: 파이프라인 실행

세 줄을 하나씩 볼게요. `Received message`는 텔레그램 메시지가 Echo한테 도착했다는 뜻이에요. 여러분이 보낸 그 문장이 따옴표 안에 그대로 보입니다. `Parsing intent: 파이프라인 실행`은 Echo가 메시지에서 "파이프라인을 시작하라"는 의도를 읽어냈다는 뜻이에요. `Reading AGENTS.md...`는 s8에서 설명한 그 파일, 그러니까 진행 규칙을 읽는 중이라는 뜻입니다. 이 세 줄이 보이면 접수가 정상적으로 된 거예요. 반대로 메시지를 보냈는데 `Received message`부터 안 뜨면, 메시지가 Echo까지 도달하지 못한 겁니다. 그땐 페어링 상태부터 확인하면 돼요.

이 텔레그램 알림이 왜 중요한지 이야기할게요.

파이프라인은 백그라운드에서 돌아요. 여러분이 브라우저에서 activity-monitor를 띄워놓지 않으면 언제 끝났는지 알 방법이 없어요. 텔레그램 알림이 오면 컴퓨터 앞에 없어도 바로 알 수 있습니다.

텔레그램이라는 채널이라서 좋은 점도 있어요. 폰에 있잖아요. 이동 중에도, 회의 중에도, 침대에서도 확인이 됩니다. 월요일 아침 출근길 지하철에서 "파이프라인 완료, 파일 7개"를 확인하는 상황을 상상해보세요. 사무실에 도착하기 전에 이미 오늘 보고가 준비된 걸 아는 거예요.

크론으로 설정해두면 이게 더 의미 있어요. 월요일 오전에 자동으로 파이프라인이 돌고, 끝나면 텔레그램으로 알림이 와요. 여러분은 폰으로 확인하고, 출근해서 대시보드를 열면 됩니다.

흐름을 한 번 더 정리할게요.

세 단계예요.

**1단계:** 크론 시간이 되면, 또는 텔레그램에서 직접 메시지를 보내면, OpenClaw가 Echo 에이전트를 깨워서 메시지를 전달합니다.

**2단계:** Echo가 AGENTS.md를 보고 파이프라인을 실행합니다. Aria → Sam → Min → Evan 순서로 각 에이전트가 작업하고, 결과를 파일로 넘겨요.

**3단계:** 모든 에이전트 작업이 완료되면 Echo가 텔레그램으로 결과 파일 목록을 전송합니다.

컴퓨터 앞에 있을 필요가 없어요. 텔레그램으로 결과를 수신하면 됩니다.

이 세 단계에서 사람이 개입하는 지점이 몇 개인지 세어보세요. 크론이면 0개예요. 시작도 자동, 진행도 자동, 보고도 자동. 직접 메시지를 보내는 경우에도 1개, 시작 신호뿐입니다. 이번 클립에서 만들고 있는 게 바로 이 구조예요. 사람은 결과를 받아서 판단하는 자리에만 있으면 됩니다.

여기서 이런 질문 하실 수 있어요. 알림이 안 오면 어떻게 하나요? 두 가지 경우예요. 아직 도는 중이거나, 중간에 멈췄거나. 구분하려면 아까 배운 `openclaw logs --follow`로 로그를 보면 됩니다. 마지막 로그가 계속 갱신되고 있으면 진행 중이고, 특정 스텝에서 멈춰 있으면 그 지점이 문제예요. 알림은 결과 채널이고, 로그는 진단 채널. 이렇게 역할을 나눠서 기억해두시면 됩니다.

KPI 목록이 표로 정리돼 있습니다.

```
| KPI         | 계산식                        | 단위  | 목적               |
|-------------|-------------------------------|-------|--------------------|

| CVR         | conversions / clicks × 100   | %     | 랜딩 효율          |
| CPC         | spend / clicks                | 원    | 클릭 단가          |
| CPA         | spend / conversions           | 원    | 전환 단가          |
| ROAS        | revenue / spend × 100         | %     | 광고 수익률        |
```

이 표를 읽는 법부터 볼게요. 열이 네 개예요. 지표명, 계산식, 단위, 목적. 이 네 열이 지표 정의의 최소 구성입니다. 계산식 열을 보세요. CTR이 "클릭을 노출로 나눈다"라고 말로 적힌 게 아니라 `clicks / impressions × 100`이라고 컬럼명 그대로 적혀 있어요. 해석의 여지가 없죠. 실무에서 부서마다 전환율 숫자가 다르게 나오는 사고 대부분이 계산식을 말로만 합의해서 생깁니다. 분모를 뭘로 쓰는지가 사람마다 다른 거예요. 이 표는 그걸 원천 차단합니다.

표의 흐름도 의미가 있어요. CTR에서 CVR, CPC, CPA, ROAS로 내려가는 순서가 광고의 단계 순서예요. 노출에서 클릭, 클릭에서 전환, 그리고 비용 효율. 위에서 아래로 읽으면 광고 성과를 보는 순서가 됩니다.

각 KPI 아래에 **왜 이 지표를 선택했는지** 이유도 써있어요. "CTR은 광고 소재 자체의 매력도를 측정합니다. CTR이 낮으면 타겟팅보다 크리에이티브 문제를 먼저 확인해야 합니다." 이런 식으로요. 지표가 낮을 때 어디를 봐야 하는지까지 적혀 있는 거예요. 정의서이면서 해석 안내서인 셈입니다.

**차원 분석** 섹션도 있어요. "채널별, 월별, 캠페인별로 분해합니다." 라고 써있어요. Min이 이 차원에 따라 집계해요. 차원이 왜 중요하냐면, 전체 ROAS가 좋아도 채널별로 쪼개면 한 채널이 다른 채널의 부진을 가리고 있을 수 있거든요. 쪼개서 봐야 문제가 보입니다.

Min은 이 문서를 받아서 정의된 공식대로 계산만 하면 됩니다. KPI 정의가 명확하면 분석 결과도 일관성이 유지돼요. 그리고 이 파일은 파이프라인 밖에서도 쓸모가 있어요. 팀에 새 멤버가 오면 "우리 팀 지표는 이렇게 계산한다"는 문서로 이 파일을 그대로 주면 됩니다.

## s31 — 디자인 토큰으로 대시보드 퀄리티 올리기

> **🎬 촬영** `[슬라이드만]`

대시보드 열어본 직후 슬라이드로 마무리. 프롬프트 복붙 시연은 선택.

---

**[화면: 슬라이드]**

방금 Evan이 만든 `06_dashboard.html`을 열어봤죠. 클립 마무리 전에, 이 대시보드 퀄리티를 한 단계 더 올리는 방법을 알려드릴게요.

대시보드를 브라우저에서 열면 데이터는 다 있는데 뭔가 허전한 느낌이 들 때가 있습니다. 색이 일관되지 않거나, 버튼 스타일이 제각각이거나, 다크 모드가 없거나.

이 허전함의 원인을 짚고 갈게요. 데이터의 문제가 아니에요. 색을 그때그때 정해서 생기는 문제예요. 카드 만들 때 회색 하나 고르고, 차트 만들 때 또 비슷한 회색 고르고. 한 화면에 미묘하게 다른 회색이 네다섯 개 섞이면, 뭐가 문제인지 꼬집어 말하긴 어려운데 어수선한 인상이 됩니다. 색을 고르는 기준이 없다는 게 원인이에요.

그 허전함을 채우는 방법이 두 가지 있습니다.

**PATH A는 키트 그대로 실행**이에요. 가장 빠른 방법입니다. 레포를 클론하고 `bash setup.sh`를 실행하고 파이프라인을 한 번 돌리면 5분 안에 완성된 대시보드가 나와요. 실습할 때는 이 방법으로 따라하시면 됩니다.

Evan 에이전트가 이미 좋은 품질의 대시보드를 만들도록 셋업돼 있어요. Evan의 AGENTS.md에 디자인 시스템 가이드가 들어있고, 에이전트가 그 가이드를 보고 대시보드를 작성합니다. 그러니까 방금 열어본 대시보드가 어느 정도 정돈돼 보였던 건 우연이 아니에요. 지시문에 디자인 기준이 미리 들어가 있었던 겁니다.

**PATH B는 처음부터 만들기**예요. 자기 브랜드에 맞는 색상 시스템을 적용하고 싶을 때 쓰는 방법입니다.

GitHub 링크 하나를 Claude Code 프롬프트에 붙여넣으면 돼요.

링크는 `github.com/material-foundation/material-tokens`입니다. 구글이 만든 **Material Design 3** 공식 디자인 토큰 레포예요.

Material Design 3가 뭔지 간단하게 설명할게요. 구글이 Android, Gmail, YouTube 같은 제품에 적용하는 디자인 시스템이에요. 여기서 "토큰"이란 색상, 크기, 간격 같은 디자인 값들을 이름 붙여서 변수로 관리하는 방식이에요. 하드코딩 대신 변수를 쓰는 거죠.

토큰이라는 개념을 비유로 한 번 더 풀게요. 회사의 브랜드 규정집이라고 생각하시면 됩니다. 규정집에 "우리 회사 대표색은 이 파랑"이라고 적어두면, 명함 만드는 사람도 홈페이지 만드는 사람도 그 규정집을 참조해요. 각자 "파란색 비슷한 거"를 알아서 고르는 게 아니라요. 그러다 대표색이 바뀌면 규정집 한 줄만 고치면 되고, 그걸 참조하던 모든 결과물이 따라 바뀝니다. CSS에서 그 규정집 역할을 하는 게 `:root` 블록이고, 규정집의 각 항목이 토큰이에요.

예를 들어, 이전에 대시보드를 만들 때 배경색을 `#F9FAFB`라고 직접 썼다면, 토큰 방식에서는 `--md-sys-color-surface`라는 변수를 써요. 이 변수가 `#F9FAFB`를 가리키고 있는 거예요.

이게 왜 좋냐면, 나중에 배경색을 바꾸고 싶을 때 `--md-sys-color-surface` 하나만 수정하면 대시보드 전체에 반영됩니다. 100군데에 써있는 `#F9FAFB`를 하나씩 찾아서 바꿀 필요가 없어요. 하나씩 바꾸는 방식의 진짜 문제는 시간보다 누락이에요. 100군데 중 97군데만 바꾸면 세 군데에 옛날 색이 남아요. 그게 아까 말한 "미묘하게 다른 회색"이 되는 겁니다. 토큰은 참조하는 곳이 전부 같은 값을 보니까 누락 자체가 불가능해요.

토큰 이름도 잠깐 볼게요. `--md-sys-color-surface`가 길어 보이는데, 뜯어보면 체계가 있어요. MD3 시스템의 색상 토큰이고, 역할이 surface, 그러니까 바탕면이라는 뜻이에요. 중요한 건 이름에 색이 아니라 **역할**이 적혀 있다는 점입니다. `light-gray`가 아니라 `surface`예요. 색은 바뀌어도 역할은 안 바뀌니까, 이름을 역할로 지어두면 값을 바꿔도 이름이 계속 유효합니다. 다크 모드가 가능한 것도 이 덕분이에요. 뒤에서 보여드릴게요.

이 레포 링크를 Claude Code에 주면 CSS 변수 시스템을 자동으로 생성해줍니다. 왜 레포 링크를 주는 방식이냐면, 토큰 이름 체계를 우리가 발명할 필요가 없기 때문이에요. 구글이 수년간 다듬어서 공개해둔 명명 체계가 이미 있는데, 그걸 Claude Code한테 참고 자료로 던져주면 검증된 구조를 그대로 가져옵니다. 프롬프트는 이렇게 쓰면 돼요.

```
이 레포의 CSS 토큰 구조를 참고해서 대시보드에 적용해줘.
:root에 MD3 시맨틱 컬러 변수 정의하고,
하드코딩된 색상을 전부 토큰으로 교체하고,
다크 모드도 추가해줘.
```

이게 전부예요. 이 프롬프트가 네 줄인데, 각 줄이 Claude Code한테 시키는 작업이 하나씩 있어요. 줄 단위로 읽어볼게요.

첫 줄, "이 레포의 CSS 토큰 구조를 참고해서 대시보드에 적용해줘." 참고 자료 지정이에요. Claude Code가 레포의 토큰 명명 체계를 읽고, 우리 대시보드에 어떻게 입힐지 계획을 세웁니다. 어떤 구조를 따를지 기준을 주는 줄이에요.

둘째 줄, ":root에 MD3 시맨틱 컬러 변수 정의하고." 규정집을 만드는 작업이에요. 대시보드 CSS 맨 위에 변수 선언 블록을 새로 쓰는 겁니다. 아직 화면은 안 바뀌어요. 규정집만 생긴 상태예요.

셋째 줄, "하드코딩된 색상을 전부 토큰으로 교체하고." 제일 손이 많이 가는 작업이에요. Claude Code가 CSS 전체를 훑으면서 색상 코드가 박힌 곳을 전부 찾아서 변수 참조로 바꿉니다. 사람이 하면 지루하고 누락이 생기는 그 작업을 기계적으로 전부 처리해요. 여기서 "전부"라는 단어가 중요합니다. 이 단어가 없으면 눈에 띄는 몇 군데만 바꾸고 끝낼 수 있어요. 아까 말한 97군데 문제가 생기는 거죠. 프롬프트에서 범위를 명시하는 습관, 크론 메시지 쓸 때랑 같은 원리예요.

넷째 줄, "다크 모드도 추가해줘." 규정집의 두 번째 판을 만드는 작업이에요. 같은 토큰 이름에 어두운 화면용 값을 매긴 블록을 추가합니다.

실행되면 결과물이 어떻게 되는지 순서대로 볼게요.

먼저 `:root` 블록에 시맨틱 컬러 변수들이 정의됩니다.

```css
:root {
  --md-sys-color-primary: #3182F6;
  --md-sys-color-surface: #F9FAFB;
  --md-sys-color-on-surface: #191F28;
  --md-sys-color-outline: #E5E8EB;
  /* ... */
}
```

이 블록의 네 줄을 읽어볼게요. `primary`는 강조색이에요. 버튼이나 활성 상태처럼 눈길이 가야 하는 곳에 쓰는 색입니다. `surface`는 바탕면, 카드나 화면 배경이에요. `on-surface`는 이름 그대로 "surface 위에" 올라가는 것, 그러니까 바탕 위 글자색이에요. 바탕과 글자가 짝으로 정의돼 있어서 대비가 항상 보장됩니다. `outline`은 테두리랑 구분선 색이에요. 색상 네 개가 각자 역할을 갖고 있는 규정집이 완성된 거예요.

그 다음에 대시보드 코드에서 하드코딩된 색상들이 전부 변수로 교체됩니다. `background: #F9FAFB`가 `background: var(--md-sys-color-surface)`로 바뀌는 식이에요. `var()`는 "규정집에서 이 항목을 찾아 쓰라"는 CSS 문법입니다. 이 교체가 끝나면 대시보드 안에 직접 적힌 색상 코드가 없어져요. 모든 색이 규정집을 거쳐서 나옵니다.

마지막으로 다크 모드 CSS가 추가됩니다.

```css
@media (prefers-color-scheme: dark) {
  :root {
    --md-sys-color-primary: #6BA4FA;
    --md-sys-color-surface: #1A1D21;
    --md-sys-color-on-surface: #E2E4E8;
    --md-sys-color-outline: #2E3138;
  }
}
```

라이트 모드에서 쓰던 변수 이름 그대로인데, 값만 바뀌었어요. `surface`가 밝은 회백색에서 어두운 색으로, `on-surface`가 진한 글자색에서 밝은 글자색으로. 역할은 그대로고 값만 뒤집힌 겁니다. 맨 윗줄의 `@media (prefers-color-scheme: dark)`는 "보는 사람의 OS가 다크 모드일 때만 이 규정집을 쓰라"는 조건문이에요. OS가 다크 모드로 설정돼 있으면 이 값들이 자동으로 적용됩니다. 대시보드 코드는 그대로인데 다크 모드가 생기는 거예요.

이게 가능한 이유를 다시 짚으면, 아까 말한 역할 기반 이름 덕분이에요. 코드는 "surface 색을 써라"라고만 말하고, surface가 실제로 무슨 색인지는 규정집이 정합니다. 그래서 규정집을 두 벌 두면 화면이 두 벌 생겨요. 만약 색상이 코드에 하드코딩돼 있었다면, 다크 모드를 만들려고 CSS 전체를 복사해서 색을 일일이 다시 칠해야 했을 겁니다.

여기서 이런 질문 하실 수 있어요. 다크 모드용 색 값은 누가 정하나요? 라이트 색을 그냥 반전하면 되는 거 아닌가요? 단순 반전으로는 안 돼요. 어두운 배경에서는 같은 색도 다르게 보여서, 다크용 값은 따로 조정이 필요합니다. 그 조정된 값의 조합이 MD3 토큰 레포에 들어 있어요. 우리가 레포를 참고 자료로 준 이유가 여기서 한 번 더 작동하는 겁니다. Claude Code가 그 체계를 참고해서 다크 값을 뽑아줘요.

이렇게 하면 나중에 브랜드 색상이 바뀌어도 `:root` 블록에서 `--md-sys-color-primary` 하나만 수정하면 대시보드 전체 색이 바뀝니다.

실무 상황에 대입해볼게요. 회사에서 매주 이 대시보드를 쓰다가, 대표가 "우리 브랜드 색으로 맞춰달라"고 합니다. 토큰이 없으면 CSS를 열어서 색상 코드를 하나하나 찾아 바꾸는 작업이에요. 토큰이 있으면 `primary`에 브랜드 색 하나 넣으면 끝납니다. 그리고 이 요구는 실제로 옵니다. 대시보드가 팀 밖으로 공유되기 시작하면 반드시 와요. 미리 토큰 구조를 잡아두는 게 그때를 위한 준비예요.

여기서 자주 하는 실수도 하나 말씀드릴게요. 토큰을 적용해놓고, 나중에 급하게 수정하면서 색상 코드를 다시 직접 박아 넣는 거예요. 그 순간부터 그 부분만 규정집 밖에 있게 됩니다. 브랜드 색을 바꿔도 거기만 안 바뀌어요. 토큰 구조를 만들었으면 색은 항상 `:root`에서만 고친다, 이 원칙을 지키셔야 합니다.

PATH A와 PATH B, 두 방법 모두 같은 결과가 나와요. 원리를 이해하면 내 브랜드에 맞게 커스텀할 수 있어요. 처음에는 PATH A로 빠르게 따라하고, 나중에 자기 프로젝트에 적용할 때 PATH B 방법을 써보시길 권합니다. 그리고 PATH B로 만든 디자인 기준이 마음에 들면, 그 내용을 Evan의 AGENTS.md에 적어두세요. 그러면 다음 주 파이프라인부터 Evan이 처음부터 그 기준으로 만들어줍니다. s37에서 배운 커스텀이랑 여기서 배운 토큰이 만나는 지점이에요.
