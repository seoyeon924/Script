## CLIP 02 recap — 이번 클립에서 배울 것 (3분)

잠깐, 클립 시작 전에 전체 그림부터 짚고 가겠습니다.

지난 클립에서 OpenClaw 설치랑 기본 연동까지 마쳤습니다. Echo 봇이 텔레그램으로 제 메시지를 받는 것도 확인했고, Claude Code가 작업 에이전트로 붙어있다는 것도 봤어요.

이번 클립에서는 그 위에 뭘 올리냐면 — **자동화**예요.

제가 직접 텔레그램에 메시지를 보내지 않아도, 정해진 시간에 알아서 에이전트가 깨어나서 파이프라인을 실행하고, 결과물까지 만들어주는 흐름을 만들 거예요.

구체적으로 세 가지를 봅니다.

첫 번째, 에이전트 5명이 어떤 구조로 협업하는지. Aria, Sam, Min, Evan, 그리고 메인인 Echo가 어떤 순서로 일을 나누는지를 설명해요.

두 번째, 크론 설정이에요. "매주 월요일 오전 9시에 자동으로 파이프라인 실행"을 명령 한 줄로 설정하는 방법이에요.

세 번째, 실전 실행이에요. CSV 파일 하나 넣고 텔레그램으로 메시지 한 줄 보내면 대시보드 HTML이랑 임원 보고서까지 자동으로 만들어지는 걸 라이브로 보여드립니다. 그리고 결과물 파일 7개를 하나씩 뜯어볼 거예요.

클립이 좀 길어요. 20분짜리 데모 섹션이 하나 있는데, output 파일을 직접 열어서 같이 보는 시간이에요. 천천히 따라오시면 됩니다.

## s8 — 에이전트 5종 구조 (12분)

**[화면: s8 슬라이드]**

이번 실습에서 쓸 에이전트는 다섯 명이에요.

다섯 명이라고 하면 좀 많아 보일 수 있는데, 실제로 여러분이 관리해야 할 건 하나예요. 나머지는 알아서 돌아갑니다. 왜 다섯 명인지부터 이야기할게요.

---

분석 파이프라인을 한 에이전트가 혼자 처리하면 어떻게 될까요?

작업이 길어질수록 컨텍스트가 쌓입니다. 처음엔 빠르게 가다가, 데이터 프로파일링 결과가 쌓이고, EDA 결과가 또 쌓이고, 거기에 KPI 계산까지 더해지면 에이전트의 작업 창이 무거워져요. 그러다 결국 앞에서 분석한 내용을 참조를 못 하거나, 응답이 느려지거나, 최악의 경우 중간에 끊겨요.

그래서 **역할을 쪼갭니다**. 각 에이전트가 딱 자기 담당 스텝만 보고 결과를 파일로 넘겨요. 다음 에이전트는 그 파일을 받아서 이어서 작업하고요. 컨텍스트가 분리되니까 각 에이전트가 훨씬 깔끔하게 일합니다.

이게 멀티 에이전트 파이프라인의 이유예요.

---

자, 다섯 명을 소개할게요.

**Echo**가 메인이에요. 총괄 지휘관이라고 보시면 됩니다. 여러분이 텔레그램으로 메시지를 보내면 Echo가 받아요. 크론 잡이 설정된 시간에 보내는 메시지도 Echo한테 갑니다.

Echo가 하는 일이 뭐냐면, 메시지를 받아서 파이프라인을 오케스트레이션해요. "Aria, 이 CSV 데이터 프로파일링해줘." "Sam, Aria 결과 받아서 KPI 뽑아줘." 이런 식으로 각 서브 에이전트한테 순서대로 지시를 내립니다. 그리고 전부 완료되면 결과물 파일 목록을 텔레그램으로 여러분한테 돌려보내요.

여러분은 Echo한테 시작 신호만 주면 됩니다. 나머지는 Echo가 다 알아서 해요.

---

**Aria**는 STEP 1-2 담당이에요.

STEP 1이 **데이터 프로파일링**이에요. CSV 파일을 받으면 컬럼 구조를 파악하고, 결측치가 얼마나 있는지, 각 컬럼의 데이터 타입이 뭔지, 특이한 값은 없는지 체크해요. 결과를 `01_dataset_profile.md` 파일로 저장합니다.

STEP 2가 **EDA 보고서**예요. 프로파일링 결과를 바탕으로 변수 간 분포를 보고, 주요 패턴이랑 이상치를 정리해서 `02_eda_report.md`를 만들어요.

Aria는 데이터를 처음 만나는 에이전트예요. 다른 에이전트들이 Aria의 결과물을 기반으로 작업하기 때문에, 프로파일링이 꼼꼼할수록 이후 단계의 품질이 올라갑니다.

---

**Sam**은 STEP 3-4 담당이에요.

STEP 3이 **문제 정의**입니다. Aria가 EDA 보고서를 만들고 나면, Sam은 그 결과를 읽어서 "이 데이터가 어떤 비즈니스 문제에 쓸 수 있겠다"를 정리해요. `03_problem_definition.md`에 저장됩니다.

STEP 4가 **KPI 요약**이에요. 문제 정의를 바탕으로 어떤 지표를 봐야 할지, 어떻게 계산해야 할지를 정리해서 `04_kpi_summary.md`를 만들어요.

Sam이 중요한 이유가 있어요. Aria가 데이터의 현황을 보고했다면, Sam은 그걸 비즈니스 언어로 번역하는 역할이에요. 뒤에 Min이랑 Evan이 Sam의 KPI 정의를 기반으로 분석이랑 대시보드를 만들거든요. Sam이 KPI를 잘 정의할수록 최종 결과물 품질이 달라집니다.

---

**Min**은 STEP 5 담당이에요.

KPI 기반 **심층 분석이랑 인사이트 도출**입니다. Sam이 정리한 KPI를 실제 데이터에 적용해서 계산하고, 트렌드를 분석하고, 눈에 띄는 패턴이나 이상 신호를 찾아요. 결과는 `05_analysis_report.md`로 저장됩니다.

Min이 만드는 분석 보고서가 임원 보고서랑 대시보드의 원재료가 됩니다. 수치 계산이랑 해석은 Min이 다 해요.

---

**Evan**이 마지막 STEP 6-7이에요.

STEP 6이 **대시보드 제작**입니다. Min의 분석 결과를 받아서 HTML 대시보드를 만들어요. 차트 라이브러리 쓰고, 반응형 레이아웃 짜고, 브라우저에서 바로 열리는 `06_dashboard.html`을 생성합니다.

STEP 7이 **임원 보고서**예요. 전체 파이프라인 결과를 경영진이 읽기 좋게 정리한 `07_executive_report.md`를 만들어요. 수치만 나열하는 게 아니라, 배경 → 주요 발견 → 권고안 형식으로 정리됩니다.

Evan은 결과물의 마지막 포장을 담당하는 에이전트예요.

---

이 흐름을 정리하면 이렇습니다.

```
CSV 입력
  └→ Aria (STEP 1-2: 프로파일링 + EDA)
        └→ Sam (STEP 3-4: 문제 정의 + KPI)
              └→ Min (STEP 5: 심층 분석)
                    └→ Evan (STEP 6-7: 대시보드 + 임원 보고서)
                          └→ Echo가 텔레그램으로 결과 전송
```

순차적이에요. 앞 단계 결과물이 다음 단계의 입력이 됩니다. 파일로 넘어가기 때문에 중간에 하나가 실패해도 재시작할 수 있어요.

---

**AGENTS.md** 파일 이야기를 잠깐 할게요.

각 에이전트가 어떤 역할을 맡고, 어떤 파일을 만들어야 하는지는 AGENTS.md에 정의돼 있습니다.

Echo가 파이프라인을 시작할 때 이 파일을 먼저 읽어요. "Aria는 STEP 1-2 담당이고, 결과는 `01_dataset_profile.md`에 저장해야 한다." 이런 내용이 명시돼 있어요. Echo가 이걸 읽고 각 에이전트한테 지시를 내립니다.

이 AGENTS.md를 여러분이 직접 수정할 수 있어요. 예를 들어 KPI를 특정 지표로 고정하고 싶다면, Sam의 AGENTS.md에 "반드시 매출·전환율·ROAS를 포함할 것"이라고 추가하면 됩니다. 대시보드 색상이나 레이아웃을 바꾸고 싶다면 Evan의 AGENTS.md에 추가하면 되고요.

코드를 건드리지 않고 자연어로 에이전트 행동을 커스텀하는 방식이에요. 이 부분은 s37에서 다시 볼게요.

---

수동 작업이랑 비교해볼게요.

이 분석 파이프라인을 사람이 직접 하면 얼마나 걸릴까요? 데이터를 받아서 pandas로 EDA 돌리고, 결과 해석하고, 문제 정의 문서 쓰고, KPI 계산식 정리하고, 차트 그리고, 대시보드 HTML 짜고, 임원 보고서 쓰는 거예요. 빠른 사람도 반나절이에요. 데이터가 크거나 복잡하면 하루 이상 잡아야 합니다.

이 파이프라인을 돌리면 20-40분이면 끝납니다. 여러분이 하는 일은 CSV 하나 넣고 텔레그램으로 메시지 한 줄 보내는 게 전부예요.

## s21 — 크론 메시지가 대시보드를 만드는 방법 (5분)

**[화면: s21 슬라이드]**

자, 에이전트 구조를 봤으니까 이제 **언제, 어떻게 실행되는지** 흐름을 봅시다.

크론이라는 단어가 익숙하지 않으신 분도 있을 거예요. 그냥 **정해진 시간에 자동으로 뭔가를 실행하는 스케줄러**라고 생각하시면 됩니다. Linux·Mac에 기본으로 내장돼 있는 기능이에요. OpenClaw는 이 크론을 에이전트 메시지랑 연결해줘요.

흐름을 그려볼게요.

```
크론 트리거 (정해진 시간)
    ↓
Echo 에이전트에게 message 전송
    ↓
Echo가 메시지를 받아서 파이프라인 실행
    ↓
결과 완료 후 텔레그램으로 알림 전송
```

중요한 포인트가 있어요. 크론이 에이전트에게 보내는 건 **사람이 직접 보내는 채팅 메시지랑 완전히 같은 형식**입니다.

여러분이 텔레그램에서 Echo한테 "파이프라인 실행해줘."라고 보내는 거랑, 크론이 오전 9시에 자동으로 같은 메시지를 보내는 거랑 에이전트 입장에선 차이가 없어요. 둘 다 똑같이 처리됩니다.

이게 왜 중요하냐면, **별도의 API나 자동화 코드가 필요 없다**는 뜻이에요. 크론에 메시지 내용만 써두면 그걸 에이전트가 받아서 실행합니다.

---

매주 월요일 오전 9시에 대시보드가 만들어지는 흐름을 상상해보세요.

월요일 9시, 여러분은 아직 출근 준비 중이에요. OpenClaw 크론이 자동으로 Echo한테 메시지를 보냅니다. Echo가 파이프라인을 시작하고, 다섯 에이전트가 순서대로 작업해요. 40분쯤 후에 텔레그램으로 "파이프라인 완료. 생성된 파일: 01_dataset_profile.md, 02_eda_report.md ... 07_executive_report.md"라는 알림이 와요.

여러분은 출근해서 커피 한 잔 마시면서 06_dashboard.html을 열면 됩니다. 오전 보고 준비 완료예요.

이게 크론이랑 파이프라인을 연결했을 때 만들어지는 루틴이에요.

## s13 — 크론 스케줄 종류 (5분)

**[화면: s13 슬라이드]**

크론 스케줄 지정 방식이 두 가지예요. 상황에 따라 골라 쓰시면 됩니다.

---

첫 번째는 `--every`예요. **단순 주기**를 지정할 때 쓰는 방식입니다.

```bash
--every 1d    # 매일
--every 2h    # 2시간마다
--every 30m   # 30분마다
--every 1w    # 매주
```

숫자 + 단위로 써요. `d`는 day, `h`는 hour, `m`은 minute, `w`는 week입니다.

매일 한 번 전날 데이터 요약을 받고 싶다면 `--every 1d`를 쓰면 됩니다. 실시간성이 중요한 데이터라면 `--every 2h`로 2시간마다 돌릴 수도 있어요.

언제 실행되냐고요? `--every` 옵션은 등록한 시점부터 주기가 시작돼요. 오전 10시에 `--every 1d`로 등록하면 매일 오전 10시에 실행됩니다.

---

두 번째는 `--cron`이에요. **정확한 시간을 지정**하고 싶을 때 쓰는 방식입니다.

cron 표현식이라는 걸 씁니다. 처음 보면 좀 낯설 수 있는데, 패턴만 알면 읽기 어렵지 않아요.

```
형식: 분 시 일 월 요일
예시: 0 9 * * 1
      │ │ │ │ └── 요일 (1=월요일)
      │ │ │ └──── 월 (*=매월)
      │ │ └────── 일 (*=매일)
      │ └──────── 시 (9=오전 9시)
      └────────── 분 (0=0분)
```

`0 9 * * 1`은 "매주 월요일 오전 9시 0분"이에요.

자주 쓰는 패턴 몇 가지 알려드릴게요.

```bash
"0 9 * * 1"     # 매주 월요일 오전 9시
"0 8 * * 1-5"   # 평일 매일 오전 8시
"0 9 1 * *"     # 매월 1일 오전 9시
"30 17 * * 5"   # 매주 금요일 오후 5시 30분
```

월요일 오전 주간 보고라면 `0 9 * * 1`, 퇴근 전 일일 요약이라면 `30 17 * * 1-5` 이런 식으로요.

---

`--every`랑 `--cron` 중 어떤 걸 쓸지는 간단해요.

"며칠마다, 몇 시간마다"처럼 **간격**이 중요하면 `--every`를 쓰세요. "월요일 오전 9시에"처럼 **특정 시간**이 중요하면 `--cron`을 쓰세요.

비즈니스 루틴이라면 대부분 `--cron`이에요. 보고서는 특정 요일, 특정 시간에 만들어야 하거든요.

## s23 — 크론 message — 바로 쓸 수 있는 프롬프트 (5분)

**[화면: 터미널]**

프롬프트 작성법을 보기 전에, 왜 이게 중요한지 먼저 이야기할게요.

크론이 에이전트한테 보내는 메시지는 **여러분이 직접 써두는 텍스트**예요. 이 메시지를 에이전트가 받아서 그대로 실행하기 때문에, 메시지가 모호하면 에이전트가 엉뚱하게 동작할 수 있어요. 사람한테 지시할 때랑 똑같아요. 지시가 명확할수록 결과도 명확합니다.

---

프롬프트 작성 팁 세 가지예요.

**첫 번째, 파일 경로를 절대경로로 명시하세요.**

```bash
# 좋지 않은 예
--message "input 폴더에 있는 CSV로 파이프라인 실행해줘."

# 좋은 예
--message "~/Projects/openclaw-pipeline-kit/runs/latest/input/ 에 있는 CSV 파일로 /run-pipeline 을 실행하세요."
```

왜냐하면 크론은 특정 작업 디렉토리를 전제하지 않아요. 상대경로를 쓰면 어느 위치에서 실행되느냐에 따라 파일을 못 찾을 수 있습니다. 절대경로는 어디서 실행돼도 항상 같은 파일을 가리켜요.

---

**두 번째, 완료 조건을 명시하세요.**

```bash
# 완료 조건이 없는 예
--message "데이터 분석해줘."

# 완료 조건이 있는 예
--message "~/Projects/.../input/ CSV로 파이프라인 실행하세요. 완료 후 생성된 파일 목록을 알려주세요."
```

"완료 후 파일 목록 출력"처럼 끝내는 조건이 있어야 에이전트가 작업이 끝난 걸 인식하고 멈춥니다. 완료 조건이 없으면 에이전트가 계속 다음 작업을 찾거나, 응답 대기 상태에서 멈출 수 있어요.

---

**세 번째, 슬래시 명령어를 직접 넣으세요.**

```bash
--message "... /run-pipeline 을 실행하세요."
```

`/run-pipeline`처럼 Echo가 알아듣는 시작 문구를 프롬프트 안에 직접 넣어주세요. Echo의 AGENTS.md에 파이프라인 실행 순서가 정의돼 있어서, 시작 지시만 명확하면 나머지는 알아서 진행해요.

---

자, 실제 명령어를 터미널에 붙여넣겠습니다.

**[화면: 터미널]**

```bash
# 매주 월요일 오전 9시 — 주간 대시보드
openclaw cron add \
  --cron "0 9 * * 1" \
  --message "그룹 ID는 -XXXXXXXXXX야. 단톡방에서 Aria 불러서 파이프라인 시작해줘. CSV는 ~/Projects/openclaw-pipeline-kit/runs/latest/input/ 에 있어. 완료 후 생성된 파일 목록을 알려줘." \
  --agent main
```

따라해보세요. 복붙하셔도 됩니다.

등록이 되면 터미널에 성공 메시지가 뜹니다. 확인해볼게요.

```bash
openclaw cron list
```

등록된 크론 목록이 나와요. ID, 스케줄, 메시지 내용, 연결된 에이전트가 보입니다. 방금 등록한 항목이 있으면 정상이에요.

---

매일 오전 8시짜리 일일 요약 크론도 하나 더 등록해볼게요.

```bash
# 매일 오전 8시 — 일일 지표 요약
openclaw cron add \
  --every 1d \
  --message "~/Projects/openclaw-pipeline-kit/runs/latest/input/ 최신 파일 분석해서 지표 3개와 전일 대비 변화 요약해줘." \
  --agent main
```

이건 `--cron` 대신 `--every 1d`를 썼어요. 매일 실행하는데 특정 시간은 상관없는 경우예요.

---

활용 시나리오를 몇 가지 드릴게요. 여러분 상황에 맞게 응용하시면 됩니다.

**마케팅팀** 시나리오예요. 매주 월요일 오전 9시에 지난 주 광고 성과 CSV를 분석해서 채널별 ROAS, 전환율, 예산 소진율 대시보드를 만들어요. 팀장이 출근하기 전에 이미 대시보드가 준비돼 있는 거예요.

```bash
openclaw cron add \
  --cron "0 9 * * 1" \
  --message "~/data/marketing/weekly/ 최신 CSV로 /run-pipeline 실행. 채널별 ROAS·전환율·예산 소진율 포함한 대시보드 만들어줘. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

**IR팀** 시나리오예요. 매월 1일 오전 8시에 전월 재무 지표를 분석해요. 매출, 영업이익, 비용 구조 변화를 임원 보고서 형식으로 만들어줍니다.

```bash
openclaw cron add \
  --cron "0 8 1 * *" \
  --message "~/data/finance/monthly/ 최신 CSV로 /run-pipeline 실행. 매출·영업이익·비용 구조 분석 포함한 임원 보고서 만들어줘. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

**HR팀** 시나리오예요. 매월 첫째 월요일에 인력 현황 데이터를 분석합니다. 부서별 인원 변동, 이탈률, 채용 현황을 정리해줘요.

```bash
openclaw cron add \
  --cron "0 9 * * 1#1" \
  --message "~/data/hr/monthly/ 최신 CSV로 /run-pipeline 실행. 부서별 인원·이탈률·채용 현황 분석해줘. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

**영업팀** 시나리오예요. 평일 매일 오전 8시에 전일 영업 실적을 분석해요. 지역별, 담당자별 목표 달성률이랑 파이프라인 현황을 매일 아침 받아봅니다.

```bash
openclaw cron add \
  --cron "0 8 * * 1-5" \
  --message "~/data/sales/daily/ 최신 CSV로 /run-pipeline 실행. 지역별·담당자별 목표 달성률 분석. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

**1인 사업자** 시나리오예요. 주간 정산 데이터나 구글 애널리틱스 export CSV를 넣어두면, 매주 월요일에 트래픽·전환·수익 요약이 텔레그램으로 와요. 별도 분석 툴 없이도 주간 현황을 파악할 수 있습니다.

```bash
openclaw cron add \
  --cron "0 9 * * 1" \
  --message "~/data/business/weekly/ 최신 CSV로 /run-pipeline 실행. 트래픽·전환·수익 주간 요약 만들어줘. 완료 후 파일 목록 알려줘." \
  --agent main
```

---

공통점이 보이시나요? 절대경로, `/run-pipeline`, 완료 조건. 이 세 가지가 항상 들어가 있어요. 이 패턴을 그대로 쓰시면서 파일 경로랑 분석 요구사항만 바꾸시면 됩니다.

## s14 — /run-pipeline 자동 실행 연동 (6분)

**[화면: 텔레그램 + 터미널]**

자, 크론 설정이 됐으니까 이제 실제로 파이프라인이 어떻게 실행되는지 보겠습니다.

지금은 크론이 오전 9시를 기다리는 게 아니라, **텔레그램에서 직접 메시지를 보내서** 동일한 흐름을 체험해볼 거예요. 크론이 자동으로 보내는 메시지나 여러분이 직접 보내는 메시지나 에이전트 입장에선 똑같이 처리됩니다.

텔레그램 Echo 봇 DM을 열어주세요. 그리고 터미널도 옆에 띄워두세요. 두 화면을 같이 보면서 진행할 겁니다.

---

텔레그램에 이 메시지를 그대로 복붙해서 보내세요.

```
그룹 ID는 -XXXXXXXXXX야.
단톡방에서 Aria 불러서 파이프라인 시작해줘.
CSV는 ~/Projects/openclaw-pipeline-kit/runs/latest/input/ 에 있어.
```

## s31 — 디자인 토큰으로 대시보드 퀄리티 올리기

**[화면: 슬라이드]**

방금 Evan이 만든 `06_dashboard.html`을 열어봤죠. 클립 마무리 전에, 이 대시보드 퀄리티를 한 단계 더 올리는 방법을 알려드릴게요.

대시보드를 브라우저에서 열면 데이터는 다 있는데 뭔가 허전한 느낌이 들 때가 있습니다. 색이 일관되지 않거나, 버튼 스타일이 제각각이거나, 다크 모드가 없거나.

그 허전함을 채우는 방법이 두 가지 있습니다.

**PATH A는 키트 그대로 실행**이에요. 가장 빠른 방법입니다. 레포를 클론하고 `bash setup.sh`를 실행하고 파이프라인을 한 번 돌리면 5분 안에 완성된 대시보드가 나와요. 실습할 때는 이 방법으로 따라하시면 됩니다.

Evan 에이전트가 이미 좋은 품질의 대시보드를 만들도록 셋업돼 있어요. Evan의 AGENTS.md에 디자인 시스템 가이드가 들어있고, 에이전트가 그 가이드를 보고 대시보드를 작성합니다.

**PATH B는 처음부터 만들기**예요. 자기 브랜드에 맞는 색상 시스템을 적용하고 싶을 때 쓰는 방법입니다.

GitHub 링크 하나를 Claude Code 프롬프트에 붙여넣으면 돼요.

링크는 `github.com/material-foundation/material-tokens`입니다. 구글이 만든 **Material Design 3** 공식 디자인 토큰 레포예요.

Material Design 3가 뭔지 간단하게 설명할게요. 구글이 Android, Gmail, YouTube 같은 제품에 적용하는 디자인 시스템이에요. 여기서 "토큰"이란 색상, 크기, 간격 같은 디자인 값들을 이름 붙여서 변수로 관리하는 방식이에요. 하드코딩 대신 변수를 쓰는 거죠.

예를 들어, 이전에 대시보드를 만들 때 배경색을 `#F9FAFB`라고 직접 썼다면, 토큰 방식에서는 `--md-sys-color-surface`라는 변수를 써요. 이 변수가 `#F9FAFB`를 가리키고 있는 거예요.

이게 왜 좋냐면, 나중에 배경색을 바꾸고 싶을 때 `--md-sys-color-surface` 하나만 수정하면 대시보드 전체에 반영됩니다. 100군데에 써있는 `#F9FAFB`를 하나씩 찾아서 바꿀 필요가 없어요.

이 레포 링크를 Claude Code에 주면 CSS 변수 시스템을 자동으로 생성해줍니다. 프롬프트는 이렇게 쓰면 돼요.

```
이 레포의 CSS 토큰 구조를 참고해서 대시보드에 적용해줘.
:root에 MD3 시맨틱 컬러 변수 정의하고,
하드코딩된 색상을 전부 토큰으로 교체하고,
다크 모드도 추가해줘.
```

이게 전부예요. Claude Code가 실행되면 어떻게 되는지 설명할게요.

먼저 `:root` 블록에 시맨틱 컬러 변수들이 정의됩니다.

```css
:root {
  --md-sys-color-primary: #3182F6;
  --md-sys-color-surface: #F9FAFB;
  --md-sys-color-on-surface: #191F28;
  --md-sys-color-outline: #E5E8EB;
  /* ... */
}
```

그 다음에 대시보드 코드에서 하드코딩된 색상들이 전부 변수로 교체됩니다. `background: #F9FAFB`가 `background: var(--md-sys-color-surface)`로 바뀌는 식이에요.

마지막으로 다크 모드 CSS가 추가됩니다.

```css
@media (prefers-color-scheme: dark) {
  :root {
    --md-sys-color-primary: #6BA4FA;
    --md-sys-color-surface: #1A1D21;
    --md-sys-color-on-surface: #E2E4E8;
    --md-sys-color-outline: #2E3138;
  }
}
```

라이트 모드에서 쓰던 변수 이름 그대로인데, 값만 바뀌었어요. OS가 다크 모드로 설정돼 있으면 이 값들이 자동으로 적용됩니다. 대시보드 코드는 그대로인데 다크 모드가 생기는 거예요.

이렇게 하면 나중에 브랜드 색상이 바뀌어도 `:root` 블록에서 `--md-sys-color-primary` 하나만 수정하면 대시보드 전체 색이 바뀝니다.

PATH A와 PATH B, 두 방법 모두 같은 결과가 나와요. 원리를 이해하면 내 브랜드에 맞게 커스텀할 수 있어요. 처음에는 PATH A로 빠르게 따라하고, 나중에 자기 프로젝트에 적용할 때 PATH B 방법을 써보시길 권합니다.
