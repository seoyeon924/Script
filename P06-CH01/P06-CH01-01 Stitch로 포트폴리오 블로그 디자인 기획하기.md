## s1 — 챕터 표지

**[화면: 챕터 표지]**

안녕하세요. Part 6 시작합니다.

지금까지 여러분은 데이터를 다루는 방법, 시각화하는 방법, 대시보드를 만드는 방법을 배웠습니다. 그런데 한 번 생각해보세요. 여러분이 지금까지 만든 대시보드들, 분석 결과들, 그게 지금 어디 있나요?

로컬 파일 폴더에 있거나, Tableau Public에 올라가 있거나, 기껏해야 GitHub에 코드가 올라가 있을 거에요.

그게 문제입니다. 취업 준비나 이직 준비를 하다 보면, 면접관이 "작업물 보여주세요"라고 했을 때 링크 하나를 줘야 하는데, 흩어져 있는 파일들을 하나하나 보내거나 Tableau Public 링크 여러 개를 보내는 게 전부인 경우가 많아요.

이게 아쉬운 이유가 뭐냐면, **맥락이 없기 때문**입니다. 이 대시보드를 왜 만들었는지, 어떤 인사이트를 발견했는지, 어떤 과정을 거쳐서 만들었는지 — 이 이야기를 같이 보여줄 공간이 없는 거에요.

그래서 이번 챕터에서는 포트폴리오 블로그를 처음부터 만들어서 실제로 공개 URL로 배포하는 전 과정을 함께 합니다.

도구는 세 가지입니다. 첫 번째는 Google이 만든 AI 디자인 툴인 **Stitch**로 블로그 UI를 기획하고요. 두 번째는 **Claude Code**와 **Notion MCP**로 실제 동작하는 페이지를 빌드합니다. 세 번째는 **Netlify**로 배포해서 공개 URL을 만듭니다.

기술 스택은 React + Vite + TypeScript이고 Notion을 CMS로 씁니다. 이걸 처음 들으시는 분들도 걱정 안 하셔도 됩니다. 코딩을 직접 하는 게 아니라, 프롬프트를 이용해서 AI가 코드를 짜게 하는 과정입니다.

이번 챕터 끝나면 여러분은 두 가지를 갖게 됩니다. 하나는 여러분의 이름이 붙은 공개 URL의 포트폴리오 블로그. 그리고 또 하나는 Notion에서 글을 쓰면 그게 자동으로 블로그에 올라가는 자동화 파이프라인입니다.

자 그럼 시작해보겠습니다.

## s2 — CLIP 01 섹션 브레이크

**[화면: Clip 01 섹션 브레이크]**

첫 번째 클립입니다. Stitch로 블로그 디자인을 기획하는 내용이에요.

잠깐, 왜 코딩부터 시작하지 않고 디자인부터 시작하냐고 물어보시는 분들이 있을 거에요.

경험상 디자인 없이 코드부터 짜기 시작하면, Claude Code한테 "포트폴리오 블로그 만들어줘"라고 입력하는 순간, AI가 자기 나름의 디자인을 만들어버립니다. 그게 마음에 안 들면 "다시 해줘", "색상 바꿔줘", "레이아웃 바꿔줘"를 반복하다가 정작 내용은 못 채우는 상황이 생겨요.

반면에 Stitch로 먼저 시안을 뽑아놓으면, Claude Code한테 "이 디자인처럼 만들어줘"라고 구체적인 레퍼런스를 줄 수 있습니다. 결과물의 품질이 훨씬 높아지고, 수정 횟수가 줄어듭니다.

Stitch는 Google이 만든 AI 디자인 툴인데요. 텍스트로 원하는 화면을 묘사하면 실제 HTML, CSS를 즉시 생성해줍니다. 디자이너가 아니어도, Figma를 다룰 줄 몰라도 됩니다. 어떻게 생긴 화면을 원하는지 말로만 설명할 수 있으면 충분합니다.

## s3 — 전체 빌드 워크플로우

**[화면: 4단계 워크플로우]**

본격적으로 들어가기 전에 전체 흐름을 한 번 보고 가겠습니다. 지도 없이 산에 들어가면 안 되니까요.

총 4단계로 구성되어 있습니다.

**Step 1 — 디자인 기획**입니다. Stitch에 원하는 느낌을 텍스트로 입력하면, 블로그 UI 시안을 여러 개 생성해줍니다. 색상, 레이아웃, 컴포넌트 배치까지 한 번에 나옵니다. 이 단계에서 목표는 "어떻게 생긴 블로그를 만들 건지" 방향을 잡는 겁니다. 완벽하지 않아도 됩니다. 방향만 잡으면 돼요.

**Step 2 — 코드 빌드**입니다. 제가 미리 만들어둔 실습 키트 파일인 `portfolio-blog-kit.html`을 시작점으로 씁니다. 이 파일은 홈, 블로그, 사이드바가 이미 구현되어 있는데요. Claude Code에 프롬프트를 넣어서 여러분 이름, 역할, 색상, 카테고리로 커스터마이징합니다.

**Step 3 — 콘텐츠 연결**입니다. Notion 데이터베이스를 CMS로 씁니다. CMS는 Content Management System의 약자인데, 쉽게 말하면 "글 관리 도구"입니다. Notion에서 글을 쓰면 웹사이트에 자동으로 반영되는 구조를 만듭니다. Notion MCP를 활용해서 Claude Code가 Notion API 연동 코드를 직접 작성하게 합니다.

**Step 4 — 배포**입니다. 코드를 GitHub에 push하면 Netlify가 자동으로 감지하고 빌드해서 배포합니다. 한 번만 설정해두면 그 이후는 git push 하나로 전체 파이프라인이 자동으로 돌아가요.

맨 아래에 나와 있듯이, 이 전체 과정에서 개발 경험은 필요 없습니다. 여러분이 하는 건 프롬프트 입력하는 것뿐입니다.

한 가지 더 말씀드리고 싶은 게 있는데요. 이 워크플로우는 "빠르게 뭔가 만들어서 올리는 것"보다, **처음부터 제대로 된 구조를 만드는 것**에 초점을 맞췄습니다. 처음에 구조를 잘 잡아두면 나중에 글 하나 추가하는 게 몇 초면 됩니다. 반면 처음에 대충 만들면 나중에 수정할 때마다 코드를 건드려야 해서 귀찮아집니다.

자, 그럼 Step 1부터 시작해보겠습니다.

## s4 — 포트폴리오 블로그 필요성

**[화면: 포트폴리오 블로그 — 3가지 이유]**

왜 포트폴리오 블로그가 필요한지 조금 더 이야기해보겠습니다. 이게 단순히 "있으면 좋은 것"이 아니라는 걸 먼저 이해하고 시작해야 해요.

지금 데이터 분석가나 데이터 사이언티스트를 채용하는 회사들이 이력서에서 가장 많이 보는 게 뭔지 아세요? 기술 스택도 보지만, 실제로 "이 사람이 데이터로 어떤 결과를 만들어냈나"를 보고 싶어합니다.

그런데 이력서 한 장에 그걸 다 담기가 어렵죠. 그래서 포트폴리오 링크를 따로 첨부하는 경우가 늘고 있습니다.

자, 지금 여러분이 갖고 계신 걸 생각해보세요.

Tableau Public에 올린 대시보드 몇 개, GitHub 레포지토리에 올린 Python 코드, 로컬 컴퓨터에만 있는 Excel 파일... 이게 전부인 분들이 많을 거에요.

이게 문제인 이유는 **한 곳에서 볼 수 없다는 것**입니다. 면접관이 여러분의 작업물을 보고 싶을 때, 링크 다섯 개를 따로 보내야 한다면 불편합니다. 그리고 각각의 링크에는 "왜 이걸 만들었는지"가 없어요.

반면에 포트폴리오 블로그가 있으면 어떻게 되냐면, 링크 하나를 공유하면 됩니다. 들어가면 여러분이 어떤 사람인지, 어떤 프로젝트를 했는지, 분석 과정에서 어떤 생각을 했는지가 한 곳에 다 모여 있어요.

국내에서도 개발자나 디자이너는 이미 이런 문화가 많이 자리를 잡았습니다. Velog라는 플랫폼에 가보시면 개발자들이 기술 블로그를 운영하면서 자신의 학습 과정을 기록하고, 그게 포트폴리오 역할을 하는 경우를 많이 볼 수 있어요. 취업 스터디 커뮤니티에서도 "Velog 있는 사람이 우대"라는 말이 나올 정도입니다.

데이터 분석가도 마찬가지가 되어가고 있어요. 분석한 것들을 블로그 형태로 정리하고, 이걸 공개적으로 운영하는 분들이 점점 늘고 있습니다.

그런데 Velog나 Tistory 같은 기존 블로그 플랫폼이랑 비교해서 이번에 만들 블로그가 뭐가 다르냐면요.

첫 번째로, **완전히 커스터마이징이 가능합니다.** Velog는 이미 만들어진 틀 안에서만 꾸밀 수 있어요. 이번에 만드는 건 색상, 레이아웃, 폰트, 컴포넌트 전부 여러분이 원하는 대로 설계할 수 있습니다. 다른 사람들이랑 완전히 다른 모습의 블로그를 가질 수 있어요.

두 번째로, **Works 섹션이 있습니다.** 기술 블로그는 글만 쓰는 플랫폼인데요. 이번에 만드는 건 Home 화면에 Works 그리드가 있어서 여러분이 만든 대시보드나 프로젝트를 이미지 카드 형태로 보여줄 수 있어요. 포트폴리오 사이트와 블로그가 합쳐진 형태입니다.

세 번째로, **Notion으로 글을 관리합니다.** Notion은 여러분이 이미 쓰고 계신 분들이 많을 거에요. 복잡한 CMS 어드민 화면을 배울 필요 없이, 평소처럼 Notion에 글을 쓰면 자동으로 블로그에 반영됩니다.

**[화면: https://www.youtube.com/watch?v=Q43pPgw5ZpI]**

이 영상부터 보겠습니다. 제목이 "비전공자였던 내가 대기업 데이터 분석가로 취업할 수 있었던 이유"입니다.

물류학과 출신 분인데요. 4개월 만에 롯데이노베이트 데이터 분석가로 입사하셨습니다. 댓글이 수백 개인데, 지금 여러분이랑 비슷한 처지에 있는 분들이 많이 봐요.

이 영상에서 강조하는 게 뭐냐면, 이 분이 취업에 성공한 결정적인 이유 중 하나가 **포트폴리오였습니다.** 단순히 "대시보드 만들어봤어요"가 아니라, "이 문제를 이렇게 분석해서 이런 인사이트를 냈습니다"라는 맥락 있는 포트폴리오가 있었던 거에요.

영상에서 직접 언급하는 포트폴리오 팁들:
- 프로젝트마다 비즈니스 문제 정의부터 시작
- 분석 과정에서 막혔던 부분과 해결 방법도 기록
- Tableau Public 링크만 올리는 것보다 블로그에 맥락 설명 추가

이 영상에서 제가 주목한 부분이, 포트폴리오가 있는 것과 없는 것의 차이가 생각보다 크다는 거에요. 실력이 같아도 보여줄 수 있는 게 있는 사람이 면접에서 더 할 말이 많아집니다.

**[화면: https://velog.io/@lucia/의료-분야-데이터-사이언티스트-취업-후기]**

다음은 Velog 취업 후기입니다. 정치외교학과 출신 분이 AI·의료 분야 데이터 사이언티스트로 커리어를 전환한 이야기에요.

Velog를 보면, 좌측에 "시리즈"라는 게 있는데요. 이 분은 자신의 학습 과정 전체를 시리즈로 정리해두셨어요. "분석가로 가는 길", "데이터 공부 기록" 같은 시리즈로요.

여기서 봐야 할 게 뭐냐면, Velog 자체의 폰트 크기, 레이아웃은 다 똑같잖아요. 모든 Velog 블로그가 거의 비슷하게 생겼어요. 그게 단점입니다. "나"가 없어요.

그래서 우리는 이번에 개인 블로그를 만드는 겁니다. Velog에 올리는 글이랑 완전히 다른 차별화가 생기는 거에요. 색상, 레이아웃, Works 섹션, 전부 다 내 것으로.

---

**[화면: https://github.com/suy379/Portfolio_sy]**

마지막으로 GitHub에 올라온 포트폴리오 사례입니다. 데이터 분석가를 준비 중인 분의 포트폴리오 레포인데요.

GitHub에서 이렇게 프로젝트 목록이 README로 정리된 포트폴리오도 많이 볼 수 있어요. 분류 모델링, 관광지 분석, 통계 분석 같은 프로젝트들이 폴더별로 정리되어 있습니다.

이 방식의 장점은 코드까지 다 볼 수 있다는 거고요. 단점은 **비주얼이 없습니다.** 대시보드 이미지, 분석 결과 차트 같은 걸 GitHub README에 넣을 수 있긴 한데, 블로그 형태에 비해 훨씬 투박합니다.

결국 Velog랑 GitHub 포트폴리오 각각의 장점을 합쳐놓은 게 우리가 만드는 블로그에요. 블로그 글 부분은 Velog처럼 읽히고, Works 그리드는 GitHub 프로젝트들을 카드로 보여주는 형태입니다.

---

국내 데이터 분석 관련 커뮤니티나 채용 공고들을 보면, 포트폴리오 블로그를 운영하는 분들이 공통적으로 몇 가지 콘텐츠를 올립니다.

**첫 번째가 프로젝트 케이스 스터디입니다.** "이커머스 데이터로 구매 패턴 분석했더니 이런 인사이트가 나왔다"는 식으로, 어떤 데이터로 어떤 문제를 풀었는지 과정을 상세하게 씁니다. 코드도 넣고, 시각화 결과도 넣고, 인사이트 해석도 씁니다.

**두 번째가 대시보드 소개입니다.** Tableau나 Looker Studio로 만든 대시보드를 소개하면서, 왜 이 차트를 선택했는지, 어떤 지표를 보여주려 했는지, 어떤 의사결정을 지원하는 대시보드인지를 설명합니다. 대시보드만 올리는 것보다 맥락이 훨씬 풍부해집니다.

**세 번째가 학습 기록입니다.** 강의 수강 후기, 책 정리, 새로운 툴을 써보고 느낀 점. 이런 것들을 꾸준히 올리면, 이 사람이 어떤 방향으로 성장하고 있는지가 보입니다.

이 세 가지가 잘 갖춰진 포트폴리오 블로그는 이력서보다 훨씬 강력한 자기소개 도구가 됩니다.

---

그럼 이번에 만들 블로그가 실제로 이런 역할을 할 수 있게, 구조를 잘 설계하는 것부터 시작해야겠죠. 디자인 기획은 그래서 중요합니다. 나중에 글 쓸 때 불편하지 않도록, 처음 구조를 잘 잡아두는 거에요.

---

## s5 — Stitch 소개

**[화면: Stitch 메인화면]**

자 이제 Stitch를 살펴보겠습니다.

stitch.withgoogle.com 에서 접속할 수 있습니다. 구글 계정으로 로그인하시면 됩니다.

처음 들어가시면 왼쪽에 채팅 인터페이스가 있고, 오른쪽에 캔버스가 있는 구조입니다. 익숙한 분들은 Claude나 ChatGPT 인터페이스와 비슷하다고 느끼실 거에요. 텍스트로 원하는 것을 입력하면, 오른쪽 캔버스에 결과물이 생성됩니다.

지금 슬라이드에 보이는 화면이 실제 Stitch 메인 UI입니다. 여기서 기억하실 게 세 가지에요.

첫 번째, **디자인 경험이 필요 없습니다.** Figma 다룰 줄 몰라도 됩니다. Photoshop 몰라도 됩니다. "어두운 배경에 흰색 텍스트, 좌측에 사이드바, 우측에 블로그 포스트 카드 그리드" 이런 식으로 원하는 것을 글로 묘사하면 됩니다.

두 번째, **레이아웃, 컬러, 컴포넌트 구조를 자동으로 설계해줍니다.** 어디에 뭘 배치할지, 버튼 색상은 어떻게 할지, 폰트는 뭘 쓸지를 AI가 알아서 제안합니다. 그 중에서 마음에 드는 걸 고르면 돼요.

세 번째, **결과물을 Claude Code 프롬프트의 레퍼런스로 씁니다.** Stitch가 만들어준 시안 자체를 최종 결과물로 쓰는 게 아니에요. "이 디자인 느낌으로 만들어줘"라고 말할 수 있는 레퍼런스를 만드는 겁니다. 이게 중요한 포인트입니다. Stitch는 기획 도구, Claude Code가 실제 빌드 도구라고 생각하시면 됩니다.

---

### 🖥️ [화면 전환: Stitch 소개 영상 + 공식 블로그]

Stitch를 처음 접하시는 분들을 위해, 다른 사람들이 어떻게 쓰고 있는지 먼저 보여드릴게요.

---

**[화면: https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-ai-ui-design/]**

구글 공식 블로그에 Stitch 소개 글이 올라와 있어요. 제목이 "Introducing 'vibe design' with Stitch"입니다.

**"Vibe design"**이라는 단어가 재미있어요. 우리가 이미 알고 있는 "Vibe coding"에서 나온 말인데요. Vibe coding이 "분위기로 코딩한다"는 거잖아요 — 코드를 일일이 짜는 게 아니라 원하는 분위기와 기능을 말로 설명하면 AI가 만들어주는 거. Vibe design은 그것의 디자인 버전입니다.

이 글에서 구글이 강조하는 게 뭔지 보면, "이전에는 디자이너가 Figma로 UI를 그리고, 개발자가 코드로 구현하는 두 단계가 필요했다. Stitch는 이 두 단계를 하나로 합친다"고 설명합니다.

우리 강의에서 하는 것과 완전히 같은 개념이에요. 디자인하고 코드 짜는 과정을 AI가 다 해주는 거니까요.

---

**[화면: https://www.youtube.com/watch?v=COWMtnKjolM]**

이 유튜브 영상은 초보자용 Stitch 튜토리얼입니다. 자동차 딜러십 앱 UI를 만드는 과정인데요.

제가 이 영상에서 주목하라고 하고 싶은 게, 처음 프롬프트 입력하는 부분이에요. 영상 앞부분에 나오는데요. 프롬프트가 굉장히 짧아요. "자동차 딜러십 모바일 앱, 어두운 테마, 전문적인 느낌" 이 정도입니다.

결과물 보면 놀라울 정도로 잘 나와요. 프롬프트가 짧아도 방향만 맞으면 충분히 괜찮은 결과가 나온다는 걸 보여주는 사례입니다.

우리가 쓸 프롬프트는 이것보다 조금 더 구체적으로 쓸 거에요. 그러면 훨씬 더 원하는 방향에 가까운 결과가 나옵니다.

---

**[화면: https://www.youtube.com/watch?v=gOmw6gH2b28]**

이건 조금 더 전문적인 튜토리얼 영상이에요. 몇 분만에 모바일 앱 UI를 만드는 전체 과정을 보여주는데요.

특히 이 영상에서 Annotate 기능 쓰는 부분이 나와요. 캔버스에서 특정 영역을 선택하고 거기만 수정하는 과정이요. 우리가 s6에서 설명했던 STEP 4 "세부 수정 반복"이 실제로 어떻게 작동하는지 볼 수 있어요.

영상을 다 보실 필요는 없고요. 여러분이 Stitch 써보다가 "어떻게 쓰는지 다시 보고 싶다"라고 느낄 때 참고하시면 됩니다.

---

**[화면: https://medium.com/google-cloud/how-i-overhauled-my-app-ui-in-minutes-with-stitch-and-ai-studio-524b965c3d45]**

마지막으로 이 Medium 글인데요. 실제로 프로덕션 앱의 UI를 Stitch로 개선한 경험담입니다.

제가 이 글에서 재미있다고 생각한 부분이 있어요. 이 사람이 기존에 있던 앱의 UI가 "기능적으로는 작동하지만 보기 좋지 않았다"고 하는데요. 그래서 Stitch로 새 시안을 만들고, 그걸 기반으로 실제 코드를 업데이트했습니다. 몇 분 만에요.

이게 우리가 하려는 것과 완전히 같은 과정이에요. Stitch로 "어떻게 생겨야 하는지" 방향을 잡고, Claude Code로 실제 코드를 만드는 거요.

---

여기서 많이 물어보시는 게, "v0.dev이나 bolt.new 같은 유사 도구들이 많은데 왜 Stitch를 쓰냐"는 거에요.

비교해드릴게요.

**v0.dev**는 Vercel에서 만든 도구인데요. React 컴포넌트를 바로 생성해주는 데 특화되어 있습니다. 개발자가 코드를 직접 쓸 때 좋은데, 우리처럼 디자인 시안을 빠르게 여러 개 보고 싶을 때는 조금 복잡할 수 있어요.

**bolt.new**는 풀스택 앱을 바로 만들어주는 도구라서, 오히려 너무 많이 해줘서 우리 용도에 안 맞아요. 우리는 Claude Code로 직접 빌드할 거라서 Stitch가 코드를 다 만들어버리면 오히려 불필요합니다.

**Stitch**는 UI 디자인 시안에 집중된 도구라서, 우리 워크플로우에 딱 맞습니다. 여러 스타일을 한 번에 뽑아볼 수 있고, 특정 영역을 선택해서 수정할 수 있는 Annotate 기능이 있습니다.

그리고 Google이 만들었다는 게 장점인데요. Google Material Design 가이드라인이 기반에 깔려 있어서 기본적으로 정돈된 느낌이 나옵니다.

## s6 — Stitch 디자인 프로세스

**[화면: 레퍼런스 → 대량 생성 → 선택 → 수정 / 오른쪽 결과 화면]**

실제로 어떻게 쓰는지 프로세스를 하나하나 보겠습니다. 4단계입니다.

**STEP 1 — 레퍼런스 첨부**

프롬프트를 그냥 텍스트로만 쓰는 것보다, 레퍼런스 이미지를 첨부하면 훨씬 원하는 방향에 가까운 결과가 나옵니다.

마음에 드는 블로그나 포트폴리오 사이트를 하나 찾아서 스크린샷을 찍으세요. 그걸 📎 아이콘으로 첨부하고, "이 디자인을 참고해서 데이터 분석가 포트폴리오 블로그 만들어줘"라고 입력합니다.

레퍼런스 찾는 게 막막하신 분들을 위해 몇 가지 참고할 만한 곳을 알려드릴게요.

**Awwwards.com**에 가시면 전 세계 디자이너들이 만든 웹사이트 중 수상작들이 모여 있습니다. 포트폴리오, 에이전시 사이트, 개인 블로그 카테고리로 나눠서 볼 수 있어요. 이 중에서 마음에 드는 거 스크린샷 찍으시면 됩니다.

**Dribbble.com**은 디자이너들이 자신의 작업물을 공유하는 플랫폼인데요. "portfolio website design"으로 검색하시면 다양한 레이아웃 아이디어를 볼 수 있어요.

아니면 그냥 본인이 평소에 "이런 느낌이다"라고 느끼신 웹사이트 화면을 캡처해서 쓰셔도 됩니다.

---

프롬프트 작성할 때 팁을 하나 드릴게요.

나쁜 프롬프트의 예시를 보여드릴게요.

```
포트폴리오 블로그 만들어줘
```

이렇게만 쓰면 AI가 너무 광범위하게 해석합니다. 어떤 분위기인지, 어떤 사람을 위한 건지, 어떤 구조인지가 하나도 없어요. 결과물이 나와도 내가 원하는 것과 다를 가능성이 높습니다.

좋은 프롬프트는 이렇게 씁니다.

```
첨부한 레퍼런스를 참고해서
데이터 분석가를 위한 포트폴리오 블로그를 만들어줘.

분위기: 미니멀하고 전문적인 느낌. 너무 화려하지 않게.
배경: 밝은 베이지 또는 오프화이트
강조색: 산호색 또는 테라코타 계열
레이아웃: 좌측에 고정된 사이드바, 우측에 콘텐츠

포함할 섹션:
- 사이드바: 프로필 사진, 이름, 역할, 소개 태그 3개, 메뉴
- Home: 히어로 타이틀, Works 그리드 4열, 최신 블로그 포스트 3개
- Blog: 상단 카테고리 필터, 카드 그리드

폰트는 한국어 지원되는 깔끔한 Sans-serif로
```

이렇게 쓰면 결과물이 훨씬 원하는 방향으로 나옵니다. **분위기 형용사, 색상 방향, 레이아웃 구조, 섹션 목록**을 명시해주는 게 포인트입니다.

---

### 🖥️ [화면 전환: Stitch 직접 접속]

자, 이제 직접 Stitch를 열어보겠습니다.

**[화면: https://stitch.withgoogle.com/]**

지금 보시는 게 Stitch 메인 화면이에요. Google 계정으로 로그인하면 바로 쓸 수 있습니다. 별도 설치 없고, 브라우저에서 바로 됩니다.

로그인하면 왼쪽에 프롬프트 입력창이 있고, 오른쪽에 캔버스가 있어요. 처음에는 캔버스가 비어 있습니다.

화면 상단에 보시면 몇 가지 버튼이 있어요. "Ideate"와 "Build" 모드가 있는데요. Ideate는 여러 시안을 한 번에 뽑는 모드고, Build는 하나의 결과물을 점진적으로 수정하는 모드입니다. 우리는 Ideate를 먼저 쓸 거에요.

프롬프트 입력창 아래를 보시면 📎 클립 아이콘이 있어요. 이게 레퍼런스 이미지 첨부 버튼입니다. 이걸 클릭해서 스크린샷을 첨부하는 거에요.

지금 제가 직접 프롬프트를 넣어보겠습니다. 실제로 결과가 어떻게 나오는지 보시면서 따라오세요.

---

**STEP 2 — 여러 테마 한번에 생성**

이게 Stitch에서 제가 가장 유용하게 쓰는 기능인데요.

Stitch에는 Ideate 모드와 Variations 모드가 있습니다.

**Ideate 모드**는 같은 프롬프트로 여러 가지 다른 스타일의 결과를 한 번에 뽑아줍니다. 한 번에 10개, 20개도 생성할 수 있어요. 하나씩 생성하고 "이거 마음에 안 드니까 다시"를 반복하는 것보다, 처음부터 20개를 뽑아놓고 그 중에서 마음에 드는 걸 고르는 게 훨씬 빠릅니다.

**Variations 모드**는 이미 만들어진 결과물에서 "이 방향으로 변형된 버전 여러 개를 보여줘"라고 할 때 씁니다. 큰 방향은 정했는데 세부 스타일을 더 다양하게 보고 싶을 때 유용합니다.

실제로 제가 쓸 때는 이렇게 합니다.

처음에 프롬프트 입력하고 Ideate 모드로 15-20개를 한 번에 뽑습니다. 캔버스에 결과물들이 나란히 깔리면, 전체적으로 훑어보면서 "어 이 방향이 마음에 드네, 저건 좀 아니다" 하면서 걸러냅니다. 처음에 20개에서 5개 정도로 줄이고, 그 5개 중에서 최종 2-3개를 추려냅니다.

이렇게 하면 시간이 얼마나 걸리냐면, 빠르면 15-20분 안에 방향을 잡을 수 있어요. 혼자서 색상 고르고 레이아웃 고민하면 하루도 걸릴 수 있는 작업이, AI를 쓰면 20분입니다.

---

**STEP 3 — 비교하며 선택**

결과물들이 캔버스에 나란히 펼쳐지면, 이제 비교해서 고릅니다.

볼 때 체크하실 게 몇 가지 있어요.

첫 번째, **전체적인 분위기가 내가 원하는 방향인가.** 너무 화려하거나, 너무 단순하거나, 색이 이상하거나 이런 걸 먼저 걸러냅니다.

두 번째, **레이아웃 구조가 실용적인가.** 사이드바 위치는 어디인지, 블로그 카드는 어떤 형태인지, 모바일에서도 볼 만한지를 봅니다. 너무 독특한 레이아웃은 나중에 Claude Code로 구현할 때 복잡할 수 있어요. 심플한 구조가 낫습니다.

세 번째, **Works 섹션과 Blog 섹션이 모두 표현되어 있는가.** 우리가 만들 블로그에는 포트폴리오 Works 그리드가 있어야 합니다. 이게 잘 표현된 시안을 선택하세요.

이렇게 고른 시안을 스크린샷으로 저장해둡니다. 나중에 Claude Code 프롬프트에 첨부할 거에요.

---

**STEP 4 — 세부 수정 반복**

방향을 잡은 시안이 있으면, 이제 세부를 다듬습니다.

Stitch에는 **Annotate 기능**이 있습니다. 캔버스에서 특정 영역을 드래그해서 선택하면, 그 부분만 따로 수정 지시를 줄 수 있어요.

예를 들어 전체적인 레이아웃은 마음에 드는데 헤더 색상만 바꾸고 싶다면, 헤더 영역을 드래그해서 선택하고 "헤더 배경색을 더 어둡게, 네이비 계열로 바꿔줘"라고 입력합니다. 전체 시안을 다시 만드는 게 아니라, 그 부분만 수정됩니다.

Annotate 활용 예시들을 보여드릴게요.

```
[사이드바 영역 선택] 
→ "사이드바 배경을 흰색이 아니라 매우 밝은 회색으로, 
    그리고 구분선을 더 눈에 안 띄게 subtle하게"
```

```
[Works 카드 영역 선택]
→ "카드 모서리를 더 둥글게, 
    호버했을 때 살짝 떠오르는 shadow 효과 추가"
```

```
[블로그 카드 목록 선택]
→ "지금 2열인데 3열로 바꾸고, 
    카드 간격을 좀 더 여유있게"
```

이런 식으로 구체적으로 묘사하면서 반복합니다. 한 번에 완벽한 결과가 나오기를 기대하지 말고, 여러 번 수정하면서 원하는 방향으로 좁혀가는 겁니다.

---

여기서 한 가지 주의사항이 있어요. Stitch 결과물이 완벽하게 내 취향과 맞지 않아도 괜찮습니다. 80% 정도만 방향이 맞아도 충분합니다.

왜냐하면, Stitch는 레퍼런스를 만드는 용도고, 실제 구현은 Claude Code가 하기 때문입니다. Claude Code로 구현할 때 세부 조정이 얼마든지 가능해요.

---

오른쪽 화면이 이 과정으로 나온 결과물입니다.

이 스타일을 레퍼런스로 가지고 다음 클립에서 Claude Code로 실제 동작하는 페이지를 만들겠습니다.

---

한 가지 더 팁을 드리고 마무리할게요.

Stitch 프롬프트를 쓸 때 디자이너들이 많이 쓰는 형용사들이 있어요.

`minimal`, `clean`, `sophisticated`, `editorial`, `brutalist`, `playful`, `professional`, `dark`, `airy` 같은 단어들인데요. 영어로 넣으셔도 됩니다. Stitch가 이런 디자인 키워드를 잘 이해하거든요.

예를 들어 "editorial and minimal, data visualization portfolio" 이런 식으로 넣으시면, 잡지스러운 느낌의 미니멀한 시안이 나옵니다. 분위기 형용사를 영어로 쓰고, 세부 설명은 한국어로 써도 괜찮아요.
