## s12 — CLIP 03 섹션 브레이크

**[화면: Clip 03 섹션 브레이크]**

세 번째이자 마지막 클립입니다.

지금까지 뭘 했는지 잠깐 복습하고 갈게요.

첫 번째 클립에서 Stitch로 블로그 디자인 방향을 잡았습니다. 어떤 색상, 어떤 레이아웃, 어떤 분위기의 블로그를 만들건지 시각적으로 확인했어요. 레퍼런스 찾고, 여러 테마 한 번에 뽑아보고, 마음에 드는 걸 골라서 세부 수정까지 해봤습니다.

두 번째 클립에서 `portfolio-blog-kit.html` 키트 파일을 Claude Code로 커스터마이징했습니다. 내 이름, 역할, 카테고리, 색상이 들어간 포트폴리오 블로그를 만들었고요. Notion 데이터베이스도 세팅해서 블로그와 연결했습니다. API 토큰 만들고, MCP 연결하고, `.env` 설정까지 다 끝냈어요.

이 두 클립을 다시 요약하면, 클립 1은 "무엇을 만들지" 결정하는 기획 단계였고, 클립 2는 "실제로 그걸 코드로 만드는" 빌드 단계였습니다. 하나는 시각적인 방향을 잡는 작업, 다른 하나는 그 방향을 실제로 동작하는 소프트웨어로 바꾸는 작업이었어요. 이 둘을 분리해서 진행한 이유는, 처음부터 "코드"와 "디자인"을 동시에 고민하면 둘 다 어중간해지기 쉽기 때문입니다. 방향을 먼저 정하고 나서 구현에 들어가는 게 훨씬 결과물이 깔끔하게 나옵니다.

지금 여러분 컴퓨터에는 완성된 포트폴리오 블로그 코드가 로컬에 있는 상태입니다. `npm run dev`로 실행하면 브라우저에서 잘 보이고요. 근데 이건 아직 여러분 컴퓨터에서만 보이는 거에요. 다른 사람이 볼 수 없습니다.

이제 마지막 단계입니다. 이 블로그를 인터넷에 공개하는 거에요.

세 번째 클립에서 하는 건 크게 세 가지입니다. 첫째, 콘텐츠 업데이트 파이프라인 — 새 글을 올릴 때마다 어떻게 하는지 미리 보고요. 둘째, Netlify 배포 — 처음 배포하는 방법. 셋째, 완성된 결과물을 실제로 둘러보면서 여러분이 앞으로 참고할 만한 레퍼런스들도 같이 소개해드릴게요.

이 클립이 끝나면 여러분은 `xxx.netlify.app` 주소의 본인 포트폴리오 블로그 URL을 갖게 됩니다. 그리고 그 이후에 어떻게 채워나가면 좋을지, 어떤 사례들을 참고하면 좋을지까지 다 알게 되실 거에요.

배포라는 단어가 좀 무겁게 느껴지실 수 있는데요. 사실 개념 자체는 간단합니다. 지금 여러분 컴퓨터에서만 보이는 코드를, 인터넷 어딘가의 서버에 올려서 누구나 URL로 접속할 수 있게 만드는 것뿐이에요. 예전에는 이 과정이 서버를 직접 빌리고, 설정하고, 관리하는 복잡한 일이었는데요. Netlify 같은 서비스가 나오면서 GitHub에 코드만 올려두면 나머지는 자동으로 처리해주는 시대가 됐습니다. 여러분은 그냥 "GitHub에 코드 올리기"와 "Netlify에 연결하기" 이 두 가지만 하시면 됩니다.

## s13 — 콘텐츠 업데이트 파이프라인

**[화면: 5단계 자동화 파이프라인 + 코드블록]**

배포 방법 설명 전에, 배포한 다음 어떻게 블로그를 운영하는지를 먼저 보여드릴게요. 왜냐면 이 구조가 얼마나 편리한지 알아야 "왜 이렇게 복잡하게 만드냐"는 질문의 답이 나오거든요.

지금까지 배운 걸 생각하면 이런 의문이 드실 수 있어요. "API 토큰 만들고, MCP 연결하고, `.env` 파일 만들고... 이렇게까지 복잡하게 세팅했는데, 나중에 글 하나 올릴 때마다 이 과정을 또 반복해야 하나?" 다행히 아닙니다. 초기 세팅은 한 번만 하면 되고, 그 다음부터는 정말 간단해져요.

---

포스트를 새로 올릴 때 전체 흐름입니다.

**1단계.** Notion에서 글을 씁니다. 새 행을 추가하고, 제목 입력하고, 내용 작성하고, Published 체크. 이건 여러분이 원래 Notion 쓰던 방식 그대로에요. 새로운 걸 배울 필요가 없습니다.

조금 더 구체적으로 보면, 행을 클릭해서 들어가면 일반 Notion 페이지처럼 에디터가 열립니다. 제목 쓰고, 본문에 텍스트·이미지·구분선·목록 같은 블록들을 자유롭게 넣으시면 돼요. `notion-to-md`라는 라이브러리가 이 블록들을 자동으로 마크다운으로 변환해주기 때문에, 여러분은 이미지 삽입이나 소제목 같은 걸 평소 Notion 쓰던 대로 그냥 쓰시면 됩니다. 코드블록을 넣고 싶으면 Notion의 코드블록 기능을 그대로 쓰시면 되고, 표를 넣고 싶으면 Notion 표 기능을 쓰시면 돼요. 대부분의 Notion 블록 타입이 웹으로 잘 옮겨집니다.

**2단계.** Claude Code 채팅창에 이렇게 요청합니다.

```
Notion에 새로 쓴 글 동기화하고,
GitHub에 커밋해서 push까지 해줘.
```

이 한 줄이면 Claude Code가 뒤에서 `npm run sync`를 실행하고, 결과를 확인하고, 문제없으면 `git add`, `git commit`, `git push`까지 순서대로 다 처리해줍니다. 명령어를 외울 필요가 없어요.

내부적으로 무슨 일이 일어나는지 궁금하실 수 있으니 설명드릴게요. `npm run sync`가 실행되면 세 가지를 합니다. Notion API를 호출해서 Published된 포스트 데이터 전체를 가져오고, 그걸 `posts.json` 파일로 저장하고, 커버 이미지가 있으면 로컬에 다운로드합니다.

터미널이나 Claude Code 응답에 이런 메시지가 보이면 성공입니다:

```
✓ Syncing posts from Notion...
✓ Found 4 published posts
✓ Downloading cover images...
✓ Saved to src/data/posts.json
✓ Done!
```

만약 이 메시지가 안 뜨고 에러가 난다면, 대부분 두 가지 중 하나에요. `.env` 파일의 토큰이 잘못됐거나, Notion 데이터베이스에 Integration이 연결이 안 되어 있거나. 이럴 땐 Claude Code한테 "sync가 실패했는데 왜 그런지 확인해줘"라고 그대로 물어보시면 됩니다. 지난 클립에서 했던 STEP 1, STEP 2 연결 상태까지 같이 확인해줄 거에요.

**3단계는 따로 없습니다.** 방금 프롬프트 하나로 sync와 push가 한 번에 끝났거든요. 직접 터미널에 타이핑하는 걸 좋아하시는 분들을 위해 원래 명령어도 알려드릴게요.

```
npm run sync
git add . && git commit -m "update posts" && git push
```

이 두 줄이 방금 프롬프트가 실제로 실행한 내용이에요. 프롬프트로 하든 직접 타이핑하든 결과는 똑같습니다.

**4단계.** Netlify가 GitHub 변화를 감지해서 자동으로 빌드를 시작합니다. 빌드가 완료되면 배포가 됩니다. 보통 2-3분 걸려요.

**5단계.** 공개 URL이 업데이트됩니다. 아무것도 할 것 없이, 사람들이 URL로 접속하면 새 글이 보입니다.

---

이게 처음에 복잡해 보이지만, 실제로 해보시면 글 하나 올릴 때 터미널에서 두 줄 실행하는 게 전부입니다.

비교해드릴게요. 기존 방식이랑요.

티스토리 블로그라면 → 에디터 열고, 글 쓰고, 이미지 업로드하고, 발행 버튼 누르면 끝이에요. 편합니다. 근데 디자인을 마음대로 못 바꿔요. 커스텀 도메인 쓰려면 유료이고, 광고가 달려요. 그리고 무엇보다 "내 것"이라는 느낌이 잘 안 들어요. 다른 티스토리 블로그들이랑 결국 비슷하게 생겼으니까요.

Velog라면 → 개발자 친화적이고 마크다운 지원이 잘 되어 있어서 쓰기 편합니다. 근데 이것도 마찬가지로 레이아웃, 색상 전부 고정이에요. Works 섹션 같은 것도 없고요. 순수하게 글만 쌓이는 구조입니다.

GitHub Pages + Jekyll이라면 → 마크다운 파일 직접 작성하고, 로컬에서 빌드 확인하고, git push 합니다. 커스터마이징은 자유롭지만, Notion처럼 편한 에디터가 없어요. 글 쓸 때마다 마크다운 문법 신경 써야 하고, 이미지 넣는 것도 번거롭습니다.

우리가 만든 구조는 **Notion의 편리한 에디터 + 완전한 디자인 커스터마이징 + 자동 배포**가 합쳐진 형태입니다. 처음 세팅에 시간이 걸리지만, 세팅 이후는 가장 편한 방식이에요. 그리고 결정적으로, 나만의 디자인이라는 점에서 다른 방식들과 완전히 달라집니다.

---

여기서 자주 나오는 질문들을 몇 개 미리 답해드릴게요.

**"포스트를 한꺼번에 여러 개 써도 되나요?"**

네, 됩니다. `npm run sync`는 Published 체크된 포스트를 전부 한 번에 가져와요. 그러니까 Notion에서 다섯 개를 미리 써두고 나중에 한꺼번에 Published 체크한 다음 sync 한 번만 돌려도 다섯 개가 동시에 반영됩니다.

**"이미지 용량이 크면 어떻게 되나요?"**

Notion에 업로드한 이미지가 크면, sync 과정에서 그 원본 그대로 다운로드됩니다. 너무 큰 이미지는 로딩이 느려질 수 있어요. 되도록 업로드 전에 이미지를 2MB 이하로 압축해서 올리는 걸 추천드려요. Squoosh 같은 무료 웹 압축 도구를 쓰시면 됩니다.

**"sync를 자동화할 수는 없나요? 매번 터미널 여는 것도 귀찮은데."**

가능합니다. GitHub Actions로 스케줄을 걸어서, 예를 들어 매일 자정에 자동으로 `npm run sync` → `git push`를 실행하게 만들 수도 있어요. 이렇게 하면 Notion에서 글만 쓰고 Published 체크만 해두면, 터미널을 아예 안 열어도 알아서 하루에 한 번 반영됩니다. 이건 이번 강의 범위를 넘어서는 내용이라 오늘은 다루지 않지만, 나중에 익숙해지시면 Claude Code한테 "이 sync 과정을 GitHub Actions로 매일 자동 실행되게 만들어줘"라고 요청해보세요. 충분히 가능한 작업입니다.

**"글을 수정하거나 삭제하고 싶으면요?"**

Notion에서 그 글을 수정하고 다시 `npm run sync` → `git push`만 하면 됩니다. 삭제하고 싶으면 Notion에서 Published 체크를 해제하거나, 행 자체를 지우고 다시 sync하면 블로그에서도 사라집니다.

---

실제로 해보겠습니다.

**영상 잠깐 멈추시고 Notion에서 테스트 포스트 하나를 작성해보세요.**

제목은 아무거나 넣어도 되고요. Description도 짧게, Published 체크하시면 됩니다.

그 다음에 Claude Code한테 "방금 쓴 글 동기화해줘"라고 요청해보세요. 포스트 데이터가 잘 가져와지는지 확인하시고요.

---

sync가 잘 되는 걸 확인하셨으면 다음 단계로 갑니다.

## s14 — Netlify 배포 설정

**[화면: Netlify 3단계 + netlify.toml 코드블록]**

이제 배포입니다. 처음 배포하는 과정은 세 단계로 나눠집니다. STEP 1은 GitHub 레포 준비, STEP 2는 Netlify 연결, STEP 3은 환경변수 설정입니다.

여기서 "왜 Netlify를 쓰냐"는 질문을 하실 수도 있는데요. 비슷한 서비스로 Vercel도 많이 쓰입니다. Vercel은 Next.js를 만든 회사에서 운영하는 서비스라서 Next.js 프로젝트에 특히 최적화되어 있고요. Netlify는 특정 프레임워크에 종속되지 않고 정적 사이트, React, Vue 어떤 프로젝트든 잘 붙는 편입니다. 우리 프로젝트는 Vite + React라서 둘 다 잘 동작하는데, 이번 강의에서는 설정 화면이 좀 더 직관적인 Netlify로 진행하겠습니다. 나중에 Vercel도 궁금하시면 거의 동일한 방식으로 GitHub 연결하고 배포하실 수 있어요.

---

**STEP 1 — GitHub 레포 준비**

먼저 GitHub에 코드를 올려야 합니다. 근데 이 과정, `git init`이니 `git remote add`니 하는 명령어를 하나도 안 외우셔도 됩니다. **GitHub CLI**라는 도구 하나만 준비해두면, 나머지는 전부 Claude Code한테 말로 시킬 수 있어요.

**한 번만 하는 준비: GitHub CLI 설치 + 로그인**

터미널에 딱 한 줄만 입력합니다. Mac이라면:

```
brew install gh
```

설치가 끝나면 로그인을 한 번 해줘야 해요.

```
gh auth login
```

몇 가지 질문이 나오는데, 화살표 키로 "GitHub.com" → "HTTPS" → "Login with a web browser" 순서로 선택하시면 브라우저가 자동으로 열리면서 GitHub 로그인 화면이 뜹니다. 로그인하고 승인 버튼만 누르면 끝이에요. 이 로그인은 이 컴퓨터에서 딱 한 번만 하면 되고, 다음부터는 안 하셔도 됩니다.

이 두 줄 입력하는 것도 번거로우시면, Claude Code한테 "GitHub CLI 설치해줘"라고 요청하셔도 됩니다. Claude Code가 `brew install gh`는 대신 실행해줄 수 있는데, 로그인은 브라우저 인증이 필요한 부분이라 그 단계만 직접 하시면 됩니다.

**여기서부터는 전부 프롬프트입니다.**

GitHub CLI 준비가 끝났으면, Claude Code 채팅창에 이렇게 입력하세요.

```
이 프로젝트를 GitHub에 새 레포지토리로 만들어서 올려줘.
레포 이름: portfolio-blog
Public으로 만들어줘.
```

이 한 문단이면 끝입니다. Claude Code가 뒤에서 `git init`, `git add`, `git commit`, `gh repo create`, `git push`를 순서대로 알아서 실행해줘요. 중간에 확인 요청이 뜨면 승인만 해주시면 됩니다.

레포 이름은 영문 소문자와 하이픈만 쓰는 게 좋습니다. 예: `portfolio-blog`, `sy-portfolio`, `data-portfolio` 이런 식으로요. 이 이름이 나중에 `xxx.netlify.app` 기본 도메인의 일부로 쓰이는 경우도 있어서, 짧고 명확한 이름을 추천드려요.

Public으로 만드는 걸 추천드려요. 참고로 개인 계정의 Private 레포도 Netlify 무료 플랜에서 문제없이 연결됩니다 — 다만 조직(Organization) 계정 소유의 Private 레포는 Netlify 유료 플랜(Pro)이 필요해요. 오늘은 개인 계정으로 만드는 거니까 Public이든 Private이든 배포 자체는 똑같이 됩니다. 그래도 포트폴리오는 남들에게 보여주는 목적이니 Public으로 만들어두시는 게 자연스럽습니다.

완료되면 Claude Code가 생성된 레포 URL을 알려줄 거에요. 그 주소를 브라우저로 열어서 코드가 잘 올라갔는지 확인하시면 됩니다.

---

잠깐, 여기서 실수하기 쉬운 것들을 짚고 갈게요. 실제로 수강생분들이 자주 걸리는 부분들이에요. 이것도 전부 Claude Code한테 물어보면서 확인하시면 됩니다.

**첫 번째 실수: `.env` 파일이 올라가는 경우.**

직접 확인할 필요 없이 Claude Code한테 이렇게 물어보세요. "`.env` 파일이 방금 커밋한 내용에 포함됐는지 확인해줘." 만약 포함되어 있다면 "`.gitignore`에 `.env` 추가하고, 이미 커밋된 `.env`는 Git 추적에서 안전하게 제거해줘"라고 요청하면 Claude Code가 처리해줍니다.

혹시 이미 push까지 해버렸다면, 단순히 제거하는 것만으로는 안 됩니다. 이미 히스토리에 올라간 파일이거든요. 그럴 땐 Notion에서 API 토큰을 재발급하는 게 가장 안전합니다. 예전 토큰은 무효화하고 새 토큰으로 `.env`를 다시 설정하세요.

**두 번째 실수: node_modules가 올라가는 경우.**

`node_modules` 폴더가 수백 MB라서 이게 GitHub에 올라가면 push가 엄청 오래 걸리고 레포가 거대해집니다. Claude Code한테 "`.gitignore`에 node_modules가 포함되어 있는지 확인해줘"라고 물어보시면 됩니다.

**세 번째 실수: 빌드 안 됨.**

Claude Code한테 "`package.json`에 sync랑 build 스크립트가 제대로 정의되어 있는지 확인해줘"라고 요청하세요. Claude Code가 처음에 만들어줬으면 이미 되어 있을 확률이 높지만, 혹시 모르니 한 번 더 확인하는 게 안전합니다.

---

**STEP 2 — Netlify에서 레포 연결**

Netlify.com에 접속합니다. 계정이 없으시면 GitHub 계정으로 가입하시면 됩니다. GitHub 계정으로 가입하면 별도 이메일 인증 없이 바로 시작할 수 있어서 편해요.

로그인 후 대시보드에서 **Add new site** → **Import an existing project** 를 클릭합니다.

처음 클릭하면 Git 제공자를 선택하는 화면이 나와요. GitHub, GitLab, Bitbucket 같은 옵션이 있는데, 우리는 GitHub을 선택합니다. 처음 연결하는 거라면 GitHub 계정 인증 창이 뜨는데, "Authorize Netlify"를 눌러서 권한을 승인해주세요.

권한을 승인하면 내 GitHub 레포 목록이 쭉 나옵니다. 방금 만든 레포를 찾아서 선택하세요. 레포가 많으신 분들은 검색창에 레포 이름을 입력하면 바로 찾을 수 있어요.

그러면 빌드 설정 화면이 나옵니다. 여기가 중요합니다.

보통 Netlify가 자동으로 빌드 명령어를 감지하는데, 우리 프로젝트는 `npm run sync`가 빌드 전에 먼저 실행되어야 합니다. 그래서 빌드 명령어를 직접 입력해야 해요.

---

이걸 위해서 `netlify.toml`이라는 설정 파일이 필요한데요. 이것도 직접 만드실 필요 없습니다. Claude Code한테 이렇게 요청하세요.

```
Netlify 배포용 netlify.toml 파일 만들어줘.
빌드 전에 npm run sync를 먼저 실행하고 npm run build로 빌드해줘.
publish 폴더는 dist, Node 버전은 18로 설정해줘.
```

그러면 Claude Code가 프로젝트 루트 폴더에 아래 내용 그대로 파일을 만들어줍니다.

```toml
[build]
  command = "npm run sync && npm run build"
  publish = "dist"

[build.environment]
  NODE_VERSION = "18"
```

내용을 잠깐 설명드리면, 빌드 명령어를 `npm run sync && npm run build`로 지정한 거고요. **파일 위치는 프로젝트 루트 폴더**, 즉 `package.json`이랑 같은 위치에 있어야 합니다. Claude Code가 만들어주면 자동으로 올바른 위치에 생성되니, 여러분은 위치를 신경 쓰지 않으셔도 됩니다.

`&&`는 "앞 명령어가 성공하면 다음 명령어 실행"이라는 의미입니다. sync가 성공해야 build가 실행돼요. sync가 실패하면 build도 멈춥니다.

NODE_VERSION 18을 지정하는 이유는, Netlify의 기본 Node 버전이 낮을 수 있어서 명시적으로 지정해주는 겁니다.

---

**중요: 환경변수는 netlify.toml에 쓰지 마세요.**

가끔 "netlify.toml에 환경변수 설정하면 안 되나요?"라고 물어보시는 분들이 있는데요. 안 됩니다.

netlify.toml은 GitHub에 올라가는 파일이에요. 여기에 `NOTION_API_KEY`를 쓰면 API 키가 공개 레포에 올라가버립니다. 이건 심각한 보안 문제입니다. 누가 그 키로 내 Notion 데이터에 접근할 수 있어요.

환경변수는 반드시 Netlify 대시보드에서만 설정합니다.

여기서 "제 코드 전체가 GitHub에 공개되는 건데, 코드 자체를 남들이 보는 게 부담스러워요"라고 걱정하시는 분들도 계세요. 이해합니다. 근데 다시 생각해보면, 코드 자체보다 훨씬 더 중요한 건 API 키 같은 진짜 비밀 정보고, 그건 방금 말씀드린 것처럼 `.env`와 환경변수로 완전히 분리되어 있어요. 코드 자체는 오히려 공개되어 있는 게 장점이 될 수도 있습니다. 채용담당자나 다른 개발자가 "이 사람이 어떻게 코드를 짰는지" 궁금해할 때, GitHub 링크 하나로 다 보여줄 수 있거든요. 정 부담스러우시면 나중에 레포를 Private으로 바꾸셔도 되는데, 그러면 GitHub Pages 같은 무료 정적 호스팅은 안 되고, Netlify 개인 계정 Private 레포 정도까지만 무료로 가능하다는 점 참고하세요.

---

**STEP 3 — Netlify 대시보드에서 환경변수 설정**

Netlify에서 사이트 배포가 진행되는 동안, 설정으로 이동합니다.

사이트 대시보드 → **Site settings** → **Environment variables** 로 갑니다.

`Add a variable` 버튼을 클릭하고:

- Key: `NOTION_API_KEY`, Value: (`.env` 파일에 있는 값)
- Key: `NOTION_DATABASE_ID`, Value: (`.env` 파일에 있는 값)

이렇게 두 개를 추가합니다. 값을 입력할 때 앞뒤에 공백이 들어가지 않게 조심하세요. 복사 붙여넣기 하다 보면 가끔 스페이스가 같이 딸려오는 경우가 있는데, 그러면 토큰 인증이 실패합니다.

추가한 다음에는 반드시 **재배포(Trigger deploy)**를 한 번 해줘야 해요. 환경변수는 다음 빌드부터 적용되기 때문에, 지금 배포가 이미 시작됐거나 끝난 상태라면 Deploys 탭에서 "Trigger deploy" 버튼을 눌러서 새로 빌드를 돌려주셔야 합니다.

---

잠깐, 여기서 Netlify 무료 플랜 제한에 대해 말씀드릴게요.

Netlify 무료 플랜은 월 빌드 시간 300분이 한도입니다. 우리 프로젝트 한 번 빌드에 보통 1-2분 걸리니까, 300분이면 월 150번 이상 배포가 가능해요. 포트폴리오 블로그 운영하는 데 전혀 부족하지 않습니다.

그리고 Netlify 무료 플랜에서는 `xxx.netlify.app` 형태의 도메인을 기본으로 줍니다. 나중에 개인 도메인이 생기면 Netlify 대시보드에서 연결할 수 있어요. 도메인 연결도 강의 자료에 가이드로 포함되어 있습니다.

---

배포가 완료되면 Netlify 대시보드에 URL이 나옵니다. 그 URL로 접속해보세요.

처음 들어가면 "Site not found" 가 나올 수도 있어요. 이건 배포가 아직 진행 중인 경우입니다. Deploys 탭에서 진행 상황을 볼 수 있어요. 초록색 체크가 뜨면 완료입니다.

---

배포 완료 후 확인할 것들:

**첫 번째, Notion 포스트가 잘 보이는가.** 아까 Notion에 만들어둔 테스트 포스트가 블로그 화면에 나와야 합니다.

**두 번째, 카테고리 필터가 동작하는가.** Blog 탭에서 카테고리 클릭하면 필터링이 되어야 합니다.

**세 번째, 모바일에서 보기.** 핸드폰으로 URL을 열어보세요. 반응형이 잘 되어 있는지 확인합니다.

---

문제가 생겼을 때 확인하는 법도 알려드릴게요.

Netlify 대시보드 → Deploys 탭 → 해당 배포 클릭하면 빌드 로그를 볼 수 있습니다. 오류가 나면 여기서 어떤 이유로 실패했는지 나와요.

가장 흔한 오류들:

```
Error: NOTION_API_KEY is not defined
```
→ Netlify 대시보드에 환경변수가 설정되어 있지 않은 경우. Site settings → Environment variables에서 확인하세요.

```
Error: Cannot find module '@notionhq/client'
```
→ 패키지가 설치되지 않은 경우. `package.json`에 dependencies가 있는지 확인하세요.

```
Build failed: npm run sync exited with code 1
```
→ Notion API 연동에 문제가 있는 경우. Database ID가 맞는지, 데이터베이스에 Integration이 연결되어 있는지 확인하세요.

이 세 가지 오류 중 하나에 해당하는 경우가 대부분입니다. 그리고 혹시 이 셋 다 아닌데 실패한다면, 빌드 로그를 위에서부터 천천히 읽어보시면 대부분 어디서 막혔는지 영어로 친절하게 나와 있어요. 에러 메시지를 그대로 복사해서 Claude Code한테 물어보는 것도 좋은 방법입니다.

---

빌드는 성공했는데 화면에서 문제가 생기는 경우도 있어요. 두 가지만 더 말씀드릴게요.

**첫 번째, 홈 화면은 잘 보이는데 블로그 포스트 URL로 직접 들어가면 "Page not found"가 뜨는 경우.** 이건 우리 블로그가 React로 클라이언트 사이드 라우팅을 쓰기 때문에 생기는 문제에요. `/blog/포스트ID` 같은 주소로 새로고침하거나 직접 접속하면, Netlify 서버는 그 경로에 해당하는 실제 파일이 없다고 생각해서 404를 띄웁니다.

해결 방법은 간단합니다. Claude Code한테 이렇게 요청하세요.

```
Netlify에서 블로그 포스트 URL로 직접 접속하면
404가 뜨는 문제가 있어. _redirects 파일로 해결해줘.
```

그러면 Claude Code가 프로젝트의 `public` 폴더 안에 `_redirects`라는 파일을 만들고 이 한 줄을 넣어줍니다.

```
/*  /index.html  200
```

이 한 줄이 "어떤 경로로 접속하든 일단 index.html을 보여주고, 그 다음 React가 알아서 라우팅을 처리하게 해줘"라는 뜻이에요. 이 내용을 직접 외우실 필요는 없고, 저 프롬프트 하나만 기억해두시면 됩니다.

**두 번째, 화면이 하얗게 비어있는 경우.** 브라우저 개발자 도구(F12)를 열어서 콘솔 탭을 확인해보세요. 대부분 자바스크립트 에러 메시지가 빨간색으로 나와 있을 거에요. 그 메시지를 복사해서 Claude Code한테 붙여넣고 물어보면 원인을 바로 찾아줍니다.

**세 번째, Published 체크했는데 블로그에 글이 안 보이는 경우.** 이럴 땐 순서를 거꾸로 확인하시면 됩니다. 먼저 로컬에서 `npm run sync`를 다시 실행해서 터미널에 그 포스트가 잡히는지 확인하세요. 안 잡힌다면 Notion 쪽 문제입니다 — Published 체크가 진짜 되어 있는지, Category 같은 필수 속성이 비어있진 않은지 보세요. 로컬에서는 잡히는데 배포된 사이트에는 안 보인다면, `git push`를 안 하셨거나 Netlify 빌드가 아직 안 끝난 경우일 가능성이 높습니다. Netlify Deploys 탭에서 최신 배포가 완료됐는지 확인해보세요.

---

첫 배포는 실제로 빌드 로그를 처음부터 끝까지 한 번 지켜보시는 걸 추천드려요. Deploys 탭에 들어가면 로그가 실시간으로 스크롤되면서 올라오는데요.

맨 처음에 "Installing dependencies" 라는 줄이 뜨고, `npm install`이 실행되면서 패키지들을 하나씩 받아옵니다. 이게 보통 30초에서 1분 정도 걸려요.

그 다음 "Running build command" 가 뜨면서 우리가 넣은 `npm run sync && npm run build`가 실행돼요. sync 단계에서 "Syncing posts from Notion..." 같은 메시지가 지나가고, 이어서 build 단계에서 Vite가 파일들을 번들링하는 로그가 쭉 나옵니다.

마지막에 "Site is live" 라는 초록색 메시지가 뜨면 성공입니다. 이 전체 과정을 한 번 지켜보시면, 나중에 뭔가 잘못됐을 때 "아, 이 단계에서 멈췄구나"를 바로 알아챌 수 있어요.

---

Netlify에는 또 하나 알아두면 좋은 기능이 있는데요. **Deploy Previews**라는 기능이에요. 나중에 GitHub에서 브랜치를 나눠서 작업하고 Pull Request를 만들면, Netlify가 그 PR 전용으로 별도의 미리보기 URL을 자동으로 만들어줍니다. 메인 브랜치에 합치기 전에 변경사항을 미리 확인할 수 있는 기능이에요.

지금 당장은 안 쓰셔도 되지만, 나중에 블로그에 새 기능을 추가하거나 큰 디자인 변경을 할 때, 바로 메인에 반영하지 않고 미리보기로 먼저 확인하고 싶으시면 이 기능을 찾아보시면 됩니다.

특징 세 가지를 정리해드릴게요.

**첫 번째, Notion → 웹 자동 동기화.** Notion에서 글 쓰고, 터미널에서 두 줄 실행하면 블로그에 바로 반영됩니다. 한 번 익숙해지면 정말 편해요.

**두 번째, SEO 메타태그 자동 생성.** 블로그 URL을 카카오톡이나 LinkedIn에 공유하면 미리보기 이미지가 나오고, 제목과 설명이 나옵니다. 이게 `og:title`, `og:description`, `og:image` 메타태그 덕분인데요. Claude Code가 이걸 자동으로 생성해줬을 거에요.

이게 왜 중요하냐면요. 링크를 공유했을 때 그냥 텍스트 URL만 덩그러니 뜨는 것보다, 이미지와 제목이 카드 형태로 예쁘게 뜨는 게 훨씬 클릭을 유도합니다. 채용담당자한테 카톡이나 이메일로 포트폴리오 링크를 보낼 때도 마찬가지에요. 첫인상에서 이미 차이가 납니다.

**세 번째, 다크모드와 모바일 반응형.** 기본으로 지원합니다. 화면 오른쪽 아래 보시면 다크모드 토글 버튼이 있어요. 눌러보면 배경이 어두운 색으로 바뀌고, 텍스트 색상도 자동으로 반전돼서 가독성이 유지됩니다. 핸드폰으로 접속해도 레이아웃이 잘 맞아요. 사이드바가 상단 메뉴로 바뀌거나 접히는 방식으로 반응형 처리가 되어 있습니다.

이 두 가지가 왜 중요하냐면요. 요즘은 채용담당자나 면접관이 포트폴리오 링크를 컴퓨터로만 보는 게 아니라, 이동 중에 핸드폰으로 확인하는 경우도 많거든요. 그리고 다크모드는 시스템 설정을 따라가는 분들이 늘고 있어서, 이걸 지원 안 하면 밝은 배경이 뜬금없이 눈부시게 느껴질 수 있어요.

그리고 한국 사례에서는 화려하지 않아도 경력을 명확히 정리하는 것만으로 신뢰를 주는 방법, 성공담이 아니라 시행착오를 솔직히 기록하는 회고 글쓰기, 몇 년씩 꾸준히 쌓아가는 기록의 힘, 그리고 혼자가 아니라 여러 명이 같이 만드는 커뮤니티 블로그라는 선택지까지 봤습니다.

열한 개 사례가 스타일은 다 다르지만 공통점이 하나 있어요. 전부 "이 사람이 뭘 하는 사람인지"가 첫 화면에서 바로 읽힌다는 겁니다. 여러분 블로그도 마찬가지예요. 오늘 만든 사이드바 프로필과 About 페이지가 그 역할을 하고 있고, 앞으로 콘텐츠를 채우실 때도 이 원칙 하나만 기억하시면 됩니다 — 방문자가 3초 안에 "이 사람이 뭘 하는 사람인지" 알 수 있게 만들기.

여기까지가 오늘 준비한 레퍼런스들이고요. 마지막으로 블로그를 더 확장하고 싶으실 때 고려해볼 만한 방향들을 몇 가지 짚어드리고 마무리할게요. 오늘 당장 하실 필요는 없고, 나중에 여유가 생기면 Claude Code한테 하나씩 요청해보시면 됩니다.

**방문자 분석 추가.** Google Analytics나 Plausible 같은 도구를 붙이면, 어떤 글을 사람들이 많이 읽는지, 어디서 유입되는지 알 수 있어요. Claude Code한테 "Google Analytics 연동해줘"라고 하면 스크립트 태그 하나 추가하는 정도로 끝나는 작업입니다.

**댓글 기능 추가.** Giscus나 Utterances 같은 오픈소스 댓글 위젯은 GitHub 계정으로 로그인해서 댓글을 다는 방식인데, 블로그 자체에 회원 시스템을 만들 필요 없이 붙일 수 있어요. 방문자들이 피드백을 남길 수 있게 하고 싶으시면 고려해보세요.

**RSS 피드 추가.** 다른 사람들이 여러분 블로그를 구독하고 싶을 때 쓰는 기능이에요. 기술 블로그 독자층이 있는 분야라면 도움이 될 수 있습니다.

**검색 기능 추가.** 포스트가 많아지면 카테고리 필터만으로는 부족해질 수 있어요. 그때는 간단한 클라이언트 사이드 검색 기능을 추가하는 것도 방법입니다.

이런 것들은 전부 "언젠가 하면 좋은 것"이지 "지금 당장 해야 하는 것"은 아니에요. 지금은 일단 블로그를 배포하고, 글을 몇 개 채우는 게 먼저입니다. 나중에 콘텐츠가 쌓이고 나면, 그때 이런 기능들을 하나씩 추가해가시면 됩니다.

마지막으로 URL 공유 팁을 드릴게요.

`xxx.netlify.app` URL을 LinkedIn 프로필 "Website" 항목에 넣어두세요. 그러면 채용담당자나 면접관이 프로필을 볼 때 링크를 클릭할 수 있어요.

이력서에는 "포트폴리오: xxx.netlify.app" 이렇게 한 줄 추가하세요. 이게 있고 없고의 차이가 생각보다 큽니다.

그리고 나중에 개인 도메인을 사고 싶으시면, 가비아나 Namecheap 같은 도메인 등록 사이트에서 `.com` 도메인이 연 1만~2만 원 정도 합니다. Netlify 대시보드에서 연결하는 방법은 굉장히 간단하고, 공식 문서에도 잘 나와 있어요.

도메인 이름 고르실 때 팁을 하나 드리면, 본인 이름을 그대로 쓰시는 걸 추천드려요. `본인이름.com` 이나 `본인이름데이터.com` 이런 식으로요. "데이터분석전문가.com" 처럼 직무를 그대로 넣는 것보다, 본인 이름이 들어간 도메인이 나중에 브랜딩 관점에서 훨씬 오래 씁니다. 직무는 바뀔 수 있어도 이름은 안 바뀌니까요.

정리하는 차원에서, 배포까지 끝낸 다음 체크해보시면 좋은 항목들을 순서대로 짚어드릴게요. 이 순서대로 하나씩 확인하시면 됩니다.

**하나, 배포 URL이 정상 작동하는가.** 브라우저 시크릿 모드로 한 번 열어보세요. 로그인 상태나 캐시 없이 접속했을 때도 잘 보이는지 확인하는 게 제일 확실합니다.

**둘, 사이드바 정보가 전부 내 정보로 채워져 있는가.** 이름, 역할, 소개 태그, 링크들이 Claude Code가 넣어준 임시 텍스트가 아니라 실제 여러분 정보인지 다시 한 번 확인하세요.

**셋, Works 카드가 실제 작업물로 연결되어 있는가.** 클릭했을 때 진짜 Tableau Public이나 GitHub 링크로 이동하는지 하나씩 눌러보세요.

**넷, 최소 1개 이상의 블로그 포스트가 있는가.** 텅 빈 블로그보다는, 짧더라도 글 하나 있는 블로그가 훨씬 신뢰감을 줍니다.

**다섯, 모바일에서 확인했는가.** 실제로 핸드폰 브라우저로 접속해서 레이아웃이 깨지지 않는지 봐야 합니다. 채용담당자가 이동 중에 핸드폰으로 확인하는 경우도 많거든요.

**여섯, LinkedIn이나 이력서에 링크를 추가했는가.** 만들어놓고 아무 데도 안 알리면 아무도 안 봅니다. 꼭 눈에 띄는 곳에 링크를 넣어두세요.

이 여섯 가지만 체크하시면, 오늘 만든 포트폴리오 블로그를 바로 실전에 쓰실 수 있는 상태가 됩니다.

마지막으로 하나만 더 답해드릴게요. "이 블로그, 나중에 이직하거나 회사를 옮기면 계속 유지보수해야 하나요?"

전혀 부담 갖지 않으셔도 됩니다. Netlify는 배포해두면 별도 관리 없이 그대로 떠 있어요. 서버비도 무료 플랜 안에서는 안 나가고요. 코드를 안 건드리면 그 상태 그대로 유지됩니다. 가끔 새 글 올릴 때만 `npm run sync` 두 줄 실행하시면 되고, 아예 손 놓고 몇 달 계셔도 사이트가 사라지지 않아요. 부담 없이 시작하시면 됩니다.

자, 이걸로 P06 CH01 전체 챕터를 마칩니다.

세 클립 동안 Stitch로 디자인 기획하고, Claude Code로 빌드하고, Netlify로 배포하는 전 과정을 진행했습니다.

한 번 처음부터 순서를 되짚어보면요. 첫 번째 클립에서는 코드 한 줄 안 쓰고 디자인 방향부터 잡았습니다. 두 번째 클립에서는 그 방향을 참고해서 Claude Code가 실제 코드를 만들게 했고, Notion으로 콘텐츠를 관리할 수 있게 연결했습니다. 세 번째 클립에서는 그걸 인터넷에 공개하고, 앞으로 어떻게 운영하고 채워나갈지까지 봤어요.

이 세 단계를 관통하는 공통점이 하나 있습니다. 처음부터 끝까지, 여러분이 직접 코드를 짠 순간은 한 번도 없었다는 거에요. 대신 여러분은 계속 "무엇을 원하는지"를 프롬프트로 설명했고, AI가 그걸 실제로 구현했습니다. 이게 이번 챕터에서 진짜 배우신 능력입니다. 코딩 문법이 아니라, 원하는 결과를 구체적으로 설명하는 능력이요.

지금 여러분이 갖게 된 건 단순한 블로그가 아닙니다. Notion으로 관리하고, 자동으로 배포되는 포트폴리오 블로그 시스템입니다. 지금부터 꾸준히 글을 올리고 작업물을 채워나가면, 몇 달 뒤에는 오늘 보여드린 레퍼런스들 못지않은 포트폴리오가 될 수 있습니다.

오늘 만든 이 구조는 시작점일 뿐이에요. 완벽하게 만들고 시작하려고 하지 마시고, 일단 배포하고 하나씩 채워나가시길 권해드립니다.

이걸로 P06 CH01뿐 아니라 전체 커리큘럼도 마무리하게 됩니다. 여기서 전체 과정을 한 번 정리하고 넘어가겠습니다.

**Part 1**에서는 Claude Code를 설치하고 첫 세션을 시작하는 것부터, 좋은 데이터 시각화 원칙까지 기초를 다뤘습니다.

**Part 2**에서는 CLAUDE.md 설계, MCP, Skills 같은 Claude Code의 확장 기능들을 다뤘고요.

**Part 3**에서는 서브에이전트로 파이프라인을 구성해서, 여러 에이전트가 역할을 나눠 작업하는 구조를 만들었습니다.

**Part 4**에서는 그 파이프라인을 실제 데이터에 적용해서 대시보드·보고서를 자동 생성했고, OpenClaw로 텔레그램 연동까지 다뤘습니다. D3.js, Tableau Extension, 3D Globe 같은 인터랙티브 데이터 아트도 이 파트에서 만들어봤어요.

**Part 5**에서는 캠페인 성과, A/B 테스트, PM, 리텐션, HR 이렇게 다섯 가지 실무 대시보드를 각각 기획안부터 제작, 인사이트 도출까지 전체 사이클로 연습했습니다.

그리고 이번 **Part 6**에서는 그 모든 결과물을 담을 수 있는 포트폴리오 블로그를 Stitch, Claude Code, Notion, Netlify로 처음부터 배포까지 만들었습니다.

정리하면, Part 1~2는 Claude Code라는 도구를 다루는 법이었고, Part 3~4는 그 도구를 에이전트로 확장해서 자동화하는 법이었습니다. Part 5는 그렇게 배운 걸로 실무 대시보드를 실제로 만드는 법이었고, Part 6는 그 결과물을 밖으로 꺼내서 보여주는 법이었습니다.

이 전체 과정을 관통하는 공통점이 하나 있습니다. 어느 파트에서도 코드 문법을 외우거나 처음부터 직접 짜는 과정은 없었습니다. 대신 매 파트마다 "무엇을 원하는지"를 프롬프트나 CLAUDE.md, Skill로 구체화하는 연습을 반복했습니다. 도구는 Claude Code 하나였지만, 그걸 다루는 방식은 파트가 진행될수록 단일 명령 → CLAUDE.md 설계 → 에이전트 파이프라인 → 실무 대시보드 → 배포까지 계속 확장됐습니다.

오늘 만든 포트폴리오 블로그에, Part 5에서 만든 대시보드들을 Works 카드로 채우고, Part 4에서 만든 인터랙티브 데이터 아트도 프로젝트로 올려보시면 좋습니다. 지금까지 각 파트에서 따로 만들었던 결과물들이 이 블로그 하나로 모이게 됩니다.

여기까지 전체 커리큘럼이었습니다. 수고하셨습니다.
